* How this book works
This is a book about *building reasoning machinery in Prolog*. It assumes that facts, rules, queries, unification, recursion, lists, and ordinary backtracking are already familiar. If those ideas still feel like punctuation rather than tools, work through *Prolog for Beginners: Thinking in Relations* first. We will recap a prerequisite when it is essential to a symbolic-AI mechanism, but we will not hollow the foundations book out by teaching them badly a second time.

The projects here make normally implicit things explicit. We will build interpreters that turn proof search into data, planners whose state transitions can be inspected, knowledge graphs with provenance, abductive engines that distinguish evidence from assumptions, explanation systems that expose their justifications, production-rule engines that contrast with Prolog's native backward chaining, and a capstone that composes symbolic subsystems without pretending one inference strategy solves every problem.

The standalone sibling *Prolog + LLMs: Neuro-Symbolic Systems from First Principles* owns the explicit LLM, neuro-symbolic, and RLM arc. The repository-level README and research notes cross-link the two volumes; the packaged manuscript names the sibling without a relative file link that would escape this EPUB. Classical meta-interpretation, search, planning, provenance, constraints, abduction, and expert-system architecture stay here because they are useful whether or not an LLM exists.

Examples target SWI-Prolog and mark implementation-specific behavior. Documentation is not execution evidence: when this book says a behavior is TESTED, the exact runtime and command belong in the repository's verification record rather than being inferred from a manual page.

Project 1 begins immediately. Its first milestone is small enough to understand completely: an object program represented as data, an interpreter that proves goals against it, and a proof term that records *why* a goal succeeded. We then break that interpreter on purpose and add explicit control.

** 1.1 The move from using Prolog to interpreting Prolog-like rules
Ordinary Prolog source already describes relations. Suppose we write:

#+begin_src prolog
link(gateway, router).
link(router, cache).
link(cache, database).

reachable(X, Y) :-
    link(X, Y).
reachable(X, Y) :-
    link(X, Z),
    reachable(Z, Y).
#+end_src

When you ask =reachable(gateway, database)=, the Prolog engine chooses clauses, unifies heads with goals, executes bodies, and backtracks when a path fails. For day-to-day programming that implicit machinery is a gift. For symbolic AI it is also worth taking apart, because the moment we want a proof object, a custom search policy, provenance, an explanation, a resource limit, or a different rule language, “the engine does it” is no longer enough detail.

A *meta-interpreter* is a program that interprets another program or a program-like representation. SWI-Prolog exposes general meta-calling with =call/1= [cite:@swi-metacall], but invoking a term is not yet the educational goal. We want to own the object language ourselves so every rule application can be inspected.

** 1.2 Object language and meta language
Keep two levels separate:

- The *object language* is the little rule system being interpreted.
- The *meta language* is the Prolog implementation of the interpreter.

For Project 1, an object rule is data:

#+begin_src prolog
rule(RuleId, Head, Body)
#+end_src

A fact-like rule uses =true= as its body:

#+begin_src prolog
rule(f_link_gateway_router,
     link(gateway, router),
     true).
#+end_src

A derived rule stores a normal-looking term as its head and another term as its body:

#+begin_src prolog
rule(r_reach_direct,
     reachable(From, To),
     link(From, To)).

rule(r_reach_step,
     reachable(From, To),
     (link(From, Via), reachable(Via, To))).
#+end_src

Nothing about the term =reachable(From,To)= automatically executes here. It is data inside a =rule/3= term until the meta-interpreter gives it meaning. That distinction is the first big lever of symbolic programming: structures that resemble source code can be inspected, transformed, annotated, searched, or explained before they are ever treated as goals.

** 1.3 Why rule identifiers exist from day one
The first argument is not decorative. =r_reach_step= is a stable provenance label for this teaching program. A proof that merely says “yes” cannot later explain which rule justified a conclusion. A proof that records the chosen identifiers can.

We will eventually need richer provenance—source documents, timestamps, authorship, confidence policies, versioned assertions—but stable rule identity is the smallest useful seed. It also creates a concrete engineering invariant: two bundled rules should not silently share the same provenance identifier.

This is different from predicate identity. Both =r_risk_temp= and =r_risk_fan= may conclude =risk(Host)= while representing different justifications. The predicate tells us the kind of claim. The rule ID tells us which justification was used.

** 1.4 Why the first project does not start with =clause/2=
A tiny reflective interpreter is often demonstrated by asking the host Prolog system for a predicate's clauses. SWI-Prolog's =clause/2= can indeed enumerate matching clauses, but its contract includes real implementation boundaries: static-code inspection may be restricted by flags, and reconstructed clauses are guaranteed to be semantically equivalent rather than textually identical to original source [cite:@swi-clause]. Modules, built-ins, cut, compiler transformations, and protected predicates arrive immediately.

Those topics matter. They are exactly why we are *not* hiding them inside the first five lines of the book.

Milestone A therefore uses an explicit list of =rule/3= terms. The interpreter's current object language has only three forms:

1. =true=, which succeeds without selecting another object rule;
2. conjunction =(A,B)=, which proves =A= and then =B=;
3. an ordinary goal, which must unify with a rule head in the supplied program.

No interpreted cut. No interpreted negation. No arithmetic escape hatch. No arbitrary host predicate call. The small boundary is a feature: we can reason about it completely.

** 1.5 Lab -- read a rule as data
Open =books/symbolic-ai-prolog/code/meta-interpreter/programs.pl=. Before running anything, answer:

1. Which =rule/3= terms are facts?
2. Which two rules can justify =risk(alpha)=?
3. Which rule introduces recursion?
4. Which rule IDs should appear in a proof of =reachable(gateway,database)= if the route goes through =router= and =cache=?
5. Why is =RuleId= not derivable from the predicate name alone?

Then construct one new =rule/3= term by hand without adding it to the program. Ask yourself which pieces are syntax of the *meta language* and which pieces are data belonging to the *object language*.

** 2.1 Start with the base case
If the object goal is =true=, there is nothing more to justify:

#+begin_src prolog
prove_goal(_, true, true).
#+end_src

The third argument is already becoming useful: the interpreter does not merely succeed; it emits a proof artifact. For the control constant =true=, the proof artifact is simply =true=.

* Precise questions
** What is the current StarIntel release versus the wire schema version?
The current coordinated release/profile is *0.9.1*. Canonical documents still carry =schema_version="0.9.0"=. Those values are deliberately different. The current Python package is version 0.9.1, while its =SPEC_VERSION= constant remains =0.9.0=. Its schema lock records release =0.9.1=, wire schema =0.9.0=, schema path =starintel-doc-v0.9.0.schema.json=, and canonical schema commit =6479c0a9dc88ce9fed183515fc4df5d245de0b3a=.

The server's current v0.9 runtime document records the same distinction and additionally names schema revision =0.9.0+fields.20260909.1=. Therefore the book must not call the active release "0.9.0" merely because the immutable wire schema is named 0.9.0.

A fourth version-like value exists: a document's integer =version= field. It is a document revision field, not the wire schema version. Once persisted in CouchDB there may also be an =_rev= value, which belongs to CouchDB's MVCC/revision protocol rather than the StarIntel document-version contract.

** What actually happens at the canonical HTTP document boundary?
The current ASDF system loads =frontends/http-boundary-core=, then authentication/authorization files, then =frontends/http-authorization-routes=. The later authorization route file replaces =POST /new/document/:dtype= with =handle-authorized-new-document-route=. That handler performs strict document validation and calls =publish-document=. The latter calls =star.authorization:authorized-publish-document= before the unchecked RabbitMQ publication function.

The strict input validator checks a JSON object, non-empty =_id=, =dataset=, and =dtype=, optional route/body dtype agreement, exact wire =schema_version=, then =star.documents:validate-v09-document=. Schema failures become a typed =422 invalid_document_schema= response.

The server also injects server-side tenancy before RabbitMQ publication/persistence and strips that internal tenancy field on egress. The client-visible 0.9 document contract therefore must not be taught as if callers are expected to forge server-owned authorization/tenant context.

** Does a successful HTTP submit mean the record is durable?
No. The server's own current documentation says HTTP publication success means the producer call succeeded; it does not prove downstream persistence. The architecture is asynchronous:

#+begin_example
client
  -> HTTP boundary: parse + validate + authorize
  -> RabbitMQ documents.ingest.<dtype>
  -> ingest consumer
  -> CouchDB durable document
  -> RabbitMQ documents.new.<dtype>
  -> local/external actors
  -> derived documents may re-enter documents.ingest.<dtype>
#+end_example

That distinction is not RabbitMQ trivia. RabbitMQ's official documentation separates publisher confirms from consumer acknowledgements: the two mechanisms cover different links and are orthogonal. The book therefore treats "request accepted", "broker accepted", "consumer processed", and "document persisted" as distinct observations unless the exact runtime path proves otherwise.

** What is active, merely present, or historical?
The current server ASDF file is an executable inventory. It loads the auth/authorization systems, event and matcher actor files, RabbitMQ, HTTP boundary/auth routes, lifecycle, and other active services. A source file existing in the repository is insufficient evidence that it is active. The server architecture document itself calls out files that are present but not loaded.

This is especially important because some prose has drifted. =doc/http-authorization-runtime.org= is marked ACTIVE and its claims match loaded current source. Meanwhile older paragraphs in =README.org= and =doc/architecture.org= still state that built-in HTTP authentication/authorization is absent. For this book, executable load/route evidence wins; the prose conflict is recorded, not silently averaged away.

* Project 1 contract
Project 1 milestone A is a *consumer* of the real Python adapter, not a competing implementation. It pins =starintel-doc= commit =5857914a1e34ad18a6956b8ff0df5349de0ca099= and runs synthetic fixtures through the package's public validation and round-trip functions.

Acceptance oracles for this milestone:
1. a canonical synthetic =person= validates and round-trips without losing =extensions=;
2. a canonical synthetic =operation= validates under the 0.9.1 package while retaining wire =schema_version="0.9.0"=;
3. removing a required =_id= produces =missing_required_field=;
4. using a rejected dtype alias produces =invalid_enum=;
5. a date-time without an RFC 3339 zone produces =invalid_datetime=;
6. changing wire schema version to =0.8.0= raises the package's unsupported-version error.

These are book tests of the imported real boundary. They are not a claim that the book independently proves every schema branch.

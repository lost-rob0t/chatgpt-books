* Bounded local index capture
The Node capture wrapper limits each synthetic document to 2,048 emitted index
field/value pairs. The ceiling belongs to this teaching harness, *not* to
CouchDB/Clouseau or the production StarIntel server. The exact pinned server
index function remains unchanged. A document that would exceed this budget
raises an error and produces no partial JSON output; this is a failed lab
observation, not evidence that the document is unindexable in production.

Run =python3 -m unittest test_emission_budget -v= from the search-lab directory
(or use the existing =run-tests= suite with its pinned dependencies). Boundary
tests accept exactly 2,048 emissions, reject 2,049, and preserve regular
small-document projections. The injected array is synthetic, not collected data.

* Bounded pagination cycle check
The optional HTTP client's twelve-page limit remains the final resource bound,
but a shorter non-adjacent bookmark cycle (for example =A -> B -> A=) now
fails at the first recurrence instead of resubmitting an earlier cursor.
Continuation tokens are opaque; the client does not derive identities or
ordering from their contents. Repeated result identities remain a separate
error even when bookmarks themselves are distinct.

=python3 -m unittest test_bookmark_cycle -v= executes network-free response
doubles with the real =collect=, =interpret_page= and =next_bookmark= helpers.
These tests do *not* prove live CouchDB/Clouseau bookmark guarantees or stable
membership under concurrent writes; the opt-in HTTP tier remains untested.

* Hermetic multi-tenant fixture admission contract
=python3 -m unittest test_tenant_seed_contract -v= checks the five historical
synthetic fixture roles and the *declared* disposable configuration. It models
the pinned server's =tenant-adaptation-for= mapping and public dataset list;
it does NOT load native authorization machinery or prove real HTTP credential
acceptance. The opt-in service run remains UNTESTED without that server stack.

* Index projection and embedded-document agreement
The =interpret_page= teaching client keeps =fields= (stored search-index
projection) separate from =doc= (the embedded retrieved document). If both
supply scalar =dataset= or =dtype= strings and disagree, the client rejects
that hit rather than silently selecting the document value. Such disagreement
could indicate a changed record or a stale projection; it does not establish
which observation is current, nor does matching metadata prove a snapshot.
Missing stored fields remain missing, and a fields-only hit is not promoted
to a full document. The hermetic =test_index_document_consistency.py= covers
both disagreements, ordinary hits and existing tenant/revision checks.


* Require an object root for a captured projection

A JSON array, string, number, boolean or =null= is not a StarIntel document.
The historical JavaScript index can still emit a default =tenant_id= for some
non-object roots because JavaScript permits property lookup on non-null
primitives. That is an index-function emission, *not* a validated document.
=lab.projection()= now rejects a non-dictionary root before calling Node.

=python3 -m unittest test_projection_document_root -v= runs the actual pinned
index over a synthetic mapping and rejects scalar/array roots before Node. It
also preserves the existing rejection of non-finite JSON numbers. This
course-local shape guard does *not* validate a dictionary as canonical StarLang
0.10.1; the pinned generated SDK remains responsible for that admission.

* Strict JSON before historical index execution

=projection()= serializes synthetic Python fixtures before the pinned
JavaScript index consumes them. Python's default =json.dumps()= accepts
non-finite floats and emits =NaN=/=Infinity= spellings, but those tokens
are *not* valid JSON and cause Node's =JSON.parse()= to fail. The book's
transport boundary now uses =allow_nan=False= so invalid numeric inputs
raise a direct Python =ValueError= before invoking Node.

=python3 -m unittest test_projection_json_finite -v= covers NaN, both
infinities, nested values, finite numbers and booleans against the actual
pinned index capture. This is course-local input handling, not a change
to CouchDB, Clouseau or StarIntel Server's JSON policy. It proves neither
live search behavior nor canonical StarLang admissibility for non-finite
numbers.

* Distinct storage and canonical revision evidence
A historical embedded CouchDB document may expose =_rev= (storage MVCC)
while a canonical =0.10.1= record may expose =rev= (document contract).
They are not interchangeable. When both appear, =Hit.storage_revision=
and =Hit.canonical_revision= retain the two observed values separately.
The existing =Hit.revision= convenience field remains backward compatible
(storage value first), but its value alone does not identify the revision
namespace or establish canonical validation.

=python3 -m unittest test_dual_revision_evidence -v= checks both values,
single-source and fields-only hits, plus malformed shadowed revisions.
These are typed search-response observations, not proof that an embedded
document passed the generated SDK, was durable at query time, or shares a
snapshot with the index projection.

* Detach retained search evidence from mutable decoded pages
=Hit= uses a frozen Python dataclass for its outer attributes, but nested JSON
dictionaries are mutable. Previously =Hit.document= and =Hit.fields= aliased
the input response's nested objects. A caller changing or reusing that response
could later change the appearance of retained stored fields and provenance.
The client now deep-copies both validated payloads into a distinct observation
snapshot; =Hit.revision= and the original revision-origin fields are unchanged.

=python3 -m unittest test_evidence_detachment -v= covers mutable source pages,
nested provenance, stored fields, repeat interpretation, fields-only hits and
conflicting scope/type evidence. This detaches a hit *from its input page*;
it does not recursively freeze =Hit.document= or validate canonical truth.
These checks are course-local, not evidence of server-side consistency or
CouchDB durability.

* Reject contradictory search response envelopes
=interpret_page= treats a top-level =error= member as a failed observation
*even when* =rows= also contains an array. An otherwise well-shaped
={"rows":[],"error":"backend_failed"}= is not evidence of zero hits, and a
populated result alongside =error= cannot be trusted as a successful page.
The six network-free =test_mixed_error_envelope.py= regressions include both
mixed shapes, a null error member, ordinary empty and populated pages, and an
error-only response. These checks are for the book client; they do not prove
that a real server emits mixed envelopes or that live HTTP status mapping works.

* Historical HTTP seed versus actual search-field emissions
=python3 -m unittest test_historical_seed_projection -v= joins the five opt-in
historical =fixture()= variants to the *actual pinned JavaScript index capture*
in the hermetic runner. It verifies each document emits the exact =fname=
search term, its assigned dataset, and =person= dtype; it also demonstrates
nested-field precedence, null shadowing, and absence of =schema_version= in
the captured fields. A changed fixture/adapter can otherwise leave all by-ID
read-backs successful while the fielded search's positive controls never match.
The tests do not execute Lucene tokenization, server tenant adaptation,
authenticated middleware, live CouchDB/Clouseau or durable visibility. They
establish raw index-field emission for the synthetic historical fixture only;
server-side tenant metadata is intentionally not guessed from an offline seed.

* Server-owned tenant stamping before historical FTS indexing

A raw v0.9.0 fixture is *not* the server's internal indexed representation.
=fixture()= deliberately contains no =tenant= or =tenant_id=. If the exact pinned
historical JavaScript search index is executed directly on the raw fifth
=book-other-public= fixture, its =tenant_id= fallback emits =default=.
That does not mean the server's dataset-to-tenant map was ineffective:
=resolved-server-tenant= and =stamp-server-tenant!= at the pinned server
source derive and inject the configured tenant on the internal document before
the relevant bulk publish paths. The unchanged index then selects
=tenant_id=other= from the internally stamped document. It is incorrect to
submit =tenant_id= from a client just to make an offline projection look right.

=python3 -m unittest test_tenant_stamp_index -v= checks the exact original
server Lisp form fingerprints and bulk publish call sites, plus the pinned
JavaScript FTS index on the real synthetic client fixtures. The test uses a
clearly identified Python *model* of the internal stamp for the Node index
comparison: original SBCL Lisp stamping, credential admission, MQ, CouchDB,
Clouseau, durable persistence and actual authenticated search were *not*
executed by this new test. Unstamped =other= raw fixture produces default;
modeled server-stamped fixture produces other; the remaining four fixture
datasets stamp to default. The test also guards against altering the client
fixture and checks a pre-existing internal tenant is not overwritten.

This is a crucial pipeline boundary: raw fixture projection != server-stamped
index projection != indexed search visibility != durable canonical verification.

* Analyzer configuration is separate from index callback values

The pinned =source/views/search.json= declares a =perfield= analyzer: =dataset=
and =tenant_id= use =keyword=, as does =name=; =content= and the default use
=standard=. =dtype= and =title= therefore fall back to =standard= in this
historical design. These declarations matter when reading the server's scoped
search query, but a captured =index(name, value, store=true)= callback has
*not yet tokenized* =value= with Clouseau/Lucene.

Run =python3 -m unittest test_search_analyzer_contract -v= in the pinned
search-lab environment. The five tests read the original design document,
check the concrete per-field contract, and execute the unchanged JavaScript
index on a synthetic document where =name= and =content= contain identical
text. Both raw emissions remain identical despite different declared
analyzers. This is TESTED configuration and callback behavior, *not* a live
keyword/standard tokenizer, query containment, authorization, or ranking test.

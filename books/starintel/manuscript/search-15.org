* Chapter 15 -- Document Search: From Stored JSON to Authorized Evidence
:PROPERTIES:
:ID:       c28dc507-faf2-4e26-b1ba-bc2b8236e7af
:END:

A search result is an observation made through a particular query, index and
visibility policy. It is not the database itself. If you remember only one
operational distinction from this chapter, remember that accepting a document,
reading it back by identity, and finding it through full-text search are three
different observations. Each proves something useful; none substitutes for the
other two.

Consider a fictional cooperative. An ingest adapter submits its record, receives
an HTTP success, and immediately searches for its name. The search returns no
rows. A rushed diagnosis is "CouchDB lost the document." A better diagnosis asks:
was this an asynchronous acceptance, did the record reach durable storage, did
the index select the name field, did the query use the correct field, and was
this caller allowed to see that dataset and tenant? Those questions locate a
boundary you can inspect instead of turning every failure into a server restart.

This chapter begins Project 4, Add Search or Inference. Its deliverable is a
small search client, an executable inspection of the maintained index, and
contract tests. It does not implement a replacement authorization engine or a
parallel StarIntel database. It also does not claim relationship traversal,
vector retrieval, graph ranking, or automatic inference is available through
these two document-search routes.

** Choose the search surface deliberately

The two interfaces share a backend but establish their authority differently.
The authenticated operation is =documents.search=, declared in
=cli/http-contract-documents.lisp= and finally mounted in
=source/frontends/http-contract-routes.lisp=. Its stable route is
=GET /api/v1/documents/search=. It requires =search:read=.

The public-read route is =GET /api/v1/search=. Whether it permits anonymous
requests depends on server public-mode configuration. "Public-read surface"
describes the route's policy, not an immutable promise that every deployment
allows anonymous access. Its handler creates a server-owned public authorization
context; it does not reuse the caller's supplied identity or scopes.
[cite:@starintel-search-runtime-20261009]

#+caption: Public and authenticated search contract differences.
| Behavior at the inspected pin | Public search | Authenticated document search |
|-------------------------------+---------------+-------------------------------|
| Required =q= | Nonempty string | Nonempty string |
| Default =limit= | 25 | 25 |
| Accepted =limit= range | 1 through 50 | 1 through 100 via shared parser |
| Explicit query-length cap in handler | 512 Lisp characters | No matching 512-character handler check |
| Dataset selection | Server public list | Authorized caller scopes and optional requested dataset |
| Tenant selection | Public context grants =tenant:*= | Requested =tenant=, defaulting to =default= |
| Caller =dataset= or =tenant= parameter | Rejected with HTTP 400 | Compiled through authorization |
| =bookmark= | Forwarded | Forwarded |
| =sort= forwarding | Not forwarded by this handler | Forwarded if supplied |
| Backend request | =search/fts=, =include_docs=true= | =search/fts=, =include_docs=true= |

The course's =request_path()= now refuses an explicit =sort= parameter on
=public= requests: the pinned public handler ignores that parameter rather
than sending it to CouchDB. A URL-encoded =sort= string is not evidence of
backend sorting. The authenticated route forwards the supplied value, but
actual ranking and paging stability still require a service-level experiment.

The shared parser is named =bounded-query-integer= and its docstring mentions
clamping. Its implementation rejects values outside the range; it does not
silently clamp them. Tests are more useful than relying on the helper's name.
For example, public =limit=51= yields =query_parameter_out_of_range=, while
=limit=2x= yields =invalid_query_parameter=. Missing or empty =q= yields
=missing_query_parameter=. A 513-character public query yields
=search_query_too_long=. Caller public-scope parameters yield
=public_scope_is_server_owned=.

The authenticated cap is easy to miss: its handler does not supply an explicit
maximum, so it inherits =+http-max-query-limit+=100. Conversely, lack of the
public query-length check is not evidence that the authenticated route accepts
unlimited requests. Transport, proxy, parser and backend constraints remain
separate. The lab tests the inspected handler boundary, not an imaginary
unbounded deployment.

** The public query cap is measured in Lisp characters, not HTTP bytes

At the pinned public handler, the explicit 512 limit checks =(length q)=
/after/ parsing the query string. This measures Lisp string characters. It
is not an HTTP URL byte limit, a Lucene parser bound, or a backend resource
budget. For example, the following executable, synthetic Python demonstration
shows that encoding the same string for an HTTP query requires more bytes:

#+name: search15-public-query-length-units
#+begin_src python
from urllib.parse import urlencode

query = '\u03bb' * 512
assert len(query) == 512
assert len(query.encode('utf-8')) == 1024
encoded = urlencode({'q': query})
assert len(encoded.encode('ascii')) > 1024
#+end_src

The pinned Lisp handler admits 512 such characters at its own validation
boundary and rejects 513 with =search_query_too_long=; the hermetic Lisp suite
checks both cases on the extracted handler. A live HTTP deployment may impose
independent transport or proxy limits before the Lisp handler sees that string.
This example therefore does *not* predict the result of a complete HTTP
request, nor does it claim all 512-character Lucene expressions are valid.


** Public visibility is a deployment decision

The public handler builds scopes from =*public-search-datasets*=, initialized
from =STAR_PUBLIC_SEARCH_DATASETS=. At the inspected pin the fallback is
=("*")=. Its public context also carries =search:read= and =tenant:*=.
An operator combining public and private collections must configure the public
list explicitly. A route that rejects a caller's =dataset= parameter can still
expose an overly broad server-configured dataset set.

The historical and merged server route source uses =defparameter= to bind
=*public-search-datasets*= from =STAR_PUBLIC_SEARCH_DATASETS= when that Lisp
form is evaluated. Subsequent =public-search-scopes= calls read the bound
list; they do not re-read the environment for each HTTP request. Changing a supervisor environment variable after the process started does not update that bound value.
Use a reviewed restart, reload, or explicit in-process rebinding procedure and
verify the effective public dataset scope before treating a configuration
change as live. This is source-backed binding-lifetime reasoning; no native
server reload or deployed authorization transition was executed by the book.

For a disposable teaching deployment choose:

#+begin_example
STAR_PUBLIC_SEARCH_DATASETS=book-public,book-other-public
STAR_TENANT_DATASET_MAP=book-other-public=other
Public-mode: enabled for this experiment
Allowed public records: book-public and book-other-public across tenants
Private fixture dataset: book-private
#+end_example

Do not infer a tenant restriction from a dataset restriction. The inspected
public context grants all tenants, so a record in =book-other-public= adapted
to tenant =other= can be publicly visible. The teaching fixture maps that
dataset to =other= on the server; the authenticated reader only receives
=book-public= from tenant =default=. Choosing a public dataset name is an
operational publication decision, not a confidentiality label in the canonical
schema.

Public search rejects an attempted override before sending a backend request:

#+begin_src python
from lab import request_path
path = request_path('public', 'fname:bookneedle', dataset='book-private')
# The server should reject this parameter with HTTP 400.
#+end_src

Authentication does not let an administrator turn the public route into a
private search console. The route uses its own public context. Use the
=documents.search= surface for caller-authorized retrieval. Conversely, an
anonymous caller is not entitled to ingest documents or dispatch targets just
because the read plane is configured public.

** A canonical visibility label is not a public search permission check

The canonical StarLang =0.10.1= =Org= has optional =visibility= and
=accessControl= properties. Do not infer from those document labels that
the inspected public search automatically enforces a second, per-record
visibility rule. In both the historical and merged server source, the
public handler builds trusted =search:read=, =tenant:*=, and configured
=dataset:= scopes, then sends the resulting query to =search/fts=.
The index callback emits dataset and server tenant fields but does not
emit =visibility= or =accessControl=.

=test_visibility_index_boundary.js= executes the *unaltered historical*
index callback on a fictional record. Changing =visibility= from =public=
to =private=, or changing the access-control metadata, leaves the complete
ordered emission stream identical when all indexed properties stay the
same. Changing the dataset, internal server-stamped tenant, or indexed
content produces different emissions. The exact source Git blob is
attested, and an intentionally modified callback is a negative control.
These are raw JavaScript callback facts, not a Lucene search result.

This is a source-level warning about *policy composition*, not evidence
of a deployed record disclosure. Canonical schema acceptance, server
configuration, middleware, installed design, and active Clouseau behavior
still need their own tests. Do not mix private records into an
operator-configured public search dataset on the assumption that a
=visibility= flag alone will prevent retrieval. For finer-grained
policies, establish and test the actual server enforcement boundary
before claiming the dataset is safe for public search.

** Public aggregate statistics are not a public-search denominator

There is a second, easily confused boundary: the versioned public stats
handler reads =data/total= and =data/count_by_dtype= CouchDB reduced views
from the configured default database. Those original map functions count
ordinary documents without testing their =dataset=. The handler does not
apply =STAR_PUBLIC_SEARCH_DATASETS= to these aggregate view requests,
although the separate public /search/ handler constructs a server-owned
dataset-scoped query. The relevant map strings and public stats handler are
unchanged between the historical pin and merged 0.10.1 server.
This is source inspection, not a live authorization finding.

For example, a *synthetic* database with three public-dataset documents and
one private-dataset relation produces a total-map count of four, whereas the
modeled public-dataset membership is three. =count_by_dtype= also emits one
private relation. The actual pinned map functions, not reimplemented count
logic, are exercised by =test_public_stats_scope_difference.js=; its

Public mode and middleware determine whether an anonymous user can request

** Response caching is not search freshness

The historical and merged server source declare distinct cache directives for
read surfaces. =GET /api/v1/search= calls =set-cache-control "no-store"= after
constructing its server-authorized query; =GET /api/v1/stats= calls
=set-cache-control= with =public, max-age=15=. The latter aggregates the
unscoped =data/total= and =data/count_by_dtype= views. Its 15-second response
reuse policy is not a measurement of indexing lag, source age, record count
visible to a particular principal, or the freshness of canonical documents.

The authenticated =documents.search= handler makes no direct =set-cache-control=
call in the pinned source. This source-level absence does not prove final wire headers:
middleware and the HTTP runtime may add or replace directives. Likewise, a
=no-store= search response does not establish that a search index is complete
or that the returned records match the latest durable revisions. Compare
server policy, installed design, index generation, query context, authorized
by-ID readback and canonical validation as separate evidence gates.

The network-free =test_search_cache_contract.py= attests the exact historical
Lisp route Git blobs and checks these declared directives. The same source
behavior was inspected at merged server =ca6fdcbdc1f3b8aa344c533a40d298f741a54f25=.
No live HTTP response cache, browser/proxy behavior or Clouseau freshness was tested.

** An internal tenant stamp changes what the index sees

Do not execute the historical search design directly on a client fixture and
assume the resulting tenant field proves end-to-end scope behavior. The
=book-other-public= fixture contains a dataset but intentionally has no
=tenant_id= or =tenant=: that is the historical client-visible contract.
When executed directly on that raw fixture, the exact pinned JavaScript
indexer emits =tenant_id=default=.

The server's pinned =resolved-server-tenant= and =stamp-server-tenant!=
functions instead map that dataset to =other= under the disposable lab's
=STAR_TENANT_DATASET_MAP= setting and stamp the *internal* document before
the selected bulk publish paths. The same unchanged FTS indexer then emits
=tenant_id=other= from a modeled stamped copy. This is a source-grounded
index-projection comparison, not proof of successful deployed indexing,
authentication, persistence or runtime tenancy isolation.

** Authorization belongs before the backend query

The maintained =authorized-search-query= builds a parenthesized user query and
adds dataset and tenant clauses. Restricted scope values are escaped through
=lucene-escape=, quoted by =lucene-term=, and combined as disjunctions within
each dimension. The dimensions are conjoined with the user query.

For this non-administrator principal:

#+begin_example
search:read
dataset:book-public
tenant:default
#+end_example

and =q=fname:bookneedle=, the useful shape is:

#+begin_example
(fname:bookneedle) AND (dataset:"book-public") AND (tenant_id:"default")
#+end_example

This is an explanatory trace of the actual compiler's structure. It is not a
client-side permission check. A client sending a dataset name cannot grant
itself that dataset. The authenticated route requests =default= tenancy when
no =tenant= parameter is supplied; a principal granted only =tenant:other=
must request the appropriate tenant or face denial.

A restricted request for an unauthorized dataset or tenant produces an
authorization error rather than an apparently successful empty search. This
matters for both UX and debugging: distinguish "the search ran and found no
rows" from "this identity cannot run that scoped search." The service lab
expects HTTP 403 for those requests and first verifies that each fixture
credential can authenticate. Otherwise a broken credential could masquerade as
a policy test.

Wildcard and administrator cases deserve separate inspection. In this compiler,
wildcard dimensions omit that dimension's constraint; an optional requested
value does not turn a wildcard grant into the same constrained query produced
for a restricted principal. Do not use the table's ordinary restricted example
to predict administrator behavior. A narrowing UI should not assume that its
requested dataset constrains an administrator backend query at this pin.

Filtering rows after an unscoped backend search is a poor substitute for backend
scoping. Even if the UI drops unauthorized documents, counts, ordering and
bookmarks can describe a larger corpus. The inspected compiler explicitly aims
to scope the backend request. Its string construction alone does not establish
that every hostile Lucene expression is safely contained. Adversarial query
parser behavior is a further service-level security test, not a guarantee made
by this educational harness.

The final implementation also emits search-query audit information when
observability is enabled. The audit text bound of 16,384 UTF-8 bytes is a
retention bound on one audit event, not the public query-admission limit.
Keep audit retention, input validation and result pagination separate when
reading source. A log event can prove that a query reached the compiler without
proving backend success or complete results.

** A query audit is not an authorization decision or a search result

The historical Server's final authorization service emits a =search.query=
observability event *before* =search:read= authorization, but only when
observability logging is enabled. The event describes the submitted user query,
not the backend-expanded dataset/tenant clause, a successful HTTP response or
a snapshot of matched records. Missing logs cannot establish that no search
was attempted, and present logs can describe requests that were later denied.
The source is =source/authorization/services-final.lisp= at the Chapter 15
historical pin (Git blob =cb0344ca916ce54af8413289b12d234b5d61b781=).

The emitted attributes distinguish =query.text= (at most 16,384 UTF-8 bytes),
=query.bytes= (original UTF-8 length), =query.sha256= (digest of the *full*
submitted string) and the string-valued =query.truncated=. For an untruncated
event, the text, digest and byte count can be checked for *internal
consistency*. For a truncated event, the digest identifies an independently
supplied candidate query, but cannot reconstruct omitted text. The cut may fall
inside a multibyte character; do not turn a lossy displayed prefix into a
byte-for-byte query claim. A matching digest does not authenticate the logger
or prove that the caller was authorized.

The offline =verify_query_audit.py= example checks those distinctions without
loading credentials or contacting StarIntel. =test_query_audit_evidence.py=
executes both complete and truncated synthetic events and deliberate tampering.
These are *offline checker tests*, not native Lisp audit, successful index search,
backed-up logs, or a replayable audit trail. Retain the query, caller context,
response and authorized by-ID evidence separately when the investigation needs
reproducibility.

** Stored documents become selected index fields

The server calls =cl-couch:fts-search= against the default CouchDB database,
design document =search= and index =fts=. This is the maintained full-text
search path. It is different from a CouchDB view or Mango selector.

For this path CouchDB requires a connected Clouseau service. A database can
store JSON while its full-text service is unavailable. The official search
API uses bookmarks for subsequent pages, and =include_docs= asks for embedded
documents. These backend semantics must be verified with an actual service;
a callback that captures JavaScript index emissions cannot reproduce analyzers,
ranking or bookmark generation. [cite:@couchdb-search-api-book;
@couchdb-search-index-book]

The checked-in index declares a per-field analyzer configuration:

#+caption: Explicit analyzer choices in the historical search index.
| Indexed field | Explicit analyzer |
|---------------+-------------------|
| =content= | =standard= |
| =name= | =keyword= |
| =dataset= | =keyword= |
| =tenant_id= | =keyword= |
| Other indexed fields | Default =standard= |

The keyword analyzer retains a value as a single token; standard analysis
segments text. This distinction means a name field and a content field need
not behave like interchangeable substring searches. The lab captures emitted
values but does not run either analyzer. [cite:@couchdb-search-index-book]

The executable =test_search_analyzer_contract.py= pins those
per-field declarations and executes the original JavaScript index on a
synthetic document with the *same text* in =name= and =content=. Both
=store=true= callbacks carry that text unchanged even though the declared
analyzers differ. In particular, =dataset= and =tenant_id= are keyword fields
where the pinned scoped query compiler expects exact dimensions. This proves
the source configuration and raw callback values, *not* deployed Clouseau
tokenization, Lucene parsing, query containment or authorization.

Read the projection function as code, not as a list of imagined searchable
schema properties. It explicitly adds =tenant_id=, =dataset=, =dtype=, =title=
and =summary=. It processes selected source metadata, selected domain fields,
and =schema_org.sameAs=. It recursively handles arrays of scalars, keeps
strings/numbers/booleans, and ignores nulls or arbitrary object values. All
captured scalar index calls set =store=true=.

For selected domain fields, =doc.data[field]= wins whenever it is not
JavaScript =undefined=; otherwise the function uses =doc[field]=. That creates
an important historical compatibility lesson:

#+begin_example
Top level name: Example Cooperative
Nested data.name: Older Display Name
Indexed name: Older Display Name
#+end_example

If =data.name=null=, the nested key still wins the selection, but the scalar
adder ignores null. There is no indexed =name= in this case, even if the
top-level name contains text. The lab executes the exact checked-in function
and tests both cases. It does not "fix" them in a local imitation.

A raw JSON array, string or number is not a document. The historical
JavaScript may nevertheless emit =tenant_id=default= for such a value.
Accordingly, the teaching =projection()= helper rejects a non-object root
before executing Node. This checks only the *shape* of the capture input:
canonical validity still depends on the generated StarLang SDK, and the old
index function is not a validator.

The function supplies =tenant_id= from server metadata, falls back to the older
=tenant= field, and finally uses =default=. This internal index dimension is
part of the current server's authorization implementation. It is not permission
to add =tenant_id= to a canonical =0.10.1= document builder.

There is no explicit =index("default", ...)= call in the checked-in projection.
The teaching queries therefore specify fields, such as =fname:bookneedle=,
instead of assuming an unqualified term searches every emitted field.

** Canonical validation and index coverage are different contracts

The canonical synthetic organization has =id=, =schemaVersion=, =dtype=,
=dataset=, provenance fields and =name=. The real SDK accepts it, and the
maintained index function emits its =name=. That overlap does not prove this
historical server accepts the full canonical record through its write boundary.

The canonical synthetic person has =fname= and =lname=. These names overlap
with the index selection too. Add canonical =fullName="Alex Example"= and
validate it again: the SDK accepts the field. The inspected index selects
=full_name=, not =fullName=. Capturing its emissions proves that it omits the
canonical combined-name field while still emitting =fname=. This is a concrete
migration coverage gap, not a reason to rename the canonical key.

The later 0.10.1 server merge added the omitted camelCase index fields, but
not to this immutable historical lab pin. Source-level adoption is not proof
that the merged index is installed in a running database, that existing
records are reindexed, or that all producers emit the canonical version.
Do not rename canonical records into historical spellings to conceal a
projection gap, and do not treat old and new source pins as one release.

Build an index-coverage ledger:

#+caption: Canonical schema fields versus historical index coverage.
| Canonical field or structure | Observation at this historical index pin | Engineering consequence |
|------------------------------+-------------------------------------------+-------------------------|
| =name= on synthetic org | Emitted | Can study projection without asserting ingest adoption |
| =fname= on synthetic person | Emitted | Useful fielded fixture query |
| =fullName= | Not emitted under that spelling | Canonical validity does not imply query coverage |
| Arbitrary extension members | Not traversed generically | Search capability requires an intentional mapping |
| Document references and relations | No traversal implemented by these handlers | A matching relation document is not a graph walk |

This ledger connects Gate A, canonical data, to Gate D, investigation retrieval,
without blurring their authority. A valid stored record can remain invisible to
a query for an omitted field. An index hit can also be an old record whose
embedded document still needs a version-aware reader.

** Schema version is required canonically but omitted from this FTS projection

At the current StarLang =0.10.1= generated authority, =schemaVersion= is a
required field of =Org=, =Person=, =Relation= and =GeoPoint=. The pinned
*historical* search-index callback selects =dataset=, =dtype=, =name= and other
listed fields, but makes no =index()= emission for =schemaVersion=. Schema
acceptance and index coverage are separate checks.

Run =test_schema_version_index.js= through the Chapter 15 test runner. Six
native Node assertions execute the original Git-blob-attested FTS callback.
Two otherwise identical synthetic organizations with =schemaVersion= values
=0.9.0= and =0.10.1= produce identical *ordered index emissions*. Changing
the dataset or name changes those emissions. A deliberately altered, non-upstream
index function that emits =schemaVersion= makes the same version-only comparison
different, demonstrating that the control can detect the omitted field.

These examples are index-function inputs, *not* claims that either synthetic
record passed canonical SDK validation, that the historical server admitted a
=0.10.1= document, or that a version-filtered Lucene query was run. In a
mixed-version corpus, infer neither a record's schema authority nor index
completeness from a full-text hit. Retrieve the canonical record through an
authorized durable read, inspect its =schemaVersion= and validate under the
appropriate generated contract before making a version-specific claim.

** Text-bearing canonical types do not share one FTS content field

In the generated StarLang =org.starintel/core@1= =0.10.1= schema, a
=Message= has a required =message= string. =EmailMessage= offers =body=,
=Transcript= offers =text=, and =Policy= offers =text= alongside =name=.
=SocialMediaPost= offers =content=. These are *different canonical field
names*, not interchangeable aliases. A record's ability to carry text does
not mean the historical search design can query every text-bearing member.

Both the pinned historical =source/views/search.json= and the inspected merged
0.10.1 design select =content= and =name=, but do *not* select =message=,
=body= or =text=. The native =test_canonical_text_coverage.js= runs the
unmodified Git-blob-attested index callbacks on synthetic shapes: changing
only =Message.message=, =EmailMessage.body=, =Transcript.text= or =Policy.text=
leaves ordered raw =index()= calls unchanged. By contrast, changing
=SocialMediaPost.content= or =Policy.name= changes emitted field values.

#+caption: Typed canonical text versus the two inspected raw FTS projections.
| Generated 0.10.1 definition | Text-bearing property | Raw callback emission |
|-----------------------------+-----------------------+-----------------------|
| =Message=                   | =message=             | Omitted               |
| =EmailMessage=              | =body=                | Omitted               |
| =Transcript=                | =text=                | Omitted               |
| =Policy=                    | =text=                | Omitted               |
| =SocialMediaPost=           | =content=             | Emitted               |
| =Policy=                    | =name=                | Emitted               |

This is *field selection*, not an evaluation of the document's validity or
of its contents' evidentiary reliability. The samples are canonical-shaped
but were not passed through the generated SDK. The callbacks did not run
inside CouchDB/Clouseau, and no result ranking, authorization, installed
index or actual service visibility was tested. In particular, a returned
=Message= row says nothing by itself about whether its =message= text was
indexed. For a development search feature, start with an explicit,
versioned, dtype-aware text projection; test canonical validation, server
admission, installed indexing and authorized retrieval as separate gates.


** A canonical Relation is not an FTS graph edge

Canonical StarLang =0.10.1= has a distinct =Relation= document model with
required =source=, =destination= and =predicate= fields as well as
=id=, =dataset=, =dtype= and =schemaVersion=; optional fields include
=direction=, =rev= and =provenance=. This structure defines a candidate
record shape, not a claim that the book has stored or inferred a graph edge.
The canonical source is generated schema blob
=537163da436f67a973e280d1704e32bdba5b888b= at StarLang commit
=96d26c338078676ec1dc6928755901636c9f7ef0=.

The =test_relation_fts_boundary.js= lab executes both byte-attested original
historical and merged Server JavaScript callbacks with a fictional, typed,
directed =owns-device= example. The unchanged callbacks emit =tenant_id=,
=dataset= and =dtype=; changing the relation's =predicate=, =source=,
=destination= or =direction= does not change the captured emissions. Changing
=dataset= does. A deliberately altered (non-upstream) callback that indexes
=predicate= acts as a test-sensitivity control. The normal one-checkout run
verifies the historical function; an optional second input exercises the
merged index definition without presenting it as the historical deployment.

This is *raw index-field coverage*, not a graph query, live search result,
canonical SDK validation or authority to traverse endpoints. A search hit
cannot itself establish a stored, directional or inferred relationship.
A future graph workflow must separately verify authorized scope, canonical
identity and revision, provenance, and whether its edge is a candidate,
a durable document, or a rule-derived inference. No Project 4 graph or Prolog
implementation is assumed here.

** A canonical GeoPoint is not automatically a spatial search result

A StarLang 0.10.1 =GeoPoint= defines =geometryType=, =longitude= and
=latitude=, with decimal-string coordinate values. =geohash= and
=placeName= are also defined source properties. But the *historical*
=source/views/search.json= full-text projection has no =index()= emission for
those properties. It still emits =dataset=, =dtype= and an internal tenant
index term for a synthetic =dtype=geo= document.

Run =test_geo_index_coverage.js= under the pinned Chapter 15 lab. Seven native
Node tests execute the *actual Git-blob-attested historical index function*:
two synthetic points with different coordinates and place descriptions yield
the same ordered FTS emissions; changing the dataset changes those emissions.
Adding =content= yields text emissions but not geometric coordinates.
An input missing the required coordinates produces the same FTS emissions:
index projection is not canonical admission. The test uses a shape informed by
the generated =0.10.1= GeoPoint definition; it does *not* execute SDK
validation of that particular sample.

This comparison does not prove equal durable documents, proximity, containment,
co-location or identity. Nor does it establish that deployed StarIntel has no
other spatial services. It establishes only the historical FTS projection's
field-selection boundary. A future geospatial retrieval path needs its own
index definition, authorized query, exact source/runtime pin, and real
integration tests. Never infer a directional graph link or spatial predicate
from a plain text-search match.

** Interpret a page as retrieval evidence

A typical explanatory page looks like this; it is a synthetic response fixture,
not captured service output:

#+begin_src json
{
  "total_rows": 99,
  "bookmark": "opaque+/=",
  "rows": [{
    "id": "org:book-example",
    "order": [1.4, "org:book-example"],
    "fields": {"name": "Example Cooperative"},
    "doc": {
      "_id": "org:book-example",
      "_rev": "1-demo",
      "dtype": "org",
      "dataset": "book-synthetic"
    }
  }]
}
#+end_src

The row identity locates the record. =fields= is the stored index projection;
=doc= is the embedded document requested by the handler. Neither the sort
order nor a relevance value is the truth confidence of a claim. Do not turn a
high-ranked record into a verified observation or collapse conflicting records
simply because their names are similar.

The illustrative =total_rows=99= does not mean this one-row page contains 99
records. Keep page size, result count, retrieved unique identities, and corpus
size as different measurements. An index order tuple is backend retrieval
metadata, not a canonical document revision. Retain the embedded document's
identity, revision if present, dataset, dtype and provenance when handing a hit
to downstream analysis. A later by-ID read may observe a different revision.

The *confidence in a record's underlying evidence* is not a search ranking.
The canonical StarLang 0.10.1 =Person= shape exposes =confidence= as
=ConfidenceScore= (a decimal-text string) and =verificationStatus= as a
string, but neither the pinned historical nor the subsequently merged server
FTS callback emits these keys. The native
=test_confidence_not_retrieval_score.js= test executes both Git-blob-attested
index functions: changing only these two synthetic metadata values leaves the
*ordered raw index() emissions* identical. Changing indexed =content= does not,
and a deliberately modified (non-upstream) callback that emits =confidence=
provides a negative control. These synthetic projection inputs are *not*
claims of canonical SDK validity, installed Clouseau scoring, equal rankings,
or verified claim quality. Inspect record provenance and validation separately;
never promote retrieval position to a confidence score.

An embedded search hit can contain two different kinds of revision evidence:
CouchDB's storage =_rev= and canonical StarLang's document =rev= where that
schema applies. They are not alternative spellings of the same contract.
The lab preserves both as =Hit.storage_revision= and
=Hit.canonical_revision=; its older =Hit.revision= convenience field
chooses storage first for compatibility, but cannot identify the namespace.
A malformed value in either revision field fails interpretation even when
the other field is well formed. An unvalidated embedded value is still only
observed search JSON, not independently verified canonical or durable evidence.

The current server removes its injected =tenant_id= from stored fields,
embedded documents and embedded outbox payloads on egress. The hermetic Lisp
check executes those actual scrubbing functions. Scrubbing metadata is separate
from excluding unauthorized documents: removing a tenant label cannot repair a
leaked record. The live test checks which synthetic identities are returned,
as well as whether tenancy metadata leaked.

The book's =interpret_page= helper refuses an error envelope, an invalid row
shape, duplicate identities within a page, a row/document identity disagreement,
and direct server-tenant leaks. In particular, an explicit top-level =error=
key wins over a plausible =rows= array. A mixed JSON object such as
={"rows": [], "error": "backend_failed"}= must not be mistaken for a successful
empty search page. This is a fail-closed client invariant against malformed or
contradictory envelopes, not a claim that the maintained server emits such an
object. Network-free regressions exercise both empty and populated mixed
responses alongside ordinary successful pages. They do not replace actual
HTTP status mapping or deployed search-service tests. A fields-only row remains
a fields-only hit; the helper does not manufacture a complete document from
index fields.

There is also a *returned-page bound*, separate from total hits or cursor
budgets. For the inspected server, public search accepts at most 50 requested
rows per page; authenticated document search inherits a 100-row maximum. The
teaching =interpret_page= rejects a returned =rows= array longer than 100
*before* constructing any =Hit= copies. A synthetic 101-row envelope is
out of contract even if its records are otherwise well formed; the client
fails rather than silently truncating it. Six network-free cases in
=test_page_row_budget.py= check the boundary. This client guard does not prove
that the backend enforces its declared query limit, or that any number of
returned hits implies a complete index or durable canonical evidence.

For production, validate the embedded payload with the appropriate version
reader, retain original response evidence where appropriate, and record the
query/surface/time/version context of a retrieval. Canonical provenance lives
with the record; query execution context describes how you obtained that
record. They complement each other.

** Retaining an observation without rewriting its evidence

A decoded search response is mutable Python data. Even if a result wrapper uses
=@dataclass(frozen=True)=, nested dictionaries are not thereby frozen. The
teaching client deep-copies the embedded =doc= and stored index =fields= *after*
checking their types and scope metadata. Later edits to the response cannot
silently rewrite those retained observations:

#+name: search15-evidence-detachment-example
#+begin_src python
from lab import interpret_page

page = {'rows': [{
    'id': 'person:synthetic',
    'doc': {'_id': 'person:synthetic',
            'provenance': {'sources': ['initial']}},
    'fields': {'name': 'original'}
}]}
hit = interpret_page(page)[0][0]
page['rows'][0]['doc']['provenance']['sources'].append('later')
page['rows'][0]['fields']['name'] = 'later'
assert hit.document['provenance']['sources'] == ['initial']
assert hit.fields['name'] == 'original'
#+end_src

This example is TESTED by =test_manuscript_detachment_example.py= against the
same =interpret_page= used by the hermetic Chapter 15 lab. The copy separates
later changes to a decoded response from retained result evidence; it does not
make =hit.document= recursively immutable, validate the canonical schema,
prove that a CouchDB write persisted, or ensure an index snapshot. Record the
query, route, pin and retrieval time separately when interpreting that hit.

** Pagination needs a bounded client

Treat the bookmark as an opaque continuation value. Preserve the same query
and sort while continuing it. The CouchDB search API documents bookmarks and
sorting parameters; its bookmark is not a document ID or an integer offset.
[cite:@couchdb-search-api-book]

The lab sends =limit=1= to make continuation behavior impossible to overlook.
Its client URL-encodes =q= and =bookmark=, stops on an empty page, rejects a
missing or repeated bookmark on a nonempty page, tracks repeated identities
across pages, and caps the number of requests.

Neither historical public nor authenticated HTTP handler forwards =skip= or
=offset= to the full-text backend. A syntactically valid URL with one of those
parameters cannot establish offset pagination. The book client rejects both
parameters on both surfaces, even when set to zero, and demonstrates that
rejection in =test_offset_pagination_contract.py=. Preserve and resend the
opaque server-issued =bookmark= instead. The test inspects client behavior;
it does not establish snapshot consistency under concurrent writes.

The page budget is a client resource policy, not the server's result-limit
contract.

#+begin_src python
from lab import interpret_page, next_bookmark, request_path
hits, bookmark = interpret_page(page)
continuation = next_bookmark(previous_bookmark, bookmark, hits)
if continuation is not None:
    path = request_path('authenticated', original_query,
                        limit=1, bookmark=continuation)
#+end_src

The variables here belong to the caller's loop; see =service_checks.py= for the
complete executable client. A useful terminal condition is an empty page, not
"the bookmark exists." A short page may deserve another request. A repeated
bookmark with records deserves explicit diagnosis, not an endless loop.

The lab intentionally requires a quiescent synthetic corpus for its exact-set
pagination assertion. It does not prove snapshot isolation across concurrent
writes. If an investigation needs an export with reproducible membership,
design a documented export/snapshot policy instead of treating a paged search
as a durable frozen dataset.

** The visibility ladder is a debugging method

#+begin_export html
<figure>
<img src="assets/search-visibility.svg" alt="An accepted record must reach durable storage, selected index fields and analyzer state before an authorized query can return it; omitted fields or scope exclusions can produce no hit." />
<figcaption>HTTP acceptance, durable read-back, index projection and authorized hits are separate observations.</figcaption>
</figure>
#+end_export

Work through this ladder with a single synthetic identity:

1. Record the request route, payload version and acceptance response. Do not
   label asynchronous acceptance as a completed durable write.
2. Poll an authorized by-ID read with a deadline. Preserve identity and revision
   when it becomes visible. Failure to read it does not yet locate an index bug.
3. Execute or inspect the exact index projection on that payload. Is the query
   field emitted? Does an old nested field shadow the intended top-level value?
4. Check the installed design document and functioning search service. The
   checked-in JSON file is a proposed installation source, not evidence that
   the live database currently has that exact revision installed.
5. Check the fielded query and authorization dimensions. Is the caller in the
   correct dataset and tenant? Is the public list intentionally configured?
6. Interpret the response as a page. Preserve failures, distinguish zero rows
   from denial, and keep continuation bounded.

For this chapter a durable read without a search hit is an informative intermediate
state. It may indicate a projection mismatch, index/backend state, query mismatch
or visibility exclusion. It is not enough evidence to claim eventual index lag
was the cause. Name the next measurement that would distinguish those cases.

** Classify the first missing search observation without inventing a cause

The ladder is actionable only when each observation is tagged as /true/,
/false/ or /unknown/. A failed search does not make an unperformed by-ID read
false; a locally emitted index field does not establish that CouchDB installed
that FTS definition. The book's new offline
=code/search-lab/diagnose_search_evidence.py= accepts the historical or merged
Server generation and a public/authenticated route label, then chooses one
next experiment. It does *not* execute queries, inspect credentials, or decide
which dataset/tenant the server permits. The historical public handler
constructs scopes from its server-owned dataset configuration; the
=documents.search= handler uses the authenticated caller's authorization
context. The two routes cannot be treated as interchangeable evidence.
[cite:@starintel-search-runtime-20261009]

For example, a synthetic document can be read back by ID while its canonical
text field is omitted by the inspected historical FTS callback. Give the
decision aid explicit =durable_by_id=true=, =field_emitted=false= and
=target_search_hit=false=. It recommends selecting an actually indexed search
field; it does *not* assert that the record is missing or the user was denied.
By contrast, when a search hit is observed but a by-ID read has not been, the
next check is an authorized by-ID read. A hit is still only retrieval evidence.

#+begin_src sh
printf '%s\n' '{"generation":"historical","surface":"public","checks":{"durable_by_id":true,"field_emitted":false,"target_search_hit":false}}' | \
  python3 books/starintel/code/search-lab/diagnose_search_evidence.py -
#+end_src

The local =test_diagnose_search_evidence.py= suite proves that unknown is not
silently converted into false, that neither source projection nor a matching
exported FTS design proves active index coverage, and that even a positive
control does not validate an individual target. The output is a proposed
next measurement, not a production diagnosis. Actual HTTP authorization,
index service behavior, search parser semantics and concurrent mutation
remain UNTESTED unless separately observed on a running pinned stack.

** Common mistakes and their repairs

#+caption: Search-evidence mistakes and recommended diagnostic steps.
| Mistake | Why it fails | Better next step |
|---------+--------------+-----------------|
| Search immediately after HTTP acceptance and blame storage | Acceptance, read-back and search visibility differ | Observe each boundary with deadlines |
| Add canonical =tenant_id= because the index uses it | Internal runtime metadata is not schema authority | Let the maintained server stamp its own tenant metadata |
| Rename =fullName= into historical =full_name= silently | Hides a consumer migration gap | Keep canonical records and test index adoption explicitly |
| Use public search for a private analyst's dataset | The route uses public server scopes | Use authenticated =documents.search= |
| Assume public scope-override rejection means safe public configuration | Default dataset list is wildcard | Inspect and configure server-owned public datasets |
| Treat =fields= as the complete document | It is a selected stored projection | Read/validate =doc= or perform an authorized by-ID read |
| Interpret ranking as evidence confidence | Retrieval order is not claim verification | Inspect record provenance and conflicting evidence |
| Put a bookmark directly into a URL | Reserved characters can change the request | Use a query-string encoder |
| Restart every service on a missing hit | Destroys useful intermediate evidence | Locate the first unproven boundary |
| Call projection capture a full-text integration test | No analyzer or service was executed | Keep hermetic and service-backed evidence separate |

** Exercises and worked answers

*** Exercise 1 -- Explain an empty page (★)

A write returned success. By-ID read-back has not run. Search returns no rows.
Name what is established and the next useful observation.

Answer: the write boundary accepted the request and the search returned an empty
page for that query/context. Durable storage has not been observed. Attempt an
authorized by-ID read with a deadline before diagnosing the index.

*** Exercise 2 -- Predict public visibility (★)

In a separate hypothetical deployment, the public list is =book-public= and
its context grants =tenant:*=. A record in
=book-public= belongs to =other=. A second record in =book-private= belongs to
=default=. Which one should the teaching public search retrieve?

Answer: the first can be visible, provided its indexed terms match. The second
should be excluded by dataset scope. The public route's tenant wildcard is not
a default-tenant restriction.

*** Exercise 3 -- Extend canonical index coverage (★★)

Add canonical =fullName= to the synthetic person and validate it. Confirm that
the *pinned historical* index omits it. Run the independent
=compare_index_generations.js= against the historical and merged 2026-10-10
server index files. What can each result establish?

Answer: the old projection omits =fullName= while the merge emits it
alongside =full_name=. Both observations are from the exact original index
functions and synthetic inputs. Neither proves the installed database has
that design/reindex, that deployed HTTP authorization permits the query,
or that every producer emits valid 0.10.1 records. Test those separately.

*** Exercise 4 -- Make a safe paging client (★★)

Extend the client to persist a retrieval ledger containing surface, query,
retrieval time, source pin, unique identities and observed revisions. Keep
credentials out of that ledger. Explain its consistency limitation.

Answer: the ledger makes the observed traversal inspectable, but does not create
a server snapshot. Concurrent mutation can change later pages or by-ID reads.
A claim of reproducible corpus membership needs an explicit export policy.

*** Exercise 5 -- Diagnose an allowed record that stays invisible (★★★)

All five by-ID reads succeed, the reader credential authenticates, and public
search never sees any of the allowed records. List three distinguishing checks.

Answer: compare installed =search/fts= design content against the source pin;
verify Clouseau is functioning and inspect its errors; inspect actual field
emissions and the compiled fielded query. Check public dataset configuration
before assuming the search index is broken. Do not accept an empty result as
a successful authorization proof when the positive controls failed.

*** Exercise 6 -- Test query containment (★★★)

Design service-level adversarial cases for nested Boolean expressions,
unbalanced parentheses and caller-written dataset/tenant terms. State what the
hermetic compiler tests cannot prove.

Answer: a string containing appended scope clauses does not prove how the real
Lucene parser evaluates hostile syntax. Record whether parsing fails or whether
only authorized fixture identities appear, with allowed positive controls.
Run the real parser and middleware at an immutable pin. Treat any unauthorized
identity as a failure, regardless of displayed counts or scrubbed metadata.

*** Exercise 7 -- Bound the next chapter (★★★)

A relation record appears in full-text search. Can the client claim it traversed
a person-to-organization graph?

Answer: no. Retrieving a relation document is different from resolving typed
endpoints, joining records and traversing edges under a visibility policy.
Those require their own maintained contracts and tests. Chapter 16 remains a
separate research/implementation boundary; this chapter invents none of them.

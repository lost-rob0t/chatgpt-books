** Chapter 1 -- A System for Growing Evidence
:PROPERTIES:
:ID:       d8bd0f07-439e-4f7c-b0dd-7ba1efee64c3
:END:
StarIntel makes more sense if you begin with *flow* rather than a list of repositories. A useful unit enters the system as a typed document. A service validates it, a durable boundary stores it, messages announce what happened, and actors can derive more documents and relations. The graph grows because new evidence can trigger more work.

That is the first mental model for this book:

#+begin_example
input -> validated document -> durable corpus -> event -> actor -> derived document
                                                        ^                    |
                                                        |____________________|
#+end_example

The last arrow is why the system feels recursive even though the implementation is not simply one function calling itself. A derived document can re-enter the ingest path, become durable, and cause another round of work. The current server calls this dataflow recursion. [cite:@starintel-server-20260916]

*** What StarIntel is not
It is tempting to compress the whole project into one slogan: a database, a scraper platform, an actor system, an OSINT UI, a graph explorer, or an inference engine. Each description catches a real piece and misses the architecture.

For the current implementation, =starintel-server= is a Common Lisp backend service layer. It owns persistent document ingest, CouchDB storage/querying, RabbitMQ routing, HTTP service boundaries, local actor integration, and recursive dataflow. Quasar is a separate control-plane concern; browser UI is separate again; external actor services can live outside the server process. [cite:@starintel-server-20260916]

This separation matters to hackers because ownership predicts where a bug belongs. A malformed document rejected before publication is not a CouchDB bug. A document accepted by the HTTP boundary but never persisted might be a producer, queue, consumer, validation, or database problem. An actor that exists as a source file but is not in the server's ASDF load graph is not an active runtime capability.

*** The current architecture at a glance

#+attr_html: :alt A StarIntel document moves from a client through HTTP validation and authorization, RabbitMQ ingest, an ingest consumer, CouchDB persistence, a documents.new event, and actors that may derive documents which re-enter ingest.
[[file:assets/document-flow.svg]]

The diagram is a teaching model verified against the current server source at revision =d4e8447c6049eaed65a93e81668ae1ec4b65c25c=. It is not a claim that every historical or future StarIntel path has exactly these nodes. One of the habits this book will build is attaching an architectural statement to the revision that made it true.

*** Four questions to ask at every boundary
When debugging StarIntel, ask these before touching code:

1. *What object crossed the boundary?* A JSON document, a Rabbit delivery, an actor message, a CouchDB response, or something else?
2. *Which contract admitted it?* Schema validation, authorization, routing, actor protocol, or database revision rules?
3. *What observation do we actually have?* A local function returned, a broker accepted a message, a consumer acknowledged it, or durable state changed?
4. *Who owns the next state transition?* The HTTP service, broker, consumer, database, actor, or caller?

These questions prevent a classic distributed-systems mistake: treating an earlier success as proof that every later stage succeeded.

*** First trace: accepted is not persisted
Suppose a client submits a valid document. The current canonical HTTP path parses the request, validates the document, passes the authorization boundary, and publishes to the ingest route. The server documentation explicitly distinguishes that publication from downstream persistence. [cite:@starintel-server-20260916]

So this reasoning is invalid:

#+begin_example
HTTP returned success
therefore the document is in CouchDB
#+end_example

The corrected reasoning is:

#+begin_example
HTTP returned success
therefore this HTTP path reached its successful publication boundary

To prove persistence:
observe the downstream ingest/database result separately
#+end_example

RabbitMQ's own documentation reinforces why these observations are separate. Publisher confirms and consumer acknowledgements solve different legs of delivery and are orthogonal mechanisms. [cite:@rabbitmq-confirms-43] This chapter does *not* assert that StarIntel currently enables every RabbitMQ safety option; later messaging chapters inspect that exact configuration before making stronger claims.

** Chapter 2 -- Reading a Living Multi-Repository System
:PROPERTIES:
:ID:       d5118939-b23f-4a66-97e7-82cd4bdb97c6
:END:
A hacker's guide to a living system cannot treat documentation as scripture. Documentation is evidence. Tests are evidence. Package manifests and load graphs are evidence. Running behavior is evidence. They can disagree.

The first source-reading skill is therefore *evidence ranking*.

*** Executable ownership beats filenames
At the inspected server revision, =source/starintel-gserver.asd= is the active Common Lisp system definition. It loads document access, databases, authentication, authorization, actors, RabbitMQ code, HTTP boundary code, lifecycle code, and the main entry point in a specific serial order. [cite:@starintel-server-20260916]

That means a Lisp file merely existing under =source/= does not prove it runs. The current architecture documentation even lists actor files that are present but not loaded. This is a small lesson with a huge payoff: when you add or debug a capability, check the load graph before tracing runtime messages that can never occur.

A useful classification is:

| State | Meaning for this book |
|-------+-----------------------|
| Active | Loaded/started by the current runtime path or independently proven active by current tests/source. |
| Present, inactive | Code exists but the normal runtime does not load/start it. |
| Experimental | Loaded or present, but explicitly incomplete or not a stable capability. |
| Historical | Describes behavior that current source has superseded. |
| Proposed | Design/issue material not yet evidenced by current implementation. |

*** A real documentation conflict
The inspected server repository contains older prose saying the HTTP service lacks built-in authentication and authorization. If you stopped reading there, you would teach the wrong current architecture.

Current executable evidence says otherwise. The ASDF system loads =auth/*= and =authorization/*=. It then loads baseline HTTP boundary routes and, later, =frontends/http-authorization-routes=. That later file installs authorized handlers for routes including =POST /new/document/:dtype=. The publish helper itself calls an authorization service before the unchecked Rabbit side effect. The repository also contains an HTTP authorization runtime document marked ACTIVE whose route/action matrix matches these current sources. [cite:@starintel-server-20260916]

The correct conclusion is not "documentation is useless." The correct conclusion is:

- some repository prose has drifted;
- the current auth/authorization path is evidenced by loaded source and route replacement;
- stale paragraphs should be treated as historical until reconciled;
- the book must preserve the disagreement as a debugging lesson rather than silently blending incompatible claims.

This pattern will recur. StarIntel is evolving quickly enough that "I read a README once" is not a verification strategy.

*** Repository roles for the foundation slice
Three repositories matter immediately:

**** =starintel-server=
The Common Lisp backend service. For this slice, it defines the live ingest/dataflow/authorization/persistence boundary we are learning to trace. [cite:@starintel-server-20260916]

**** =star-cl=
The Common Lisp document library pinned by the current server. The inspected server runtime lock converges on revision =9ce8f88f57fb7ac143851f7fd2c75dccd6a40cc3=. [cite:@star-cl-091]

**** =starintel-doc=
The Python document package. Its current package version is =0.9.1= and it exposes validation, normalization/round-trip behavior, schema inventory, and a conformance adapter. Project 1 uses this real package rather than reimplementing its rules. [cite:@starintel-doc-091]

Later chapters add Quasar, actor repositories, Prolog components, and other language bindings only after inspecting their current heads. This keeps the beginner's mental model small without pretending the broader system does not exist.

*** A repeatable source-audit loop
When a chapter makes a version-sensitive claim, use this loop:

1. Record the repository and exact head.
2. Read package/build manifests to identify what is loaded.
3. Read the narrow source path that implements the claim.
4. Read tests or executed CI evidence that crosses the same boundary.
5. Read current docs for intended semantics.
6. Record contradictions explicitly.
7. Only then turn the claim into tutorial prose.

For a system this dynamic, the revision is part of the citation.

- ★★★ Write a five-line "historical/current" note for a hypothetical route whose old implementation is still in-tree but replaced by a later-loaded handler.

** Chapter 3 -- The Canonical Document Model
:PROPERTIES:
:ID:       f3a00aa5-cab8-4e49-a880-2cbd838c7750
:END:
The first edition of this chapter taught the document contract from the server's
then-current 0.9 runtime.  That was useful runtime evidence, but it is no longer
the right place to begin.

For new StarIntel work, begin at the *schema authority*.

As of this edition's 2026-10-05 source audit, the canonical document library is
=org.starintel/core@1= version =0.10.1= in
=lost-rob0t/star-lang/specs/starintel/0.10.1/core.star=.  The generated release
lock declares both =releaseVersion= and =schemaVersion= as =0.10.1= and declares
=lowerCamelCase= as the canonical JSON key style. [cite:@starlang-starintel-0101]

This changes the beginner's first question from:

#+begin_example
Which JSON file should I copy?
#+end_example

to:

#+begin_example
Which StarLang contract defines this document,
and which generated artifact does my language consume?
#+end_example

That is a much stronger mental model because it survives language bindings,
runtime migrations, and repository reshuffling.

*** Read =core.star= before generated code

The canonical source begins with a versioned specification library:

#+begin_src lisp
(spec-library "org.starintel/core@1"
  (:version "0.10.1")
  ...)
#+end_src

The file then defines scalars, enums, records, and documents.  Generated JSON
Schema and language bindings are products of that source.  They are important
products, but they are not separate authorities.

The distinction matters when generated artifacts disagree with hand-written
code.  The right debugging question is not "which copy looks newer?" but:

1. which =core.star= revision is authoritative;
2. which release lock names the generated artifacts;
3. which artifact revision did this consumer actually pin;
4. did the runtime load that consumer.

A generated binding can be perfectly valid and still be the wrong release for
the process that loaded it.

*** The base =document= is intentionally rich

The canonical base document declares five fields that establish the common
identity/typing envelope:

#+begin_src lisp
(document document
  (:persistence persistent)
  (id document-id :required)
  (rev string :optional)
  (dataset string :required)
  (dtype string :required)
  (schemaVersion string :required)
  ...)
#+end_src

[cite:@starlang-starintel-0101]

The base contract then adds optional groups for provenance, temporal scope,
collection metadata, causal/correlation identity, confidence/quality,
classification and access metadata, hashes/content metadata, raw material,
notes, deletion/tombstone state, and extensions.

That breadth is deliberate.  StarIntel wants a =person=, =relation=,
=wireless-network=, =file=, or =operation= to carry common evidence and lifecycle
metadata without every dtype reinventing its own spelling.

A useful way to learn the envelope is by responsibility:

| Group | Representative fields | Question answered |
|-------+-----------------------+-------------------|
| Identity | =id=, =rev=, =dtype=, =dataset=, =schemaVersion= | What object/contract is this? |
| Source | =sources=, =sourceUrls=, =sourceRecordIds=, =sourceKinds= | Where did it originate? |
| Time | =observedAt=, =collectedAt=, =firstSeenAt=, =validFrom=, =expiresAt= | When was it observed/valid? |
| Execution lineage | =runId=, =correlationId=, =causationId=, =parentId=, =rootId= | Which workflow caused it? |
| Assessment | =confidence=, =qualityScore=, =verificationStatus= | How is its quality assessed? |
| Provenance | =provenance=, =chainOfCustody=, =transformHistory= | How did it become this representation? |
| Policy | =sensitivity=, =visibility=, =owner=, =accessControl= | How should it be handled? |
| Content identity | =contentHash=, =hashAlgorithm=, =normalizedHash= | Which bytes/normalized content are represented? |
| Escape hatch | =extensions= | What explicitly non-core metadata must survive? |

Do not read that table as "fill every field."  Most are optional because
different sources know different things.  The contract gives components a
shared vocabulary when those facts are known.

*** Identity is not a CouchDB implementation detail

The canonical =document-id= scalar is a string constrained to a bounded,
portable character set.  The important point is conceptual: =id= is the
StarIntel document identity.

=rev= is a revision token carried by the canonical model when revision
information needs to cross the boundary.  A storage engine may have its own
native revision representation, but clients should not infer that the
canonical identity is "whatever CouchDB happened to call =_id=."

For current new work:

#+begin_example
id            logical StarIntel document identity
rev           revision/concurrency metadata when exposed canonically
dataset       corpus / grouping boundary
dtype         concrete document contract discriminator
schemaVersion canonical StarIntel document release
#+end_example

The old 0.9 runtime used =_id= and =schema_version=.  Those spellings are
historical inputs, not the canonical 0.10.1 output vocabulary.

*** A small canonical person

The =person= document extends the common document and adds optional fields such
as =fname=, =mname=, =lname=, =fullName=, =displayName=, =bio=, dates,
nationality/citizenship, occupations, addresses, accounts, images and typed
identifier references. [cite:@starlang-starintel-0101]

A deliberately small example is:

#+begin_src json
{
  "id": "person:book-demo",
  "dataset": "book-demo",
  "dtype": "person",
  "schemaVersion": "0.10.1",
  "fname": "Alex",
  "lname": "Example",
  "collectionStatus": "normalized",
  "sourceKinds": ["human"],
  "notes": "Synthetic teaching record only."
}
#+end_src

This example teaches the *shape*.  A production collector should not invent
source/verification metadata it does not actually know.

The difference between an optional field and a guess is fundamental.  "The
schema allows =gender=" does not mean a collector may populate gender by
assumption.  Schema expressiveness is not evidentiary authority.

*** Relations make the graph explicit

StarIntel is graph-shaped because relationships are first-class documents, not
only because a UI draws lines.

The canonical =relation= extends =document= and requires:

#+begin_src lisp
(document relation
  (:extends document
   :persistence persistent)
  (source reference :required)
  (destination reference :required)
  (predicate string :required)
  ...)
#+end_src

It can additionally carry direction, an inverse predicate, note, evidence
references, weight, and temporal validity. [cite:@starlang-starintel-0101]

That means a relation can itself have identity, dataset membership, provenance,
collection metadata, confidence, lifecycle state, and revision history.

This is stronger than putting =friend_ids= inside a person record.  A
first-class relation lets you ask:

- who asserted the connection;
- what evidence supports it;
- when it was valid;
- whether a later source disputes it;
- whether two independently collected relations describe the same claim;
- whether a derived relation should be recomputed when inputs change.

The graph is evidence-bearing data, not merely adjacency.

*** References prevent accidental embedding

Many canonical fields use =reference= rather than embedding an entire target
document.  Generated bindings expose the reference as a schema-qualified
identity pair.

The architectural idea is more important than its exact generated syntax:
documents link to identities; they do not have to duplicate every object they
mention.

That keeps one document update from requiring a rewrite of every document that
references it, and it gives relation/provenance logic stable identities to
reason over.

*** Canonical operations and investigation targets are documents too

The 0.10.1 authority adds persistent research/orchestration contracts that are
easy to confuse with runtime messages.

=operation= requires a =mission= string, an =operation-status=, and a non-empty
or schema-valid phase structure.  It can also carry objectives, scope,
target-policy/bindings, datasets, capability gaps, assignments and post-actions.

=investigation-target= requires a target string and can carry a research
question, hypotheses, objectives, scope, source preferences/exclusions,
required dtypes, recurrence controls, depth/breadth controls, priority, score,
selection reasons and other research parameters. [cite:@starlang-research-contracts-0101]

These are *persistent StarIntel documents*.  They are not aliases for:

- a Sento actor mailbox message;
- a Rabbit routing key;
- the older actor scheduler's internal target object;
- a spatial mission;
- a UI tab called "target."

The same English word can exist in multiple layers.  The dtype tells you which
contract you actually have.

*** Canonical does not mean every runtime has adopted it

At the time of this edition, =starintel-server= default branch still carries its
older runtime lock: release/profile 0.9.1 over the 0.9.0 wire schema.
[cite:@starintel-server-20261005]

A tested draft migration exists in server PR #313.  That work changes the
server to accept flat lowerCamelCase 0.10.1 documents through generated StarLang
artifacts and =star-cl= at HTTP, bulk, Rabbit mutation, update and generated API
schema boundaries.  It is not merged into the default branch at this book
revision. [cite:@starintel-server-pr313]

This gives us a realistic distributed-software lesson:

#+begin_example
canonical authority can advance
        |
        v
language bindings can advance
        |
        v
runtime support can be implemented/tested
        |
        v
runtime support can merge
        |
        v
deployments can upgrade
#+end_example

Those arrows are not instantaneous.

*** The old 0.9 profile is historical compatibility, not garbage

Historical data remains valuable.  The StarLang compatibility layer explicitly
recognizes the old 0.9.0 wire family and the current 0.10.1 family.  The
versioned reader selects an explicit profile, performs defined field mappings,
validates the result, and emits canonical 0.10.1. [cite:@starlang-starintel-compat]

That is better than pretending old documents never existed.

The correct rule is:

#+begin_example
historical input -> explicit reader -> explicit migration -> canonical output
#+end_example

not:

#+begin_example
historical input -> change "schema_version" string -> hope
#+end_example

** Chapter 4 -- Validation, Provenance, Truth, and Authority
:PROPERTIES:
:ID:       81a76cbf-e77a-40cf-8e8c-2197e10830cc
:END:
A StarIntel document can be perfectly valid JSON, perfectly valid against its
schema, authorized for persistence, and still be wrong about the world.

This is not a defect in schema validation.  It is why StarIntel separates
different kinds of confidence and authority.

*** Five different questions

When someone says "this document is valid," ask which statement they mean:

1. *Parse validity* -- are these bytes valid JSON under the wire rules?
2. *Contract validity* -- does the parsed object conform to the selected
   StarIntel document contract?
3. *Semantic validity* -- do cross-field/domain invariants hold?
4. *Authorization* -- may this principal perform this action on this resource?
5. *Evidentiary quality* -- do the sources actually support the claim?

Only the first three are primarily document-validation questions.

A sixth question appears after persistence:

6. *Durability* -- did an authorized valid object actually become durable
   state?

Do not use one green check as an answer to all six.

*** Validate raw bytes before information is lost

A subtle wire-format problem appears before ordinary JSON Schema validation:
duplicate JSON object keys.

Many JSON parsers keep one occurrence and discard another.  If a security or
canonicalization boundary parses first and validates uniqueness later, the
validator may never see the ambiguity.

The current StarLang wire-conformance material therefore includes raw JSON
unique-key cases that must be given to the SDK/parser *as raw wire strings*.
[cite:@starlang-starintel-0101]

That is a general lesson:

#+begin_example
if parsing can destroy evidence about malformed input,
validate the relevant wire invariant before destructive normalization
#+end_example

This matters for signatures, hashes, migrations, forensic reproduction, and
cross-language agreement.

*** Select the schema by explicit version and dtype

A versioned document reader needs enough information to know which grammar and
semantics apply.

For canonical data:

#+begin_example
schemaVersion = "0.10.1"
dtype         = concrete document type
#+end_example

Historical compatibility uses its explicit historical marker and reader.
Ambiguous input should fail closed instead of being guessed into a profile.
[cite:@starlang-starintel-compat]

A robust reader should never decide "this looks roughly like 0.10.1."

*** Schema validity proves shape, not truth

Consider:

#+begin_src json
{
  "id": "person:book-demo",
  "dataset": "demo",
  "dtype": "person",
  "schemaVersion": "0.10.1",
  "fullName": "Ada Lovelace"
}
#+end_src

Suppose it validates.

What have you proven?

- =id= satisfies the document-id syntax;
- required base fields exist;
- =dtype= selects a compatible concrete contract;
- the field types and structural constraints pass.

What have you *not* proven?

- this identifier really denotes Ada Lovelace;
- the name was observed from a reliable source;
- the record is current;
- two sources are independent;
- the caller is authorized to store it;
- the runtime persisted it;
- a relation derived from it is correct.

Treating schema validation as truth is one of the fastest ways to build a
confidently wrong intelligence system.

*** Provenance lives on the common envelope for a reason

The canonical document includes multiple provenance surfaces:

- =sources= for canonical references;
- =sourceUrls= for source locations;
- =sourceRecordIds= for source-system identifiers;
- =sourceKinds= for collection category;
- source licensing/terms fields;
- =sourceRetrievedAt=;
- collector/method/version metadata;
- =provenance=;
- =chainOfCustody=;
- =transformHistory=;
- causal/workflow identifiers.

[cite:@starlang-starintel-0101]

These fields answer different questions.  Do not cram all provenance into one
free-text note.

For example:

#+begin_example
sourceUrls        where the source was accessed
sourceRecordIds   how the source system named the item
collector         which collector produced this document
transformHistory  how the representation changed
correlationId     which workflow/run this observation belongs to
#+end_example

This separation gives operators and downstream actors something queryable.

*** Derived evidence must preserve the path back to inputs

Suppose an actor resolves a domain, extracts an organization from a page, or
derives a spatial encounter from two observations.

The output should not merely say "confidence = 0.87."

A useful derived artifact needs enough lineage to answer:

- which input documents were used;
- which rule/model/actor version produced it;
- when the derivation ran;
- what transformation occurred;
- what uncertainty or confidence means;
- whether a human later verified/disputed it.

The canonical envelope gives you fields for that story.  The exact structure of
a particular derivation belongs to its dtype/capability contract.

*** Confidence is metadata, not permission to invent facts

The 0.10.1 common envelope supports confidence and quality metadata.  That is
useful precisely because evidence can be uncertain.

But attaching =confidence= to a claim does not absolve the producer from source
discipline.

Bad pattern:

#+begin_example
no source
guess a property
confidence = 0.51
therefore acceptable
#+end_example

Better pattern:

#+begin_example
bounded method + named inputs + known limitations
        |
        v
derived claim + confidenceBasis + provenance
#+end_example

If a value is unknown, absence is often more honest than a fabricated low-
confidence value.

*** Relations need evidence too

A relation document has required source, destination, and predicate fields and
can carry its own evidence references and temporal fields. [cite:@starlang-starintel-0101]

Imagine two person documents and a relation:

#+begin_example
person:A ---- employed-by ----> organization:B
#+end_example

The people/organization documents tell you about the endpoint entities.  They
do not automatically prove the employment assertion.

The relation should carry the provenance/evidence for the *edge claim*.

This is a key graph-intelligence principle:

#+begin_example
node provenance != edge provenance
#+end_example

If you lose that distinction, deleting or correcting one source can make it
impossible to determine which graph edges remain supported.

*** Authorization is not provenance

A caller can have permission to write a document that later turns out to be
false.

A source can be highly reliable while a caller still lacks permission to write
into a given tenant/dataset.

Therefore:

#+begin_example
provenance answers: why do we believe/retain this?
authorization answers: may this principal perform this action here?
#+end_example

The server's older runtime experiments already demonstrate that admission and
authorization are separate service boundaries.  The same architectural
separation must survive the 0.10.1 migration.

*** Tenancy is server/security context, not source evidence

Security ownership fields and source fields may appear close together in a
document or internal message, but they have different authorities.

A collector can report where content came from.
A service resolves which principal/tenant may write it.

Never let a client manufacture an authority decision merely by writing a field
that resembles server context.

*** Validation during migration is two-sided

A high-integrity migration must validate both sides:

#+begin_example
historical bytes
   |
   +-- validate/select historical profile
   |
   +-- map fields with explicit rules
   |
   +-- preserve unmapped material / migration record
   |
   +-- validate canonical 0.10.1 output
   |
   +-- compare/report semantics
#+end_example

The StarLang versioned compatibility path records migration metadata and
preserves original material rather than silently throwing unknown input away.
[cite:@starlang-starintel-compat]

The educational point is not the specific implementation trick.  It is that
migration itself is evidence-bearing work.

*** Failure lab: classify the broken contract

For each case, name the first contract that should fail.

| Case | First failure class |
|------+---------------------|
| duplicate raw JSON key | wire/parser conformance |
| no =schemaVersion= on canonical input | version/profile selection |
| unknown canonical dtype | schema/type selection |
| required relation predicate missing | contract validation |
| source/destination reference exists but assertion unsupported | evidentiary quality, not shape |
| caller lacks dataset write permission | authorization |
| HTTP accepted but no durable read-back | runtime/durability investigation |
| old 0.9 object has unknown legacy field | migration policy, not blind drop |
| actor emits a canonical-looking document with invented source metadata | provenance/producer correctness |

** Chapter 5 -- From Canonical Document to Running System
:PROPERTIES:
:ID:       e69e510f-3036-43f4-837d-b85377546515
:END:
Now connect the canonical model to actual StarIntel runtimes.

This chapter intentionally uses *two lanes*:

- the canonical 0.10.1 architecture we are building toward;
- exact historical/runtime evidence from the server revisions used by the
  book's executable labs.

Keeping those lanes separate is more educational than pretending a rolling
migration has already finished.

*** Lane A: the canonical logical flow

Regardless of implementation language, a persistent document pipeline needs to
answer these questions:

#+begin_example
raw/source material
      |
      v
canonical 0.10.1 document
      |
      v
validation + authorization
      |
      v
transport / work admission
      |
      v
durable mutation
      |
      v
post-mutation event
      |
      v
actor / index / inference / notification
      |
      v
derived canonical document or relation
#+end_example

At each arrow, ask what evidence proves that boundary completed.

The data model does not dictate RabbitMQ or CouchDB.  Those are runtime
implementations.  But once the runtime uses them, their delivery/revision
semantics become part of how we prove the logical transitions.

*** Lane B: the book's pinned 0.9 runtime evidence

The executable foundation/service labs were built against specific September
2026 server revisions whose live document boundary was still 0.9.x.
[cite:@starintel-server-20260916]

Those labs remain valuable because they prove concrete distributed-system
behavior:

- HTTP return is weaker than durable read-back;
- Rabbit publisher and consumer settlement are distinct;
- durable mutation and outbox state are distinct from event publication;
- actor send/registration is distinct from handler execution;
- crash/retry/recovery windows have to be observed, not inferred.

The *mechanisms* and evidence method remain relevant even as the document shape
moves to 0.10.1.

What changes is the document authority at the edge.

        |

A database implementation can have private fields.  Those fields do not become

*** Stage 1: source bytes become a candidate document

A collector begins with source-specific material: an API response, web page,
file, sensor observation, message, analyst input, or derived result.

Do not dump that source object directly into the database just because it is
JSON.

First decide:

- which canonical dtype represents the observation;
- which source fields map directly;
- which source fields belong in =extensions= or raw preservation;
- what provenance/time metadata is actually known;
- whether identity is source-derived, deterministic, or assigned by policy.

This normalization boundary is where source-specific vocabulary becomes shared
StarIntel vocabulary.

*** Stage 2: canonical validation

The normalized object must pass the explicit =schemaVersion= and dtype
contract.

Validation should be deterministic enough that a producer and consumer using
the same release agree on the result.

If Python, Common Lisp, TypeScript, Java, or another generated binding disagree
on the same canonical bytes, treat that as a conformance bug, not as harmless
language flavor.

*** Stage 3: admission and authorization

A valid document reaches a service boundary.

The service must separately decide:

- who is the caller;
- what tenant/dataset/resource is being targeted;
- which action is requested;
- whether the body and route agree;
- which correlation/idempotency context is trusted.

Only after these checks is the request eligible to cross into a side-effecting
transport/persistence path.

*** Stage 4: transport admission

If the server publishes work to RabbitMQ, a successful local publish call is
one observation.

A broker publisher confirmation, when configured and observed, is a stronger
and different observation.

Neither is the same as CouchDB persistence.

This gives a precise evidence ladder:

#+begin_example
HTTP/service returned
   <
publisher call returned
   <
broker responsibility evidenced
   <
consumer delivery evidenced
   <
durable mutation/read-back evidenced
   <
post-mutation event/actor effect evidenced
#+end_example

The exact order can vary by implementation, but the principle does not:
downstream facts require downstream observations.

*** Stage 5: durable mutation

The persistent store now owns a revision of the document.

For the book's CouchDB-backed runtime, durable mutation raises questions about:

- current revision;
- idempotency/mutation identity;
- conflict handling;
- server-private outbox state;
- tenant/storage metadata;
- what gets projected back to the canonical response.

The database chapter treats those mechanics in detail.

*** Stage 6: event publication

A stored document can cause a post-mutation event.

The event is not "the document happened again."  It is a transport object that
communicates a consequence of the mutation.

This difference gives you better recovery logic:

- durable document present, event pending -> publish/recover event;
- event maybe published, marker not durable -> duplicate publication possible;
- actor receives duplicate -> actor/consumer must use stable identity or
  idempotent behavior.

Exactly-once slogans are less useful than naming these states.

*** Stage 7: actor or capability processing

An actor can receive a typed work envelope, load/query documents, call tools,
derive a relation, enrich a document, or create a new observation.

But actor execution does not exempt its output from the document contract.

A derived object should re-enter through a canonical boundary so it gets:

- validation;
- provenance;
- authorization/policy;
- persistence semantics;
- event semantics;
- query/index visibility.

Otherwise you have built a second shadow database inside the actor.

*** Stage 8: recursive enrichment

The central StarIntel loop is therefore:

#+begin_example
document
  -> durable corpus
  -> event/work
  -> actor/capability
  -> derived document/relation
  -> durable corpus
  -> ...
#+end_example

The recursion is dataflow recursion, not magic recursion in one process.

Because each round produces typed evidence-bearing objects, the graph can grow
without every actor having to understand every other actor.

*** Worked trace: synthetic person to derived relation

Assume a canonical synthetic person document is admitted.

1. The producer constructs =person:book-demo= under dataset =book-demo=.
2. Canonical validation proves the object conforms to 0.10.1.
3. Authorization admits the write.
4. Transport accepts the mutation request.
5. Durable persistence makes the person queryable.
6. A post-persistence event makes relevant work discoverable.
7. An enrichment actor observes a public organization association.
8. The actor creates or references the organization document.
9. It emits a =relation= whose source is the person reference, destination is
   the organization reference, and predicate names the observed association.
10. The relation carries its own source/provenance.
11. That relation is validated/persisted like any other canonical document.

Notice what never happened: the actor edited an invisible in-memory graph and
declared victory.

The graph changed because durable evidence-bearing documents changed.

*** Debugging ledger: one row per boundary

When a document "disappears," create this table before changing code:

| Boundary | Expected input | Observable success | Stronger fact still unproven |
|----------+----------------+--------------------+------------------------------|
| normalization | source object | canonical candidate | schema validity |
| validation | candidate | valid contract result | authorization |
| authorization | valid request | allow decision | transport acceptance |
| publish | admitted request | publish observation | broker responsibility |
| broker | message | confirm/delivery evidence | durable mutation |
| consumer | delivery | settlement/handler result | later event consumers |
| persistence | mutation | revision/read-back | actor execution |
| event | persisted change | event delivery | actor side effect |
| actor | typed work | handler receipt/result | derived durability |

The first row without evidence is the next experiment.

*** Migration debugging: four objects may coexist

During the 0.9 -> 0.10.1 transition you may encounter:

1. an exact historical 0.9 document;
2. a canonical 0.10.1 document;
3. a migrated 0.10.1 document carrying migration provenance;
4. a runtime/storage projection containing private database fields.

- what mapping created it;
- which fields are intentionally private;
- whether semantic content was preserved;
- whether the canonical output validates.

** Chapter 6 -- Common Lisp Service Boundaries: What Did That Return Mean?
:PROPERTIES:
:ID:       2fcb51dd-2740-44da-8e14-98814decfc01
:END:
A service call returning is an observation. It is not automatically a durability guarantee.

That sentence sounds obvious until a distributed pipeline is on fire. Then logs like "publish succeeded" or "request completed" become dangerously easy to over-read. The current StarIntel source gives us a concrete way to train better instincts. [cite:@starintel-server-20260916]

*** Start with the load graph, not the nearest filename
The active server system is defined by =source/starintel-gserver.asd=. For the path studied here it loads the base consumer implementation, owner fixes, retry policy, producer code, CouchDB outbox, actor/producer integration, Rabbit handlers, and later authorized HTTP routes in a defined order. [cite:@starintel-server-20260916]

There is also a file named =source/consumers/rabbit-settlement.lisp=. It looks relevant. It is not a component of the current ASDF system at the inspected revision. This book therefore classifies it as *present, inactive* for this runtime claim.

That distinction is one of the most practical Common Lisp debugging habits you can learn:

#+begin_example
file exists
  != system loads file
  != startup calls entry point
  != current request can reach code
#+end_example

When two implementations appear to disagree, inspect the system definition and later redefinitions before you decide which one is live.

*** The HTTP path ends at a local publish call
The currently installed =POST /new/document/:dtype= handler validates the route/body contract and document, crosses authorization, and calls =publish-document=. The unchecked side of that boundary computes =documents.ingest.<dtype>=, stamps server-owned context, and delegates to =star.actors:publish=. [cite:@starintel-server-20260916]

=star.actors:publish= runs the Rabbit producer through a pinned Sento agent. The producer connection is therefore touched from one dedicated agent thread instead of whichever shared worker happened to receive the HTTP request. A bounded timeout protects the caller from waiting forever on a wedged publish path. [cite:@starintel-server-20260916]

Under that agent, the current producer calls =cl-rabbit:basic-publish=. The inspected path does not show a publisher-confirm selection/wait operation. RabbitMQ's own documentation makes the consequence precise: publisher confirms are a separate protocol mechanism, and consumer acknowledgements solve a different leg of delivery. [cite:@rabbitmq-confirms-43]

So use an evidence ladder:

| Observation | What it supports | What it does *not* prove by itself |
|-------------+------------------+------------------------------------|
| client serialized JSON | request material exists | server admission |
| HTTP returned 2xx | loaded handler completed its publish boundary | CouchDB persistence |
| local =basic-publish= call returned | client library call returned | publisher confirm |
| broker publisher confirm | broker accepted according to confirm semantics | consumer side effect |
| consumer ACK | consumer settled that delivery after its handler path | future actor success |
| authorized GET returns the document | durable corpus was observable through that read path | every post-persistence event was consumed |

The exact evidence available in a deployment can vary, but the categories should never collapse into one another.

*** Service context crosses the boundary; caller authority does not
The current HTTP publish projection builds Rabbit properties from server-captured service context: principal identity/type, credential identity, scopes, deadline, correlation, and authorization decision metadata. It does not simply trust fields in the submitted document to declare their own authority. [cite:@starintel-server-20260916]

This is why an ingest adapter should not grow configuration knobs like =--tenant-id= or =--scopes= and then smuggle those values into a body as if they were credentials. A client submits evidence. The server decides what the authenticated caller may do with it.

*** Hacker lab: prove only what you observed
Given the following timeline:

#+begin_example
12:00:00.100 POST /new/document/person -> 200
12:00:00.120 network link to RabbitMQ fails
12:00:05.500 GET /document/starintel:person:demo -> 404
#+end_example

Write three statements that are justified and three that are not. A justified statement can say the HTTP handler returned successfully. It cannot say the document was durable. The 404 means the authorized read did not observe that document at that moment; it does not uniquely identify which downstream boundary failed.

** Chapter 8 -- RabbitMQ: Settlement Is a State Machine
:PROPERTIES:
:ID:       398d460b-37b0-4c2d-a0dd-e2df671383b6
:END:
RabbitMQ code becomes much easier to reason about when you stop thinking in terms of "message handler returned" and start thinking in terms of *delivery ownership and settlement*.

#+caption: Current canonical ingest settlement model at the inspected StarIntel Server revision. Dotted edges mark the publisher-confirm evidence gap; the crash branch explains why a stable event ID is useful even with a durable outbox.
#+attr_html: :alt A StarIntel HTTP publish reaches a durable Rabbit queue, a consumer validates and persists a mutation plus pending outbox entry, publishes a post-persistence event, marks it published, and ACKs. Transient failures republish with bounded retry, permanent failures quarantine, and crash recovery may publish the same logical event again. Publisher confirms are not evidenced in the inspected publish paths.
[[file:assets/ingest-settlement.svg]]

*** One owner thread, one settlement authority
The active consumer stream opens its Rabbit connection/channel on an owner thread, applies QoS/prefetch, declares and binds durable queue state, then consumes deliveries. Worker clones receive distinct stream/channel ownership rather than sharing one channel across arbitrary threads. [cite:@starintel-server-20260916]

That matters because delivery tags are channel-scoped. The current consumer layer explicitly rejects settlement from the wrong owner thread and tracks unsettled deliveries so a failed settlement cannot be silently counted as completed work. Upstream hermetic consumer tests cover the owner-thread rule, distinct worker streams, settlement normalization, and filtered ACK behavior. [cite:@starintel-server-20260916]

*** The normal mutation path ACKs after the durable mutation/outbox operation
A canonical ingest delivery is decoded and strictly validated again at the Rabbit boundary. The server temporarily removes its own injected =tenant_id= before strict wire-schema validation and restores that server field afterward. Transient documents are intentionally filtered from persistence and receive a filtered ACK. Non-transient documents enter the CouchDB mutation/outbox operation. [cite:@starintel-server-20260916]

Only after that mutation function completes does the normal handler return an ACK settlement described in source as "durable mutation and publication completed." That phrase names the intended local operation order. It is not permission to erase the distributed crash windows discussed later.

*** Retry is not an infinite =NACK requeue=true= loop
The currently loaded retry policy is bounded. It classifies failures into transient and permanent families, tracks an attempt number and retry history, applies exponential delay with jitter, and eventually quarantines rather than retrying forever. [cite:@starintel-server-20260916]

The richer retry stream does something important: it republishes a new persistent copy to the original exchange/routing key with retry metadata and then ACKs the original delivery. Permanent failures and exhausted retries are persisted into quarantine, published to the quarantine route, and then the original is ACKed. This creates operator-visible terminal state rather than a poison message spinning forever.

The default policy values at the inspected revision are implementation knobs, not protocol truths: the source initializes a retry budget of four attempts, a 250 ms base delay, a 30 second maximum delay, and jitter. Operators should treat configuration values as revision-sensitive and recheck them before capacity planning. [cite:@starintel-server-20260916]

*** The republish-before-ACK uncertainty window
Now the uncomfortable bit.

The inspected initial producer, retry republisher, and quarantine publisher ultimately call =basic-publish=. No confirm-selection/wait operation was found in those source paths. RabbitMQ documents publisher confirms as the mechanism that lets a publisher learn that the broker has taken responsibility for a published message; that mechanism is independent of consumer ACKs. [cite:@rabbitmq-confirms-43]

Therefore this source sequence:

#+begin_example
publish retry copy
ACK original delivery
#+end_example

cannot, from source inspection alone, be strengthened into:

#+begin_example
broker durably accepted retry copy
THEN original was ACKed
#+end_example

without confirm evidence. The book labels this a *publisher-confirm evidence gap*. That is not a claim that a production loss was observed. It is a precise statement about what the inspected implementation proves and what it does not.

*** Documentation drift: routing names are evidence too
The current messaging prose says the update-ingest queue/binding uses =documents.updates.ingest= and =documents.updated.#=. The loaded =rabbit.lisp= constants instead define input queue =documents.update= and binding =documents.update.#=, with post-update output under =documents.updated.<dtype>=. [cite:@starintel-server-20260916]

That kind of mismatch is easy to dismiss as naming trivia. It is not. A wrong routing key is a perfectly functional black hole.

When debugging routing, collect four strings from executable configuration/source:

1. exchange name;
2. queue name;
3. queue binding pattern;
4. actual emitted routing key.

Then compare them mechanically. Do not debug a prose diagram for an hour.

*** Failure lab: classify before retrying
For each failure, decide whether retry, quarantine, or immediate operator correction is justified:

| Failure | First reasoning question |
|---------+--------------------------|
| malformed JSON/document | can the same bytes ever become valid without correction? |
| authorization rejection | will retrying with the same principal/resource decision change anything? |
| broker connection reset | was the failure transient, and is publish outcome ambiguous? |
| CouchDB conflict on same logical mutation | duplicate, concurrent update, or mutation-ID misuse? |
| handler bug such as undefined function | retryable infrastructure fault or deterministic code defect? |

A retry policy is not a garbage disposal for exceptions. Classification is part of the data contract.

- ★★ Trace a transient error from original delivery through republish and original ACK, naming the uncertainty window.

** Chapter 9 -- CouchDB: Storage Revisions, Canonical Revisions, and the Durable Outbox
:PROPERTIES:
:ID:       504fe348-019f-49dd-b90c-056960e32e90
:END:
CouchDB is the durable store in the runtime studied by this book, but CouchDB's
field names are not the StarIntel schema authority.

That distinction becomes more important in 0.10.1.

Canonical StarIntel uses =id= and optional =rev=.  CouchDB internally uses
=_id= and =_rev=.  A runtime adapter can map between those representations
without exposing the database's private storage shape as the canonical public
document contract. [cite:@starlang-starintel-0101;@couchdb-docs-35]

*** Canonical identity versus storage identity

Think in three layers:

#+begin_example
canonical document identity
       id = person:book-demo
             |
             v
runtime storage projection
             |
             v
CouchDB storage identity
       _id = implementation-owned representation
#+end_example

The same applies to revision metadata:

#+begin_example
canonical rev
    <-> runtime projection <-> CouchDB _rev
#+end_example

The 0.10.1 server migration draft explicitly treats CouchDB identity/revision as
storage concerns and projects canonical identity/revision at the HTTP/event
boundary rather than making raw CouchDB metadata the public schema.
[cite:@starintel-server-pr313]

The precise mapping is runtime implementation.
The separation is architecture.

*** Why =_rev= exists

CouchDB's =_rev= participates in optimistic concurrency control.

If you read revision A, another writer stores revision B, and you then try to
write while claiming revision A is current, CouchDB can reject the stale update.

That means a storage revision answers:

#+begin_example
Which stored revision did this update build on?
#+end_example

It does not answer:

#+begin_example
Which StarIntel schema version is this?
What logical mutation is this?
Was an event already published?
Is this document true?
#+end_example

Those belong to other contracts.

*** Mutation identity is a fourth identity layer

The pinned runtime studied by the book's outbox lab keeps logical mutation
identity separate from document identity and database revision.

If a request supplies an explicit mutation/idempotency identity, the runtime can
recognize a replay of the same logical operation.  Otherwise the historical
runtime derives one from operation/public-document content.
[cite:@starintel-server-20260916]

Now the identity table looks like:

| Identity | Question |
|----------+----------|
| document =id= | Which logical StarIntel document is this? |
| canonical/storage revision | Which document revision are we updating/observing? |
| mutation/idempotency ID | Is this the same logical write operation being replayed? |
| event ID | Is this the same logical post-mutation event appearing again? |
| correlation ID | Which broader request/workflow connects these observations? |

One string cannot safely serve all five purposes.

*** Same mutation ID + different content is not idempotency

Suppose:

#+begin_example
mutation ID = M1
content hash = H1
#+end_example

is accepted.

A replay with:

#+begin_example
mutation ID = M1
content hash = H1
#+end_example

can be recognized as the same logical work.

But:

#+begin_example
mutation ID = M1
content hash = H2
#+end_example

is a semantic conflict.

The caller reused one logical-operation identity for different work.

Correct behavior is to surface the ambiguity, not silently "deduplicate" it.

*** The outbox records committed intent to publish

A durable outbox exists because one database transaction and one RabbitMQ
publication are not one atomic transaction.

Conceptually:

#+begin_example
1. prepare mutation
2. store document mutation + pending outbox intent
3. publish post-mutation event
4. mark outbox event published
5. settle upstream delivery
#+end_example

The crucial move is step 2.

If the process dies after the database commit but before event publication,
durable state still says:

#+begin_example
this mutation committed
this event still needs publication
#+end_example

The system can recover that intent.

*** Why the outbox is at-least-once

Consider the more difficult crash window:

#+begin_example
event publication succeeded
process crashes
published marker was not committed
#+end_example

After restart, the database still says "pending."

The runtime cannot know from that local row alone whether the external side
effect happened.

Recovery must be willing to publish again.

So:

#+begin_example
outbox + stable event ID + idempotent consumers
        ->
manageable at-least-once delivery
#+end_example

not:

#+begin_example
outbox -> magical global exactly-once transaction
#+end_example

This ambiguity is fundamental whenever durable state and an external side
effect do not share one atomic commit.

*** Storage-private state should stay private

The pinned server outbox path keeps server-only mutation/outbox bookkeeping
inside the stored representation.

That information is operationally useful but does not automatically belong in
a client-facing canonical document.

A clean boundary projects:

#+begin_example
public canonical fields
        +
only intentionally exposed revision/metadata
#+end_example

while retaining private persistence machinery internally.

This reduces accidental coupling between clients and one database layout.

*** Conflict debugging: first name the conflict domain

"Conflict" is too vague.

| Conflict domain | Example |
|-----------------|---------|
| canonical document identity | an insert collides with an existing logical document |
| storage revision | writer used stale CouchDB =_rev= |
| mutation identity | same idempotency ID reused for different work |
| event identity | duplicate physical publication of one logical event |
| semantic merge | two valid updates cannot both satisfy domain invariants |

Each needs a different remedy.

Refetching a CouchDB revision cannot fix an idempotency-key reuse bug.
Generating a new idempotency key cannot solve a semantic merge conflict.

*** Crash matrix

For each point, predict durable state:

| Crash point | Document durable? | Pending event intent? | Duplicate event possible? |
|-------------+-------------------+-----------------------+---------------------------|
| before mutation commit | no | no | no event should be inferred |
| after mutation commit, before publish | yes | yes | recovery should publish |
| after publish, before marker | yes | yes | yes |
| after marker, before upstream ACK | yes | published | upstream delivery may replay; mutation identity must absorb it |

The exact historical implementation is revision-pinned.
The reasoning survives the schema migration.

*** Canonical read-back is a projection

If a client reads a 0.10.1 document from a CouchDB-backed StarIntel runtime, the
client should reason about the *canonical read result*, not the raw database row.

That means the client can ask:

#+begin_example
id?
rev?
dtype?
schemaVersion?
dataset?
domain fields?
#+end_example

without depending on:

#+begin_example
private outbox arrays?
tenant bookkeeping?
CouchDB-only identity field?
internal mutation ledger?
#+end_example

A direct database shell is a useful operator tool.
It is not the same contract as the public document API.

** Chapter 14 -- Ingestion as an Evidence Ladder
:PROPERTIES:
:ID:       ee2a6882-1976-41f6-a790-0c9951f7ae45
:END:
A client should never return one boolean called =success= when the system crossed
five asynchronous boundaries.

The job of an ingest client is to report what it actually observed.

*** The evidence ladder

A useful generic ladder is:

#+begin_example
request accepted by service
        |
        v
publish boundary returned
        |
        v
broker responsibility evidenced
        |
        v
consumer processing/settlement evidenced
        |
        v
durable mutation evidenced
        |
        v
post-mutation event/actor consequence evidenced
#+end_example

A system may expose only some rungs to a given client.

The client should not fabricate the rest.

*** Historical Project 2 used the legacy write/read routes

The original book adapter was written against the pinned 0.9 runtime and uses
the then-current legacy document routes:

#+begin_example
POST /new/document/:dtype
GET  /document/:id
#+end_example

Its fixture expects historical =_id= because that adapter intentionally tests
that historical profile. [cite:@starintel-server-20260916]

In this edition, that is a compatibility/runtime lab.

New canonical 0.10.1 clients should target a runtime that actually advertises
and implements 0.10.1, rather than changing the fixture locally and hoping an
old server accepts it.

*** Current contracted operations are a better integration seam

Current server =main= exposes named operations including:

#+begin_example
documents.create
documents.bulk.create
documents.get
documents.update
documents.delete
documents.search
#+end_example

through its machine-readable HTTP contract. [cite:@starintel-server-20261005]

The current default branch still validates its historical document profile.
Server PR #313 is the tested draft migration of these boundaries to generated
0.10.1. [cite:@starintel-server-pr313]

So a current client must discover both:

1. does the operation exist;
2. which document contract does this deployment accept.

*** Three conservative result states

The Project 2 adapter uses deliberately narrow wording:

#+begin_example
submission.state = http_publish_boundary_returned

persistence.state = not_checked
                 | observed
                 | not_observed_before_deadline
#+end_example

Those names are excellent distributed-systems hygiene.

=http_publish_boundary_returned= does not mean "broker durably confirmed."

=persistence.observed= is stronger because an authorized later read saw the
document through the server's read path.

=not_observed_before_deadline= is weaker than "lost."

The client reports an observation, not a diagnosis.

*** Why authorization failure and absence are different

Suppose write admission succeeds, but read-back returns 403.

You cannot conclude:

#+begin_example
document is absent
#+end_example

because the caller was not allowed to make that observation.

A read-back 404 under an authorized principal is a different fact.

This is why the adapter keeps authorization errors separate from polling
absence.

*** The service-backed trace is no longer hypothetical

The earlier manuscript said a future disposable-stack test should prove the
HTTP/Rabbit/Couch boundary.

That work has since been executed and merged in book PR #58.
[cite:@chatgpt-books-starintel-pr58]

At its exact pinned runtime, the disposable trace established these bounded
observations:

**** Baseline

- a synthetic HTTP POST returned 200;
- an authorized read-back later observed the persisted document.

This proves that the disposable stack could cross the complete tested
HTTP -> Rabbit -> consumer -> CouchDB -> authorized-read path for that fixture.

It does not prove every production deployment behaves identically.

**** Broker-down fault

The experiment verified RabbitMQ was stopped while the HTTP process remained
alive.

A fresh POST still returned 200.

Across the bounded read window, the document was not observed; the final reads
remained 404.

This is an extremely useful teaching result:

#+begin_example
HTTP publish-boundary return
        !=
durable persistence
#+end_example

The trace does not uniquely prove which message was lost or which internal call
reported success.  It proves only the observations it retained.

**** Explicit recovery

The experiment then performed explicit operator recovery:

#+begin_example
start RabbitMQ
restart StarIntel
wait healthy
submit fresh fixture
#+end_example

The fresh document became visible through authorized read-back.

That proves the tested explicit recovery procedure for the pinned disposable
stack.

It does *not* prove transparent broker reconnect or replay of the ambiguous
broker-down submission.

*** What PR #58 intentionally did not prove

The merged trace did not upgrade these questions to tested claims:

- publisher-confirm acceptance;
- settlement-failure redelivery;
- the exact CouchDB outbox crash window;
- transparent broker reconnect;
- production latency/SLOs;
- production capacity;
- every accepted-but-unobserved message's fate.

This is the evidence discipline the book should model.

*** A four-state client is often better than a boolean

A richer ingest result might track:

#+begin_src json
{
  "request": {
    "returned": true,
    "status": 202
  },
  "broker": {
    "confirmed": null
  },
  "persistence": {
    "checked": true,
    "observed": false,
    "deadlineReached": true
  },
  "correlationId": "corr-book-example"
}
#+end_src

=null= can mean "not observed by this client," which is very different from
=false= meaning "we have evidence it did not happen."

*** Read-back is evidence through one product path

Even a successful authorized GET proves a bounded thing:

#+begin_example
the current read API observed this document
#+end_example

It does not by itself prove:

- every secondary index has updated;
- every actor received the event;
- every replica is caught up;
- every search product can find it;
- every cache is fresh.

Each downstream product needs its own observation.

*** An ingestion timeline should preserve identities

A useful trace keeps at least:

- document ID;
- correlation ID;
- mutation/idempotency ID when exposed;
- queue/message identity when observable;
- event ID;
- actor execution/schedule IDs for downstream work.

This lets an operator ask:

#+begin_example
same document, new mutation?
same mutation, duplicate delivery?
same event, duplicate actor receipt?
new derived document from same root?
#+end_example

Without identity discipline, retries look like new work.

*** A 0.10.1 canonical ingest lab must wait for a 0.10.1 runtime

The book should not fake an end-to-end canonical test by validating 0.10.1
locally and then sending transformed historical bytes to an old-only server.

The correct future lab is:

#+begin_example
canonical 0.10.1 fixture
       |
       v
runtime advertising real 0.10.1 support
       |
       v
named documents.create operation
       |
       v
Rabbit / consumer / canonical validation
       |
       v
CouchDB mutation
       |
       v
canonical documents.get read-back
#+end_example

Until the runtime support used by the book is merged/pinned and that test runs,
the canonical end-to-end claim remains pending.

*** Debugging worksheet

| Observation | What it proves | What it does not prove |
|-------------+----------------+------------------------|
| local canonical validation passed | fixture conforms to selected contract | server accepts it |
| HTTP 2xx/202 | request boundary returned successfully | persistence |
| broker confirm | broker responsibility under configured semantics | consumer mutation |
| consumer ACK | delivery settled under consumer contract | every later event/actor |
| authorized GET returns document | server read path observes durable state | search/index/actor completion |
| search returns document | current search product observes it | every corpus path agrees |
| actor handler receipt | handler executed at least to receipt point | derived output durable |
| derived output read-back | downstream document became visible | operation phase complete unless completion evidence says so |

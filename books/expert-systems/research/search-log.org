** 2026-09-16 -- incremental positive-pattern network
Questions: Which current primary/official evidence supports the alpha/filter -> partial join -> complete activation teaching decomposition? Which semantics can be changed as optimization, and which must remain frozen from milestone B?

Inspected:
- Forgy, /Rete: A Fast Algorithm for the Many Pattern/Many Object Pattern Match Problem/, /Artificial Intelligence/ 19(1), 17--37, DOI 10.1016/0004-3702(82)90020-0, as the primary RETE bibliographic/algorithm lineage source. No paper benchmark number is imported into this project.
- official CLIPS 6.4.2 Basic Programming Guide, Appendix D.1 “Ordering of Patterns on the LHS.” The current text says CLIPS constructs a network of LHS patterns before execution, filters reactive pattern entities through it, retains partial rule instantiations, considers cross-pattern variable bindings in LHS order, and activates the rule once all pattern bindings satisfy constraints.

Result: milestone C derives a deliberately simplified positive-pattern RETE-like network from the book's own accepted matcher. Per-production alpha memories cache local matches/bindings; beta tokens cache ordered partial supports/bindings; joins extend compatible tokens; terminal tokens become ordinary milestone-B activations; assert/retract deltas maintain caches. The complete-rematch agenda remains the executable oracle. Node sharing, negative/existential CEs, truth maintenance, TREAT, persistence, and all performance claims remain deferred.

** 2026-09-16 -- justification-based truth maintenance
Questions: What problem does a TMS solve that the accepted matcher cache does not? What is the primary historical basis for recording reasons/dependencies? How does a current maintained production system describe multiple logical support groups and retraction?

Inspected:
- Jon Doyle, /A Truth Maintenance System/, /Artificial Intelligence/ 12(3), 231--272, 1979, DOI 10.1016/0004-3702(79)90008-0. Primary MIT AIM-521 artifact/metadata was inspected through MIT DSpace; its abstract describes recording and maintaining reasons for program beliefs, belief revision, explanation, and problem-solver control.
- official /CLIPS Reference Manual, Volume I: Basic Programming Guide/ 6.4.2 (2025-01-16), Section 5.4.8 “Logical Conditional Element.” The current PDF documents logical support, more than one support group from the same or different rules, removal after a support group is broken when no other group remains, and unconditional support.

Result: milestone D remains course-local and smaller than either full Doyle-style belief revision or CLIPS logical-CE semantics. It adds an explicit justification ledger over the milestone-C incremental matcher; reasons refer to exact support and conclusion occurrences; multiple reasons are OR alternatives while each reason requires all of its supports; grounding must ultimately reach current base evidence so unsupported derived cycles cannot self-sustain; base retraction drives dependency-directed cascade. Historical reasons stay inspectable but stale occurrence stamps cannot ground reasserted IDs. No ATMS, contradiction resolution, uncertainty, negative CEs, persistence, transaction guarantee, or benchmark is inferred from these sources.

** 2026-09-16 -- assumptions, contradictions, and counterevidence
Questions: How should the course make assumptions explicit without falsely claiming a full ATMS? What should happen when current grounded evidence conflicts? Which context dimensions keep a technical-state contradiction rule from collapsing observations across time?

Inspected:
- Jon Doyle, /A Truth Maintenance System/ (1979), primary MIT AIM-521 metadata/abstract, rechecked for the explicit assumption/revision framing.
- Johan de Kleer, /An Assumption-Based TMS/, /Artificial Intelligence/ 28(2), 127--162, March 1986, DOI 10.1016/0004-3702(86)90080-9. Elsevier/ScienceDirect publisher metadata and abstract were inspected; the abstract identifies assumption-set manipulation and reasoning with inconsistent information as central ATMS capabilities.
- current systemd Unit D-Bus API documentation for =ActiveState= and =SubState=; upstream documentation was cross-checked on 2026-09-16. =ActiveState= is the high-level unit state property, while =SubState= is finer grained.

Result: milestone E deliberately remains smaller than an ATMS. It marks exact current base occurrences as explicit assumptions, declares stable provenance-bearing contradiction pattern pairs, preserves both grounded sides as counterevidence, and gives callers an explicit =:halt= or =:report-only= execution policy. The technical lab models =(unit-active-state unit state epoch)= and carries =epoch= across both contradiction patterns so a legitimate transition at a later observation is not treated as simultaneous inconsistency. The epoch is course-local context, not a systemd field. No automatic source preference, uncertainty score, ATMS environment/nogood machinery, or benchmark is inferred.

Result: milestone F is a read-only explanation layer over accepted reasoning state.

* Major Projects
** Project 1 -- LFE DSL
:PROPERTIES:
:ID:       55542619-da75-550e-a955-874f79c97643
:END:
Purpose: Design, macro-expand, test, and document a useful domain-specific language.
Learning outcomes: integrate multiple chapter concepts; make architecture/test/provenance tradeoffs explicit.
Prerequisites: staged from Chapters 1--7 and revisited in Chapter 16.
Relevant chapters: Chapters 1--3 define the semantic kernel as data/patterns/recursion; Chapters 4--5 make the function/data interface explicit; Chapters 6--7 add and audit the macro surface; Chapter 16 evaluates the resulting DSL as a language design.
Architecture: keep the semantic routing kernel explicit and independently testable; macros are a source layer, not a replacement runtime. Split domain logic, interfaces, tests, and later operational boundaries rather than one monolith.
Implementation language/tooling: LFE compiled to BEAM; dependencies and LFE release are pinned/reproducible in the executable book gate.
External dependencies: public/synthetic data and primary documentation only unless a later issue records an approved dependency.
Tests: unit/scenario regressions plus direct Erlang-to-LFE interoperability at the real BEAM module boundary; macro work adds exact exported-macro expansion equality via the documented top-level expander, a separate compiled macro consumer, deliberate non-hygienic capture evidence, and a compile-failure fixture for unsupported DSL syntax.
Failure scenarios: malformed event, malformed rule, no matching route, order-dependent shadowing, missing recursive base case, invalid macro syntax/expansion, and variable capture in deliberately unsafe teaching macros.
Visuals: event/rule execution-flow figure plus macro-expansion/runtime-boundary figure; later runtime figures as those stages land.
Research requirements: verify version-sensitive APIs and macro behavior from primary LFE/Erlang sources before implementation.
Expected deliverable: runnable implementation, tests, design/research notes, diagrams, exercises, and an exportable project chapter.
Current staged implementation: *Event Routing DSL*. The runtime kernel remains ordered BEAM tuples consumed by =event-rules:route/2=. The =event-rules-dsl:routes= exported macro is now a compile-time source layer that expands accepted clauses to that same explicit rule data and rejects unsupported syntax. It intentionally introduces no runtime bindings; the regression suite contains a separate unsafe macro solely to demonstrate LFE's documented non-hygienic capture behavior.

** Project 2 -- Actor Application
:PROPERTIES:
:ID:       3b068142-3d00-5f2a-abe0-8f321c9817bb
:END:
Purpose: Build a useful raw-process service around Project 1 while keeping BEAM process/message semantics visible before OTP behaviours abstract them.
Learning outcomes: design explicit message protocols; distinguish PID identity from protocol vocabulary; correlate request/reply pairs with references; model actor state as recursive loop arguments; reason about selective receive, same-sender ordering, timeout, isolation, and observed failure; prove direct Erlang/LFE process interoperability.
Prerequisites: Chapters 1--7 and Project 1's pure routing kernel. Chapters 8--10 own the first executable process milestone.
Relevant chapters: Chapter 8 establishes the ordinary Erlang/LFE BEAM boundary and protocol terms; Chapter 9 derives process state and failure observation from recursive loops; Chapter 10 develops correlation, selective receive, ordering, timeout semantics, and protocol debugging. Later OTP chapters refactor the mechanism rather than redefining its semantics.
Architecture: one =actor-router= process owns the current immutable rule-list term and delegates routing to the independently tested =event-rules:route/2= kernel. Requests use =#(call CallerPid Ref Request)= and replies use =#(reply Ref Result)=. State changes only when the recursive loop receives a replacement rule term. No registry, process dictionary, ETS state, persistence layer, or hidden actor framework is introduced at this checkpoint.
Implementation language/tooling: LFE v2.2.2 compiled to BEAM under the same focused executable gate as Project 1, with a direct Erlang runtime smoke at the process boundary.
External dependencies: Project 1 code plus standard BEAM/LFE runtime facilities; no network service or third-party runtime dependency.
Tests: routing through the process, stale-reply correlation, rule-state replacement/readback, changed-state routing, tagged bad-request handling, same-sender ordered requests, caller-side timeout against a still-live silent process, clean stop, direct Erlang start/call/stop, and Erlang monitor observation of an intentionally crashed LFE actor.
Failure scenarios: stale reply, malformed request, wrong state recursion, caller timeout without remote cancellation, intentional actor crash, absent =DOWN= observation, and assumptions of global FIFO ordering across independent senders.
Visuals: editable actor protocol diagram showing caller/ref correlation, actor-owned state, pure Project 1 kernel delegation, and an independent monitor relationship.
Research requirements: current tagged LFE process syntax and current official Erlang process/signal/receive/monitor semantics, including selective-receive cost and ordering boundaries. OTP behaviours/supervision require a fresh later research pass.
Expected deliverable: runnable pre-OTP actor implementation, executable regressions, direct Erlang interoperability/failure smoke, research record, diagram, failure labs, and Chapters 8--10.
Current staged implementation: *Actor Router checkpoint A*. This is intentionally a raw-process teaching milestone. It does not claim =gen_server= callbacks, supervisor strategy, application layout, persistence, distribution, or release semantics.

** Project 3 -- OTP Service
:PROPERTIES:
:ID:       2b4274af-a32a-5057-91be-6e894c5a298f
:END:
Purpose: Refactor Project 2's deliberately hand-written server loop into an ordinary OTP service while preserving the already-tested routing kernel and making lifecycle, ownership, testing, and packaging boundaries observable rather than magical.
Learning outcomes: separate generic =gen_server= machinery from callback policy; read callback returns as explicit reply/state transitions; distinguish =call= from =cast= failure surfaces; use =sys= as an OTP system/debugging boundary; understand =start_link= and child-spec ownership; reason about =one_for_one= restart policy and restart intensity; prove that process restart is not process-state recovery; choose test boundaries that isolate pure semantics, service state, interoperability, and lifecycle failures; distinguish process/supervisor/application/release identities; and construct a bootable OTP release from explicit metadata rather than shell folklore.
Prerequisites: Chapters 1--10, Project 1's pure =event-rules:route/2= kernel, and Project 2's raw Actor Router. Readers should understand explicit request/reply correlation and process-local recursive state before OTP hides that plumbing.
Relevant chapters: Chapter 11 derives the behaviour/callback split, standard call/cast semantics, direct Erlang interoperability, and system-message tooling. Chapter 12 derives supervision policy, current map child specifications, controlled crash/restart, replacement state, and restart-intensity escalation. Chapter 13 turns those semantics into a layered test architecture: EUnit fixture contracts over the compiled LFE service, deterministic =sys=-controlled failure conditions, and an explicit boundary between unit/service tests and larger Common Test/system work. Chapter 14 adds an LFE =application= callback, =.app= component metadata, =.rel= whole-system composition, =systools= construction, fresh-VM boot evidence, and package-shape inspection. Distribution, persistence, production observability, and release upgrades remain later chapters/slices.
Architecture: =otp-router= is an LFE =gen_server= callback module whose state is only the current rules term and whose route requests delegate to =event-rules:route/2=. =otp-router-sup= is an LFE =supervisor= using =one_for_one= and a permanent worker child. The supervisor owns lifecycle policy; it does not own routing semantics or persistence. =otp-router-app= is a deliberately thin LFE =application= callback that hands the existing supervisor tree to OTP application ownership. =otp_router.app= identifies the component, its modules/names/dependencies/version, and its callback. A generated =.rel= then composes that component with the tested runtime's exact ERTS/Kernel/STDLIB versions. Testing preserves those boundaries rather than introducing a mock runtime.
Implementation language/tooling: pinned LFE v2.2.2 compiled to ordinary BEAM modules and exercised from both LFE and Erlang under the focused repository gate. Supervisor flags and child specifications are ordinary BEAM maps. Standard EUnit drives compiled LFE service contracts. Release construction uses the ordinary OTP application controller, =systools:make_script/2=, =erl -boot=, and =systools:make_tar/2=; no LFE-specific release wrapper is introduced.
External dependencies: Project 1 code plus standard LFE/Erlang/OTP runtime facilities. No database, message broker, distributed node, third-party actor framework, or network service is introduced.
Tests: LFE regressions cover route calls, rule replacement/readback, =sys:get_state/1=, tagged bad requests, and clean stop. EUnit fixtures give each service-contract case a fresh registered LFE server and include ownership regressions that refuse ambient/foreign registered processes. Direct Erlang interoperability/failure regressions cover timeout, supervised replacement/fresh state, and restart-intensity escalation. Checkpoint C adds a clean-build application lifecycle test, verifies the worker belongs to =otp_router=, dynamically builds a release from runtime versions, boots a fresh VM from the generated boot file, routes a real event there, rejects =.rel=/=.app= version mismatch, rejects a dependency missing from the release closure, and inspects the generated release package layout.
Failure scenarios: domain rejection versus callback crash; caller timeout without remote cancellation; volatile state loss after worker replacement; assuming a registered name means PID identity is stable; assuming supervision means unbounded restart forever; leaking or stealing a registered process between tests; =.app= callback/metadata errors; =.rel=/=.app= version disagreement; missing release dependency closure; assuming a local boot script is portable; and assuming a generated tarball proves deployment.
Visuals: editable =otp-supervision.dot/svg= separates callback/service/supervisor ownership; =testing-layers.dot/svg= maps layered test boundaries; =release-boot.dot/svg= maps LFE source -> BEAM modules -> application metadata/controller -> release metadata/=systools= -> fresh boot/package while keeping deployment claims outside the diagram.
Research requirements: tagged LFE v2.2.2 implementation evidence plus current official Erlang/OTP behaviour, testing, application, release, =rel=, and =systools= documentation. Runner OTP is recorded separately from the current upstream documentation baseline.
Expected deliverable: runnable =gen_server=/supervisor/application modules, LFE and Erlang regressions, EUnit contract fixtures, controlled failure labs, release construction/fresh-boot/package checks, research records, editable diagrams, exercises, and Chapters 11--14.
Current staged implementation: *OTP Router checkpoints A--C are merged*. PR #109 merged the accepted application/release checkpoint as =fb17a8e6cf43624db15bde9535b9721f14c0c470= after exact approved head =297f8957d57a0b839203247e26ae88978846d93b= passed focused =lfe-book= run =35167332304= and generic =books-ci= run =35167332291=. Project 3 therefore owns the completed local service/supervision/testing/application/release progression. It still deliberately excludes distributed-node operation, persistence/replay, =relup=/hot upgrade, cross-host target installation, bundled-ERTS portability, production tracing/telemetry policy, coverage/benchmark claims, and production restart/upgrade recommendations.

** Project 4 -- Supervised Distributed Workflow
:PROPERTIES:
:ID:       c3aa8a55-f0c8-591a-a153-47d67a4cdfd7
:END:
Purpose: Put the already accepted Project 3 OTP application behind a real Erlang node boundary and make remote addressing, node-local supervision, connection failure, system testing, and security boundaries explicit without rewriting the service.
Learning outcomes: distinguish module/application/process/node identities; address a locally registered =gen_server= on another node with ={Name,Node}=; use =peer= to own disposable test nodes; understand that =nodedown= is transport/node evidence rather than a domain result; separate local supervisor recovery from node-level failover; choose Common Test when lifecycle/configuration spans multiple nodes; and keep test-only cookie/plain-distribution mechanics separate from production transport security.
Prerequisites: Chapters 1--14, with Project 1's pure routing kernel and the merged Project 3 =otp_router= application as the system under test. Readers should already understand local process monitoring, =gen_server= calls, supervision, application ownership, and release construction before adding a node boundary.
Relevant chapters: Chapter 15 owns checkpoint A: node identity/naming, node-local registered names, remote =gen_server= references, disposable peers, Common Test system lifecycle, =monitor_node= failure observation, local-supervision limits, distribution-security boundaries, and a layered debugging method. Later Project 4 checkpoints may add persistence, stronger failure/recovery protocols, or deployment work only after separate research and tests.
Architecture: the distributed project does *not* fork =event-rules=, =otp-router=, =otp-router-sup=, or =otp-router-app=. A distributed origin node drives the existing application on a disposable peer node. The peer owns its normal OTP application and local supervision tree; the origin addresses the remote local registration as ={'otp-router', PeerNode}=. Node monitoring observes failure but does not create a replacement service elsewhere.
Implementation language/tooling: pinned LFE v2.2.2 remains the service language. The first system-test harness is an Erlang Common Test suite because its purpose is to prove the ordinary BEAM boundary from another node, not to introduce an LFE-specific distribution layer. OTP =peer= is used because it was introduced in OTP 25.0 and is compatible with the historical focused-runner floor. The focused workflow starts a real distributed origin node and fails closed if =peer= or Common Test are unavailable.
External dependencies: only the already accepted project code plus standard Erlang/OTP distribution, =peer=, =gen_server=, application controller, node monitoring, RPC and Common Test facilities. No third-party cluster framework, registry, database, broker, service-discovery system, or network appliance is added.
Tests: checkpoint A requires a real remote =gen_server:call/3= to the compiled LFE service and the same critical-event =pager= result; verifies the origin has no local =otp-router= registration while the remote router and supervisor PIDs both belong to =PeerNode=; stops the peer and requires ={nodedown,PeerNode}= from an explicit node monitor; then makes a later remote call and requires its caught exit reason to contain the documented ={nodedown,PeerNode}= category. The Common Test runner rejects failed, user-skipped, and auto-skipped cases rather than treating a non-run distributed scenario as success.
Failure scenarios: origin accidentally running as =nonode@nohost=; peer startup/connection failure; wrong cookie/naming mode; missing remote application resource; application start failure; node-local registration absent; domain failure confused with distribution failure; worker-only crash confused with whole-node loss; assuming =monitor_node= gives stronger signal ordering than documented; and assuming local supervision transparently restarts work on another node.
Visuals: editable =distribution-boundary.dot= shows origin Common Test node -> remote ={Name,Node}= reference -> Erlang distribution -> peer application/local supervisor/LFE worker/pure kernel, plus explicit dashed =nodedown= and remote-call-failure observation paths.
Research requirements: current official Distributed Erlang, =gen_server=, =monitor_node=/=net_kernel=, =peer=, Common Test, secure-coding and TLS-distribution documentation, with the OTP 25 introduction point for =peer= checked separately from current OTP 29.1 docs. Actual runner OTP remains execution evidence and must not be relabeled as the documentation baseline.
Expected deliverable: substantial Chapter 15, Distribution Pass 07, executable same-host multi-node Common Test harness, editable diagram, debugging/failure labs, exercises, exact claim-status ledger, and focused/publication/Nix gates before editorial handoff.
Current staged implementation: *Project 4 checkpoint A is authored but UNTESTED*. Branch =book/lfe-distribution-07= and issue #133 carry the first distributed-node slice. Until exact-head focused CI executes the new Common Test scenarios, no Project 4 behavior is promoted to TESTED. This checkpoint deliberately excludes network partitions/split brain, consensus/leader election, automatic failover, persistence/replay, exactly-once delivery, discovery frameworks, cross-host deployment, production cookie/EPMD policy, TLS configuration proof, latency/throughput benchmarks, and availability claims.

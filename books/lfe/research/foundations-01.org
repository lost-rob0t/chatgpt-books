* LFE is Lisp syntax over BEAM semantics, not a private runtime
** DOCUMENTED
At LFE v2.2.2, the user guide defines LFE literals, function references, modules/functions, patterns, and Erlang-style data forms. The upstream source examples compile normal LFE modules and use Erlang facilities directly. =examples/messenger.lfe= spawns a process and uses =receive=; =examples/fizzbuzz.lfe= demonstrates function-clause pattern matching, guards, recursion, and direct =lists= calls. The compiler CLI documents =lfec -o ... source.lfe=.

Sources:
- https://github.com/lfe/lfe/blob/v2.2.2/doc/src/lfe_guide.7.md
- https://github.com/lfe/lfe/blob/v2.2.2/examples/messenger.lfe
- https://github.com/lfe/lfe/blob/v2.2.2/examples/fizzbuzz.lfe
- https://github.com/lfe/lfe/blob/v2.2.2/bin/lfec

Teaching consequence: early code should expose ordinary BEAM terms and module calls. We should not teach a fictional object system or pretend LFE has separate process/message semantics from Erlang.

* Recurring variables in LFE patterns
** DOCUMENTED
LFE v2.2.2's own =dev/pattern-test.lfe= explicitly tests recurring variables across function-clause patterns, including tuples and lists. Project 1 uses this facility to express rules such as “the event level must be the same term as the rule level” declaratively in the clause head.

Source: https://github.com/lfe/lfe/blob/v2.2.2/dev/pattern-test.lfe

This is a useful Lisp/BEAM lesson: the source is an S-expression, but the important semantic operation is still structural pattern matching.

* Terms, lists, variables, and matching
** DOCUMENTED
Erlang System Documentation v29.0.5/29.0.6 defines values as terms; lists recursively as empty list or head plus tail; tuples and maps as compound data; and variables as single-assignment. Pattern matching binds previously unbound variables, and failed matches fail rather than mutating a previous binding.

Sources:
- https://www.erlang.org/doc/system/data_types.html
- https://www.erlang.org/doc/system/expressions.html
- https://www.erlang.org/doc/system/patterns.html

Teaching consequence: Chapter 1 must distinguish source notation from runtime representation, Chapter 2 must teach matching as control/data validation rather than “assignment with funny syntax”, and Chapter 3 can derive recursion naturally from immutable list structure.

* Processes and mailbox ordering -- important future constraint
** DOCUMENTED
Current Erlang process documentation describes communication as asynchronous signals. Ordinary received messages are appended to a process message queue and =receive= selects the first matching message. The language guarantees signal ordering from one sender to one destination, not a single universal order across independent senders. OTP 28 also introduced priority-message reception, which can change queue order relative to signal arrival while preserving the underlying signal-order guarantee.

Source: https://www.erlang.org/doc/system/ref_man_processes.html

This is deliberately recorded before the process chapters so later prose does not teach the common but wrong simplification “an Erlang mailbox is globally FIFO.” Project 2 must make sender/order assumptions explicit and test selective receive and correlation IDs.

* Project 1 semantic kernel
** DESIGN USED BY THIS SLICE
The first project stage is an event-routing rule system represented entirely as BEAM terms. The rule list is ordered and first-match wins. Initial forms are =when-level=, =when-service=, and =otherwise=. Invalid event/rule terms return tagged errors.

Why data first:
1. Chapter 1 can inspect concrete terms.
2. Chapter 2 can implement routing with patterns rather than nested conditionals.
3. Chapter 3 can make the recursive base/step cases explicit.
4. Chapters 6--7 can later add macros and compare macro-expanded output against an already-tested semantic core.
5. Chapter 8 can show Erlang calling the compiled LFE module with the same tuples/lists, proving the boundary is ordinary BEAM interoperability.

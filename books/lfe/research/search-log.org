** 2026-09-16 -- LFE macro expansion and hygiene
Question: What does current pinned LFE actually promise about macro expansion and hygiene?
Sources inspected: tagged =doc/src/lfe_guide.7.md= and =doc/src/lfe_macro.3.md= at LFE v2.2.2.
Result: macros run at expansion time with access to the current macro environment. The guide explicitly states that LFE macros are not hygienic. =lfe_macro= distinguishes one top-level expansion attempt, repeated top-level expansion, and recursive all-expression expansion. For Project 1's module-qualified exported macro, the acceptance contract is the documented repeated top-level =expand_expr/2= path used by LFE's own exported-macro regression; =expand_expr_1/2= only performs the first normalization step and is not the DSL expansion oracle.
Remaining uncertainty: no production macro in the current project needs to introduce bindings; if a later macro does, its generated-name policy and capture tests require a fresh design/test slice.

** 2026-09-16 -- correlation, selective receive, timeout, ordering, and monitors
Question: Which process/message claims can Chapters 8--10 make from current official Erlang documentation, and which require executable evidence?
Sources inspected: Erlang System Documentation v29.0.6 process reference and the official process Efficiency Guide.
Result: sends are asynchronous signals; =receive= selects the first matching queued message; signal ordering is guaranteed from one sender to one destination rather than globally across independent senders; selective receive can scan queued messages; monitors are unidirectional and deliver a correlated =DOWN= message; a local receive timeout does not itself specify remote cancellation or target death. Project 2 can turn these documented boundaries into focused regressions without claiming performance numbers.
Remaining uncertainty: aliases, priority-message APIs, links/=trap_exit=, and supervision are deliberately deferred until their owning slices are designed and tested.

** 2026-09-16 -- supervision strategy, restart intensity, and state recovery boundary
Question: What can the first LFE supervision checkpoint claim about restart behavior without conflating process replacement with persistence?
Sources inspected: Erlang/OTP 29.0.6 =supervisor= STDLIB documentation and Supervisor Behaviour design-principles chapter.
Result: =one_for_one= restarts only the affected child; child specs define a start MFA and restart policy; more than =intensity= restarts in =period= seconds causes supervisor shutdown. A replacement is started from the child spec; supervisor semantics do not restore arbitrary volatile callback state.
Remaining uncertainty: persistence/replay semantics, multi-child strategy choice, application trees, release handling, distribution, and production observability need separate slices and tests.

* DOCUMENTED -- what a macro is in LFE
The tagged v2.2.2 user guide defines macros as compile-time functions receiving the macro-call arguments and the current macro environment. It documents =defmacro=, local =macrolet=, automatic =$ENV= availability inside =defmacro=/=macrolet= expansions, =eval-when-compile= helpers, backquote/unquote, and exported macros. The guide is explicit that LFE macros are *not hygienic*.

Source: https://github.com/lfe/lfe/blob/v2.2.2/doc/src/lfe_guide.7.md
Relevant section: =Macros=.

Teaching consequence: the book must not imply Scheme-style hygiene. Production macros should minimize introduced bindings and test their expansion shape; capture must be demonstrated deliberately so readers can recognize it.

* DOCUMENTED -- macro-expansion API
The tagged =lfe_macro= manual documents these distinctions:
- =expand_expr_1/2= tries one top-level macro expansion;
- =expand_expr/2= repeatedly expands the top expression while it remains a macro call;
- =expand_expr_all/2= recursively expands macro calls throughout an expression.

Source: https://github.com/lfe/lfe/blob/v2.2.2/doc/src/lfe_macro.3.md

The tagged upstream exported-macro regression uses =lfe_macro:expand_expr/2= for module-qualified macro calls such as =core-macros:caar=. Project 1 mirrors that acceptance boundary for =event-rules-dsl:routes=. An observed failed regression on 2026-09-16 also established a useful implementation detail: =expand_expr_1/2= stopped after normalizing the module-qualified call into its =:= form, so treating that first step as the exported macro's expansion was incorrect. The project therefore uses =expand_expr/2= to reach the exported macro while still comparing the resulting top-level expansion against an exact explicit rule form. It does not use =expand_expr_all/2=, which would recursively expand nested forms and widen the regression surface.

* DESIGN USED BY THIS SLICE -- macro surface remains a source layer
Project 1's semantic kernel remains ordinary BEAM data interpreted by =event-rules:route/2=. The first macro surface is:

#+begin_src lfe
(event-rules-dsl:routes
 (when-level 'critical 'pager)
 (when-service 'billing 'billing-queue)
 (otherwise 'archive))
#+end_src

The macro expands to the same explicit list of =when-level=/=when-service=/=otherwise= tuples used by the already-tested data-first kernel. It does not add a second evaluator, process, registry, or hidden mutable runtime.

The macro performs structural syntax validation at expansion time. An unsupported clause is rejected with =bad-event-rule-syntax= rather than compiling into an opaque runtime failure.

* Capture experiment
LFE v2.2.2 documentation says macros are non-hygienic and identifies same-named macro-generated variables as the practical capture hazard. This slice includes a deliberately unsafe teaching macro that introduces =value=, while the caller also references =value=. The expected result is capture of the caller reference by the macro-introduced binding.

This experiment is pedagogical evidence, not a recommendation. The production =routes= macro introduces no bindings at all, avoiding that capture class by construction.

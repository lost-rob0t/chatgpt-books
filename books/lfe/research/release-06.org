* Primary-source findings
** An OTP application is an ownership/lifecycle component, not a synonym for a module
The =application= behaviour describes a component that can be started and stopped as a unit. When an application is structured as a supervision tree, its =start/2= callback starts the top supervisor and returns its PID. The application controller creates an application master and invokes the configured callback module from the application's resource metadata. [cite:@erlang-application-29]

For this project that means the LFE callback should not reimplement the routing service or supervision policy. Its only substantive startup action is delegating to =otp-router-sup:start_link/1=. The existing supervisor remains the owner of worker lifecycle policy, and the existing =otp-router= callback remains the owner of service semantics.

** The .app file is executable metadata
The official =app= format requires one application resource file named after the application and located in its =ebin= directory. The resource identifies application version, modules, registered names, dependencies, and the optional =mod= callback used to start the application. The application controller reads this file at load/start time, and =systools= reads it while constructing releases. [cite:@erlang-app-resource-29]

This gives the book a useful boundary: the Lisp source can compile correctly while the system description is still wrong. A missing dependency, wrong application version, or incomplete module list belongs to the packaging contract rather than to the routing algorithm.

** A release composes applications plus one ERTS version
Official release documentation defines a release as a complete system described by a =.rel= resource containing a release name/version, the ERTS version, and exact application versions. Kernel and STDLIB must be included. [cite:@erlang-release-structure-29;@erlang-rel-29]

This is a stronger claim than “my app starts in a developer shell.” The release declaration says which component versions constitute the system.

** systools validates the release/application closure before emitting boot artifacts
=systools:make_script/2= reads the release and application resources and validates their relationship before generating a human-readable =.script= and binary =.boot=. A =local= script embeds the actual application directories and is explicitly useful for local testing. A non-local script is suitable for building a relocatable release package layout. =systools:make_tar/2= packages the applications and release artifacts. [cite:@erlang-systools-29;@erlang-release-structure-29]

The Project 3 lab therefore needs both positive and negative evidence:
- construct a valid release from the current runtime's actual ERTS/Kernel/STDLIB versions;
- boot a *fresh* VM from the generated boot file;
- prove the expected OTP application owns the same supervisor/worker tree used in earlier chapters;
- corrupt the application version in =.rel= and require construction failure;
- inject an undeclared release dependency into =.app= and require construction failure;
- produce and inspect a release package without claiming this proves deployment to another machine.

** Negative tests need semantic error categories, not any error tuple
Self-review found that the first version of both failure labs accepted any ={error,_,_}= result. That was too weak: a typo, path problem, or unrelated release error could make the lesson appear green.

The official tagged OTP 29.1 =systools_make= implementation represents an unavailable application version under an =error_reading= entry with =no_valid_version=, and the tagged OTP 29.1 =systools_SUITE= regression suite pattern-matches that category. The same implementation category was also checked in OTP 25.3.2.8, matching the older runtime lineage used by the focused runner. A release dependency absent from the closure is represented as ={undefined_applications, Apps}=. [cite:@erlang-systools-make-source-29;@erlang-systools-suite-29]

The executable oracle therefore requires:
- the injected =otp_router= version mismatch to contain ={error_reading,{otp_router,{no_valid_version,_}}}= inside the =systools_make= error list;
- the missing-dependency case to return ={undefined_applications, Apps}= with =crypto= present.

Human-formatted =format_error/1= text is deliberately not part of the contract. The stable semantic category and subject are.

* LFE-specific boundary
LFE source does not create a second application model. The callback module is compiled to ordinary BEAM code and declares the standard OTP =application= behaviour in the same style that earlier chapters used =gen_server= and =supervisor=. The executable proof is more important than a language-specific recipe: Erlang's application controller loads the generated =otp_router.app=, invokes the compiled LFE callback, and later a fresh =erl -boot= runtime starts the same application from generated release artifacts.

* Failure semantics to teach
1. *Source success, metadata failure.* BEAM files can exist while =.app= or =.rel= is inconsistent. Packaging failures are not compiler failures.
2. *Application identity is not PID identity.* Starting an application creates an owned supervision tree; worker PIDs may change under supervision without changing application identity.
3. *A local boot script is intentionally host/build-path specific.* Passing =erl -boot= against a =local= script proves construction and startup on the tested environment, not portability.
4. *A release package is not a deployment result.* Seeing expected files in =make_tar/2= output proves package construction only.
5. *Version closure is deliberate.* The lab discovers ERTS/Kernel/STDLIB versions from the runtime rather than hard-coding the documentation baseline into an OTP-25 CI runner.
6. *A negative test must fail for the intended reason.* Accepting any error tuple is a false-green risk; the oracle names the semantic category and, where available, the affected application.

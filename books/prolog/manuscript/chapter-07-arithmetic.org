* Chapter 7 -- Arithmetic: Evaluation Is an Operation, Not Assignment

Project 1 can already prove paths through the synthetic =follows/2= graph. We can ask for every simple path from Ada to Ben, inspect the list of nodes, and deliberately commit to the first path when an interface truly wants that policy.

Now the project needs a numeric question:

/How many hops does this already-proved path contain?/

That sounds tiny. It exposes one of the most important boundaries in ordinary Prolog arithmetic: a term that /looks/ like an arithmetic expression is still only a term until an arithmetic predicate evaluates it.

Consider the two goals:

#+begin_src prolog
X = 1 + 2.
X is 1 + 2.
#+end_src

They are not two spellings of assignment. The first uses unification. It can bind =X= to the compound term =1 + 2= without performing addition. The second asks Prolog to evaluate the arithmetic expression on the right and then unify =X= with the resulting number. Current SWI-Prolog documents =is/2= exactly as arithmetic evaluation followed by unification [cite:@swi-arithmetic].

That difference is the point of this chapter. Arithmetic introduces an operational precondition that our earlier relations often avoided: the expression being evaluated must already contain enough numeric information to compute a value.

** 7.1 Start from data, then ask for a number
One Project 1 proof is represented by a list such as:

#+begin_src prolog
[ada, lina, ben]
#+end_src

A path with three nodes contains two edges. We could reach immediately for a library length predicate and subtract one. Instead we will derive the count recursively because the mechanism gives us a clean place to see arithmetic evaluation happen.

The base case is a one-node path:

#+begin_src prolog
path_hops([_], 0).
#+end_src

There are no edges left to traverse, so the hop count is zero.

For a longer path, count the tail first:

#+begin_src prolog
path_hops([_|Tail], Hops) :-
    Tail = [_|_],
    path_hops(Tail, TailHops),
    Hops is TailHops + 1.
#+end_src

The apparently boring goal order is doing real work. When the recursive call succeeds, =TailHops= is already numeric in the supported mode. Only then does =is/2= evaluate =TailHops + 1=.

For =[ada,lina,ben]=, the derivation is:

#+begin_example
path_hops([ada,lina,ben], H)
  -> path_hops([lina,ben], H1)
       -> path_hops([ben], 0)
       -> H1 is 0 + 1
  -> H is 1 + 1
#+end_example

The final numeric result follows from the two evaluation steps. No mutable counter is being incremented. Each recursive branch obtains a numeric value and passes that value outward through unification.

** 7.2 =1 + 2= is a term until somebody evaluates it
This is easiest to understand by separating syntax from interpretation.

The source text =1 + 2= is parsed using the infix =+/2= operator syntax. Structurally, it denotes the same kind of compound term we could write in prefix form as =+(1,2)=. Unification is about term structure. It does not automatically decide that every term with functor =+/2= must be computed.

So:

#+begin_src prolog
X = 1 + 2
#+end_src

asks whether =X= and the expression term can be made identical. An unbound =X= can simply become that term.

By contrast:

#+begin_src prolog
X is 1 + 2
#+end_src

puts the right-hand term in an arithmetic-evaluation context. SWI evaluates supported arithmetic functions recursively, obtains a number, and then unifies the left argument with that value [cite:@swi-arithmetic].

This gives us a useful debugging question whenever arithmetic surprises us:

/Am I manipulating the expression as data, or asking an arithmetic predicate to evaluate it?/

That question becomes even more important later when we manipulate syntax trees and generated terms. A term does not execute merely because its functor resembles an operator.

** 7.3 Why =is/2= is not assignment
In an imperative language, an assignment such as =x = y + 1= usually means “read the current value of =y=, compute a result, and mutate storage named =x=.”

That is a bad mental model for:

#+begin_src prolog
Hops is TailHops + 1
#+end_src

There is no update to an old value of =Hops=. The right side is evaluated, then normal Prolog unification applies to the left side.

This matters when the left side is already bound. Suppose a calculation produces integer =3=. Then =3 is 1 + 2= can succeed because the evaluated result unifies with =3=. A left side that cannot unify with the evaluated numeric term makes the goal fail.

The current SWI manual uses a sharper example: =1 is sin(pi/2)= fails because the expression evaluates to floating-point =1.0=, which does not unify with the integer term =1=; arithmetic equality =1 =:= sin(pi/2)= succeeds because it compares numeric values instead [cite:@swi-arithmetic].

The lesson is not about sine. It is that *evaluation plus unification* and *numeric comparison* are different contracts.

** 7.4 Three equal-looking questions that are not equal
By Chapter 7 you need to distinguish at least these operations:

| Question | Predicate/operator | What it asks |
|-
| Can these two terms be made the same? | =/2= | term unification; no implicit arithmetic evaluation |
| What number does this expression evaluate to? | =is/2= | evaluate the right expression, then unify the result with the left |
| Do these arithmetic expressions have equal numeric values? | ==:=/2= | evaluate both arithmetic expressions and compare numerically |

For example, =1 + 2= and =3= do not have the same term structure. They can nevertheless have equal arithmetic values when both are placed in an arithmetic comparison.

Current SWI-Prolog documents ==:=/2= and the ordering predicates =</2=, =</2=, =< /2=, =>/2=, and =>=/2= as arithmetic predicates over evaluated expressions [cite:@swi-arithmetic]. In ordinary code, choose an operator because its contract matches the question; do not pick whichever symbol looks most familiar from another language.

*** Numeric equality is not term identity
Numbers have types and representations. Integer =1= and float =1.0= need not be the same Prolog term even though arithmetic comparison considers them numerically equal. That is why an arithmetic test should use arithmetic comparison rather than accidentally relying on term unification.

The project stays on integer hop counts, so we do not need a floating-point policy yet. The distinction still matters because it prevents a very common beginner error from hardening into an API design habit.

** 7.5 Calling modes become part of the arithmetic contract
Our earlier =project_peer/3= relation can usefully answer several different directions of question. Low-level arithmetic is less forgiving.

The supported teaching mode for the new counter is:

#+begin_example
path_hops(+Path, -Hops)
#+end_example

Here =+= means “expected sufficiently instantiated at call time” and =-= means “normally produced by the call.” These symbols are documentation conventions, not Prolog syntax.

Why require the path first? Look at the last goal:

#+begin_src prolog
Hops is TailHops + 1
#+end_src

The expression on the right cannot be evaluated if =TailHops= is still an unconstrained logical variable. The official SWI CLP(FD) documentation deliberately contrasts this behavior with relational integer constraints: =3 is Y+2= and =3 =:= Y+2= require enough instantiation to evaluate =Y+2=, while a later finite-domain constraint such as =3 #= Y+2= can constrain =Y= relationally [cite:@swi-clpfd-arithmetic].

Do not draw the wrong conclusion. “=is/2= does not solve this equation backwards” is accurate. “Prolog cannot do relational arithmetic” is not. Chapters 15--16 will introduce the constraint tools designed for that job.

** 7.6 Failure lab -- move evaluation before the value exists
Make a temporary scratch predicate with the goals reversed:

#+begin_src prolog
broken_path_hops([_|Tail], Hops) :-
    Hops is TailHops + 1,
    broken_path_hops(Tail, TailHops).
#+end_src

In the intended forward mode, the first goal asks for arithmetic evaluation before recursion has produced =TailHops=. Current SWI reports insufficient instantiation for this class of low-level arithmetic call [cite:@swi-clpfd-arithmetic].

The repair is not “catch the error and keep going.” The repair is to restore the data dependency: obtain the tail count first, then evaluate the expression that consumes it.

This is a tiny example of a general debugging technique:
1. identify every variable needed by an operational primitive;
2. identify which earlier goal is supposed to instantiate it;
3. check whether goal order makes that guarantee true in the supported mode.

Later constraint programming changes the available contracts, but it does not make mode reasoning obsolete.

** 7.7 Attach the number to the existing relation
We do not replace =connection_path/3=. We compose with it:

#+begin_src prolog
connection_with_hops(Start, Goal, Path, Hops) :-
    connection_path(Start, Goal, Path),
    path_hops(Path, Hops).
#+end_src

Read this left to right operationally in the supported mode:
1. enumerate one existing simple path proof;
2. count the edges in that path;
3. return the path and its derived count together.

Declaratively, the new relation states that =Path= is a connection path from =Start= to =Goal= and =Hops= is the hop count for that path.

Most importantly, it keeps backtracking alive. If =connection_path/3= has three proofs, the wrapper can produce three path/count pairs. Arithmetic did not justify slipping =once/1= into the relation.

*** This is not shortest-path search
A common accidental overclaim would be:

#+begin_quote
Now that every path has a hop count, the system finds the shortest route.
#+end_quote

No. We have only annotated each path after the existing depth-first relation produces it. The first path still depends on the underlying search order. A caller could collect all finite results and compare them, but even that would be a different algorithmic contract with different assumptions. The dedicated search/planning project later in the book owns explicit search strategy and optimality claims.

Chapter 7 claims exactly what the code implements: *derive and filter a numeric property of already-proven paths*.

** 7.8 Arithmetic comparisons are filters, not generators
Now add a ground maximum-hop policy:

#+begin_src prolog
connection_within_hops(Start, Goal, Limit, Path, Hops) :-
    connection_with_hops(Start, Goal, Path, Hops),
    Hops =< Limit.
#+end_src

The first goal proves a path and computes a numeric hop count. The second evaluates both arithmetic operands and succeeds only when the comparison is true [cite:@swi-arithmetic].

The supported teaching mode is:

#+begin_example
connection_within_hops(+Start, +Goal, +Limit, -Path, -Hops)
#+end_example

=Limit= is expected to be numeric already. The comparison does not create candidate hop counts or constrain an unknown limit. It filters answers that already have numbers.

For the current synthetic fixture, the regression suite asserts the complete expected Ada-to-Ben answer set at a two-hop limit. The test is important because a single successful path would not prove that filtering preserved every qualifying alternative.

** 7.9 Work the project case by hand before trusting the test
The accepted Chapter 6 relation has these Ada-to-Ben simple paths:

#+begin_src prolog
[ada, lina, ben]
[ada, lina, noor, ben]
[ada, noor, ben]
#+end_src

Count edges, not nodes:

| Path | Nodes | Hops |
|-
| =[ada,lina,ben]= | 3 | 2 |
| =[ada,lina,noor,ben]= | 4 | 3 |
| =[ada,noor,ben]= | 3 | 2 |

A hop limit of =2= should therefore preserve the first and third paths and reject the middle one. This is a hand-derived fixture expectation. The repository test must still execute before we label the implementation TESTED.

That last sentence is part of the book's engineering discipline: a derivation tells us what the expected result is; the regression tells us whether the implementation on the recorded runtime actually satisfies it.

** 7.10 Arithmetic expressions have failure modes too
Arithmetic code can fail, throw, or succeed with a number depending on the expression and inputs. Chapter 7 keeps the surface deliberately small, but you should already distinguish several categories:

- *logical comparison failure*: both operands evaluate, but =Hops =< Limit= is false;
- *insufficient instantiation*: an arithmetic expression contains a variable whose numeric value is not yet known;
- *type/domain errors*: an arithmetic operation receives a term outside the operation's contract;
- *ordinary unification failure after evaluation*: =is/2= computes a numeric term that cannot unify with an already-bound left argument.

Do not turn all four into “math failed.” Different failure classes imply different bugs and different caller contracts.

The Project 1 test suite deliberately includes an insufficient-instantiation regression for low-level arithmetic. It is a semantic guard, not a benchmark and not a recommendation to use exceptions as ordinary control flow.

** 7.11 A small SWI-specific relational contrast
Current SWI also documents special-purpose integer predicates such as =plus/3= and =succ/2= that have more relational calling modes than ordinary =is/2= [cite:@swi-arithmetic]. They are useful reminders that arithmetic interfaces can have different mode contracts even before constraint programming enters the picture.

We do not rewrite Project 1 around them. The point of this chapter is to understand ordinary expression evaluation because you will encounter it everywhere, including inside otherwise relational programs. The more general integer-constraint story deserves its own project and is intentionally deferred.

** 7.12 Failure lab -- three arithmetic confusions
Work in a scratch REPL and predict each outcome before running it.

*** Confusion A: expression data versus evaluated value
Compare:

#+begin_src prolog
X = 2 + 3.
X is 2 + 3.
#+end_src

Explain the first answer as a term binding and the second as evaluation followed by unification.

*** Confusion B: numeric equality versus unification
Compare a pair of numeric terms that differ in representation, such as integer =1= and floating =1.0=. Ask separately whether they unify and whether they are arithmetically equal. Tie your explanation to the official =is/2= versus ==:=/2= distinction rather than memorizing one output.

*** Confusion C: trying to run arithmetic backwards
Start with an unknown right-side operand:

#+begin_src prolog
3 is Y + 2.
#+end_src

Explain why low-level evaluation cannot obtain =Y= from that call. Then read the later CLP(FD) form in the official documentation, but do not replace Chapter 7 project code with constraints yet [cite:@swi-clpfd-arithmetic].

** 7.13 Project 1 milestone 3 contract
After Chapter 7, Project 1 adds a narrow numeric layer without changing the meaning of its accepted relations:

- =connection_path/3= remains the source of path proofs and remains multi-answer;
- =path_hops/2= counts edges for finite proper non-empty path lists in the documented forward mode;
- =connection_with_hops/4= attaches the derived count to every path proof;
- =connection_within_hops/5= applies a ground numeric filter after proof and counting;
- the new PL-Unit suite checks exact counts, the complete path/count answer set, the complete within-limit answer set, an over-tight limit, and the low-level arithmetic instantiation boundary;
- no cut, negation, module restructuring, DCG, CLP(FD), shortest-path search, benchmark, or performance claim enters through this milestone.

Run the full Project 1 suite from the repository root:

#+begin_src sh
bash books/prolog/code/run-tests
#+end_src

The runner now requires all three named test units before executing them. If the Chapter 7 suite fails to load, the runner exits as an error instead of allowing an accidentally smaller test set to look green.

** 7.15 What comes next
Arithmetic gave us our first deliberately directional operational primitive. That makes Chapter 8's control discussion more interesting: once goal order and modes affect whether a computation can proceed, it becomes tempting to use cut to silence unwanted alternatives or patch over poor interfaces.

We will not do that blindly. The next chapter studies cut only after the relation, alternatives, and caller policy are explicit. Later still, constraint chapters revisit arithmetic with tools that recover relational integer reasoning where ordinary =is/2= is the wrong contract.

** 2026-09-16 -- failure-semantics pass 02: links, exits, monitors, and teardown races
- Questions :: Which failures propagate through a link? What changes when =trap_exit= is enabled? How do monitor and link semantics differ? What does =unlink/1= guarantee after returning? How should a caller tear down a monitor without leaving a stale =DOWN= message? Is =kill= trappable in current OTP, and which API should new OTP 29 code use to send an exit signal?
- Queries :: Official Erlang/OTP 29.0.6 Processes reference; OTP 29.0.6 =erlang= BIF reference for =unlink/1=, =demonitor/2=, =monitor/2=, =process_flag(trap_exit,...)=, and =exit_signal/2=; OTP 29.0.6 patch package for current patch confirmation.
- Sources inspected :: See [[file:sources.org][sources.org]], failure-semantics pass 02.
- Result :: Links are bidirectional and a terminating participant emits an exit signal to the other participant. A non-trapping receiver is terminated by an active linked exit whose reason is not =normal=; a linked =normal= exit is ordinarily dropped for a non-trapping receiver. A trapping receiver gets eligible active linked exits as ={'EXIT', Sender, Reason}= messages. Monitors are one-way, separately identified observations and emit a correlated =DOWN= when the monitored process terminates; monitoring a nonexistent process yields =noproc=. After =unlink(Pid)= returns, the removed link has no future effect on the caller unless a link is established again, but a trapped =EXIT= may already be queued. =demonitor(Ref, [flush])= removes the monitor and flushes one already-queued matching =DOWN= when present. OTP 29.0.6 documents =erlang:exit_signal/2= as introduced in OTP 29.0 and recommends it for new exit-signal code; an explicit signal with reason =kill= is untrappable and kills the target with reason =killed=.
- Claim classification :: DOCUMENTED from current official sources. EXECUTION VERIFIED for the merged Project 1 checkpoint B; exact run evidence is in =STATUS.org= and PR #40.
- Important boundary :: Trapping exits changes signal handling, not ownership or restart policy. Monitors observe failure but do not restart a process.

** 2026-09-16 -- OTP pass 03: =gen_server= and supervisor ownership contracts
- Questions :: What does an OTP behaviour standardize without changing raw process semantics? Which callbacks correspond to =start=, =call=, =cast=, stop, and ordinary messages? What exactly happens to a timed-out =gen_server:call= on modern OTP? What does =start_link= establish for supervision? - Queries :: Official Erlang/OTP downloads/29.0.6 patch metadata; official =erlang/otp= source at immutable tag =OTP-29.0.6= for =system/doc/design_principles/design_principles.md=, =lib/stdlib/src/gen_server.erl=, and =lib/stdlib/src/supervisor.erl=; current erlang.org gen_server/supervisor pages used only to locate concepts and cross-check source-tag behavior.
- Sources inspected :: See [[file:sources.org][sources.org]], OTP pass 03.
- Result :: OTP behaviours separate generic process machinery from application callbacks. =gen_server:call= maps to =handle_call/3= and exits the caller on timeout; timeout does not cancel callback execution. Starting with OTP 24, call uses process aliases so a late reply after an abandoned timeout is not delivered to the caller mailbox. =cast= maps to =handle_cast/2= and has no reply contract. =gen_server= participates in standard =sys= system-message/debugging support. A supervisor owns children through child specs; =permanent=/=transient=/=temporary= answer when a child qualifies for restart, while =one_for_one=/=one_for_all=/=rest_for_one= answer which children are affected. More than =intensity= restarts within =period= seconds causes the supervisor to terminate its child set and then itself with reason =shutdown=. Restart constructs a replacement process; prior process-local state only returns if initialization/recovery code reconstructs it from some external source.
- Version-sensitive finding :: Official downloads identified 29.0.6 as the latest released OTP, but the unversioned stdlib documentation route rendered 29.1/stdlib 8.1 during this run. Exact claims therefore cite the official immutable =OTP-29.0.6= tag instead of treating the drifting =/doc/= route as an exact-version artifact.

** 2026-09-16 -- application pass 04: OTP 29.1 application lifecycle and resource contract
- Questions :: What makes a supervision tree an OTP application? What does the application controller own? What does the application master do? What is the exact =.app= resource contract? - Sources inspected :: See [[file:sources.org][sources.org]], application pass 04.
- Result :: The official immutable =OTP-29.1= tag identifies the current researched runtime as 29.1. An OTP application is a component that can be loaded, started, stopped, and reused as a unit. The application controller coordinates lifecycle operations; a started supervision-tree application gets an application master, which invokes the callback module named by =mod= and tracks application process ownership. The callback =start/2= normally starts the top supervisor; =stop/1= runs after the process tree has been stopped. The =Application.app= resource is a single Erlang application-specification term in =ebin=. Loading stores specification metadata but does not load object code. =application:start/1= requires declared prerequisite applications to be running; =ensure_all_started/1,2,3= can start the dependency set. A =.app= resource defines a component, not a full release or persistence mechanism.

- Sources inspected :: See [[file:sources.org][sources.org]], release pass 05.
- Result :: A release composes exact ERTS and application versions into a bootable system; Kernel and STDLIB are mandatory. =systools:make_script/2= reads =.rel= and =.app= resources, rejects version disagreement and undefined/circular dependency or duplicate-module conditions, and emits human-readable =.script= plus binary =.boot=. Option =local= retains the actual discovered application directories and is documented for local boot-script testing; without it, generated paths use installation-relative =$ROOT/lib/App-Vsn/ebin= structure. =systools:make_tar/2= packages validated application/release artifacts into release/target-system layout. SASL is required for upgrade-capable releases, but runtime upgrade work is outside this slice.

** 2026-09-16 -- Project 3 pass 06: bounded work, dynamic children, and retry ownership
- Questions :: How are dynamic children added to an ordinary OTP supervisor? What does =restart => temporary= guarantee after termination? Which layer should own logical retry after a worker crash? What FIFO and complexity properties does STDLIB =queue= document? Which monitor facts are runtime contracts? What exactly survives when supervision replaces the queue process?
- Queries :: Official =erlang/otp= source at immutable tag =OTP-29.1=: =lib/stdlib/src/supervisor.erl=, =lib/stdlib/src/queue.erl=, and =system/doc/reference_manual/ref_man_processes.md=.
- Sources inspected :: See [[file:sources.org][sources.org]], Project 3 pass 06, and [[file:job-processor-pass-06.org][job-processor-pass-06.org]].
- Result :: Ordinary supervisors can start dynamic children from explicit child specs. A =temporary= child is not restarted and its child specification is automatically removed after termination. STDLIB =queue= provides FIFO semantics; its =len/1= is O(n), so the course implementation tracks pending length separately. A monitor correlates termination of one worker attempt but says nothing about whether replaying the logical job is safe. The course therefore gives =job_processor= ownership of job identity/retry policy and gives =job_worker_sup= only process-lifecycle ownership. Killing =job_processor= demonstrates that supervision restores that process role but not its volatile accepted-work ledger.

* Primary sources inspected
** =supervisor= at immutable tag =OTP-29.1=
URL: https://github.com/erlang/otp/blob/OTP-29.1/lib/stdlib/src/supervisor.erl

The module documentation says supervisors own child startup, shutdown, monitoring, restart
strategy, and restart intensity. For ordinary =one_for_one=, =one_for_all=, and
=rest_for_one= supervisors, =supervisor:start_child/2= dynamically adds a supplied child
specification and starts the corresponding process. A =temporary= child is never restarted;
when such a child terminates, its child specification is automatically deleted. The child
=start= function must create and link the child to the supervisor. These facts justify the
Project 3 dynamic-worker mechanism, but they do not define job retry semantics.

Claim status: DOCUMENTED.

** =queue= at immutable tag =OTP-29.1=
URL: https://github.com/erlang/otp/blob/OTP-29.1/lib/stdlib/src/queue.erl

STDLIB documents =queue= as an opaque double-ended FIFO queue. Its front contains the item
that has waited the longest; =queue:in/2= and =queue:out/1= therefore provide the pending
work ordering used by the project. The module documentation explicitly states that
=queue:len/1= is O(n) because the representation does not store length and notes that a caller
can track length itself when that operation needs to be cheap. Project 3 follows that advice
with a separate =pending_len= state field because capacity checking is on every submission.

Claim status: DOCUMENTED. No throughput claim is made.

** Processes reference manual at immutable tag =OTP-29.1=
URL: https://github.com/erlang/otp/blob/OTP-29.1/system/doc/reference_manual/ref_man_processes.md

The reference distinguishes asynchronous signal reception from =receive= execution. A monitor
establishes a one-way observation relationship; when the monitored process terminates, the
corresponding =down= signal is converted to a message while the monitor remains active. The
manual also preserves the signal-ordering/message-queue distinction and the OTP 28+
priority-message caveat already introduced in the foundation chapters.

Project 3 uses a monitor reference to correlate one worker PID with one active job attempt.
The monitor reports process termination. It does not say whether retrying the logical job is
safe; that decision belongs to the project protocol.

Claim status: DOCUMENTED.

* Derived design boundary
The project intentionally uses two different failure mechanisms:

1. =job_worker_sup= owns temporary worker process lifetime. It can start a dynamic child and
   tear the subtree down, but it never retries a temporary child.
2. =job_processor= owns logical job identity and a bounded attempt count. A worker =DOWN=
   can therefore cause a new /attempt/ of the same logical job without pretending that generic
   supervisor restart policy understands idempotency or external side effects.

This is a course design built from OTP mechanisms, not an OTP-prescribed scheduler.

* Recovery experiment
The top supervisor keeps =job_worker_sup= and =job_processor= as =one_for_one= siblings. The
failure lab starts a gated worker, kills the queue/admission process, observes the supervisor
replace that process, and then releases the already-running worker. The replacement queue has
fresh in-memory state and therefore cannot deliver the old job result.

Focused run =35154089887= executed this bounded job-processor suite successfully on implementation
head =fd8f9489cfcb53f2adda755654dc2a8f8e7058e9=. That establishes only this bounded statement:
/supervision restored the queue process role but did not reconstruct its volatile accepted-work
ledger/. Durable recovery, replay, exactly-once effects, and distributed failover remain
separate later mechanisms.

Claim status: TESTED for the bounded local experiment.

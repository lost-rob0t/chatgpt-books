** Chapter 9 -- Failure Semantics: Exit Signals Are a Protocol
:PROPERTIES:
:ID:       e9b5401a-7abc-45a0-a8a5-677dc90f98ef
:END:

By now we have three separate mechanisms in view:

- process termination has a reason;
- links can propagate that termination as an exit signal;
- monitors can report a termination as a correlated =DOWN= message.

The final missing piece before OTP is how a receiving process treats an exit signal.
Erlang's answer is not "crash or don't crash." It is a small protocol whose outcome depends
on the signal and receiver state.

Current OTP documents the decision in terms of the receiver's =trap_exit= flag, the exit
reason, the sender, whether the signal was generated by a link, and--for a link-generated
signal--whether that link is still active when the signal is received. Depending on those
facts, the signal is dropped, terminates the receiver, or is converted into a message.
[cite:@erlang-processes]

*** Default behavior first

Most application processes should begin with the default: they do not trap exits. The OTP
BIF reference explicitly notes that application processes normally are not to trap exits.
[cite:@erlang-bifs]

For our local linked-worker case, the useful beginner model is:

| Incoming linked exit | Non-trapping receiver |
|-
| =normal= | ordinarily dropped |
| abnormal reason such as =boom= | receiver terminates with that reason |

That behavior is powerful because a process can choose a shared-fate relationship without
writing a receive clause for every failure. If a worker and controller truly form one
failure unit, the runtime can carry the failure across the link.

But sometimes one process needs to /handle/ a linked process's exit instead of dying with
it. That is where trapping exits enters.

*** =trap_exit= turns eligible signals into messages

A process can set:

#+begin_src erlang
process_flag(trap_exit, true)
#+end_src

When eligible exit signals arrive, they are converted into messages of the form:

#+begin_src erlang
{'EXIT', From, Reason}
#+end_src

and can be handled by normal receive logic. [cite:@erlang-processes;@erlang-bifs]

Project 1's failure lab demonstrates the transition explicitly:

#+begin_src erlang
process_flag(trap_exit, true),
Worker = spawn_link(fun worker/0),
Worker ! {crash, boom},
receive
    {'EXIT', Worker, boom} ->
        handled
end
#+end_src

The worker is still dead. The link still reported its exit. What changed is the receiving
controller's response to that signal.

This is why "trap exits to make a process fault tolerant" is bad advice. Trapping exits
only hands the application a message. The application must still decide whether to stop,
restart something, degrade service, record evidence, or ignore the event. That policy is
the hard part.

*** A trapper is not a supervisor

Consider this tempting loop:

#+begin_src erlang
receive
    {'EXIT', Worker, Reason} ->
        NewWorker = spawn_link(fun worker/0),
        loop(NewWorker)
end
#+end_src

It looks like a tiny supervisor. It also leaves unanswered questions that production
supervision cannot dodge:

- What if the replacement crashes immediately?
- How many restarts are allowed before the subsystem should fail?
- Which siblings should be restarted together?
- In what order should children start and stop?
- How does shutdown differ from a crash?
- Who owns child specifications and initialization data?
- What should happen to requests that were in flight when the old worker died?

OTP supervisors exist because these are recurring operational policies, not because
=spawn_link= or =trap_exit= is difficult to type. Chapter 12 will let OTP own that policy.
This chapter's goal is to understand the raw signals well enough to read a supervision tree
without magical thinking.

*** =kill= is deliberately different

OTP 29 introduced =erlang:exit_signal/2= as the direct API for sending an exit signal and
recommends it for new code in place of the older two-argument =exit/2= form. With most
reasons, a trapping target can receive the signal as an =EXIT= message. An explicit exit
signal whose reason is =kill= is different: it is untrappable, and the target terminates
with reason =killed=. [cite:@erlang-bifs]

The failure lab tests that boundary using a process that has already enabled =trap_exit=:

#+begin_src erlang
erlang:exit_signal(Trapper, kill)
#+end_src

An external monitor observes the target terminating with =killed=. The test does not infer
this from a timeout; it waits for the correlated =DOWN=.

There is a subtle but important distinction here. A process that calls =exit(kill)= on
/itself/ raises an exit exception with reason =kill=. That is not the same operation as one
process sending an explicit =kill= exit signal to another process. The current BIF
reference calls out this distinction directly. [cite:@erlang-bifs]

For new code in this book, we use =exit/1= when a process intends to terminate itself and
=exit_signal/2= when a process intentionally sends an exit signal to another process.

*** Failure propagation is graph behavior

Once links form a graph, one abnormal termination can cause another process to terminate,
which emits exit signals to /its/ links, and so on. This is not a broadcast primitive. It
is local behavior repeated along active relationships.

That gives us a better way to reason about a crash cascade:

#+begin_example
worker --link-- controller --link-- peer
   X boom       receives boom
                -> terminates boom
                -> peer receives boom
#+end_example

Change the controller to trap exits and the graph behavior changes at that vertex: the
worker's signal becomes an =EXIT= message instead of automatically terminating the
controller. Whether propagation continues now depends on the controller's application
policy.

This graph view scales better than memorizing slogans. In later supervision chapters, each
supervisor/child link participates in a graph, but OTP adds disciplined ownership and
restart policy on top.

*** State dies with the process

Project 1 stores topic history inside =pmsg_server='s process state. If that process dies,
the map dies with it.

A link does not preserve that state. A monitor does not preserve it. Trapping exits does
not preserve it. Starting a replacement process does not preserve it unless some separate
recovery source exists.

This is the boundary between *failure handling* and *persistence*. We can recover
/availability/ by starting a process. Recovering /state/ requires a different contract:
reconstruct from durable storage, replay a log, ask another authoritative service, or
accept intentional loss.

Keeping that distinction explicit now prevents a later supervisor chapter from implying
that "let it crash" means "nothing important is ever lost." Process isolation makes
failure containment tractable; it does not repeal data durability.

Checkpoint B extends the existing foundations project with
=books/erlang/code/foundations/src/pmsg_failure_lab.erl=. The lab is intentionally separate

working message protocol or pretending that hand-written restart loops are OTP.

The executable claims are:

1. an abnormal worker exit propagates through an active link to a non-trapping controller;
2. a trapping controller receives the linked abnormal exit as an =EXIT= message instead;
3. a monitor observes a worker crash without making the observer share that failure;
4. after =unlink/1= returns, a later worker crash no longer kills the former linked
   controller;
5. an explicit =kill= exit signal remains untrappable and is observed externally as target
   termination with reason =killed=.

Each test uses setup messages and monitor notifications as synchronization. Timeouts only
bound a failed test; they are never treated as proof that the expected event occurred.

#+end_src

*** A failure matrix for Project 1

Before OTP, we can now state the manual system's behavior with more precision:

| Event | Relationship | Observable outcome | Automatic recovery? |
|-
| server replies | request reference | correlated reply | n/a |
| server dies while caller waits | monitor | correlated =DOWN= -> tagged caller error | no |
| caller times out | local receive deadline | caller stops waiting | no cancellation |
| linked worker exits abnormally | link | peer exits unless trapping | no restart |
| trapping peer receives linked exit | link + =trap_exit= | =EXIT= message | policy still required |
| monitored worker exits | monitor | =DOWN= message | no |
| process state owner dies | process-local state | in-memory state is gone | no persistence |

Notice how little magic remains. Every row identifies a mechanism and a limit. OTP will
compose several of these mechanisms into conventions with explicit ownership, but it does
not change what process death means.

*** Debugging a failure cascade

When a real system loses several processes at once, preserve evidence before restarting
things manually:

1. Identify the earliest termination and exact reason you can establish.
2. Capture the relevant process tree or link relationships if available.
3. Separate =DOWN= observations from =EXIT= messages; they imply different relationships.
4. Check which processes trap exits. Do not infer it from a module name.
5. Ask whether any =unlink= or =demonitor= transition was concurrent with the failure.
6. Determine which state lived only in the terminated processes.
7. Only then ask whether restart is safe and what requests or external effects may be
   ambiguous.

The final two questions are where production debugging stops being "find the crashed
PID" and becomes systems engineering.

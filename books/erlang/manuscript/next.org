* Where the book goes next

We have crossed an important boundary. Project 1 taught the raw process mechanisms. Project
2 checkpoint A has now given recurring server and failure relationships standard contracts:
=gen_server= owns the generic server loop and system-message protocol, while a supervisor
owns child lifecycle and bounded restart policy. The tests also make the limit concrete:
a replacement process restores a worker process, not the dead worker's private state.

The next chapter turns this process tree into a real OTP application. That means learning
what an application resource file describes, what the application callback owns, how
application startup relates to the root supervisor, and which configuration belongs at that
boundary. Only after that local packaging/lifecycle contract is executable will the book
move into releases and target-system construction.

Before moving on, the reader should be able to answer these questions from mechanism rather
than vocabulary:

1. Which part of a =gen_server= is generic behaviour machinery and which part is the
   application callback module?
2. Why can a timed-out =gen_server:call= still complete server-side work even though modern
   OTP prevents a late synchronous reply from polluting the caller mailbox?
3. What does =start_link= say about lifecycle ownership that =start= does not?
4. Why does =one_for_one= express a dependency assumption rather than merely a convenient
   restart setting?
5. What exactly happens after more than the configured supervisor restart intensity occurs
   inside its period?
6. Why does a new child PID not imply recovery of the old child's process-local state?
7. Which guarantees still require persistence, idempotency, or replay outside the supervisor?

Chapter 13 will package the worker/supervisor tree as an application without changing those
answers. Chapters 14 onward then move outward: releases, distributed Erlang and connection
failure, explicit persistence/recovery boundaries, tracing and runtime observability,
Common Test, mailbox/backpressure experiments, networking, and production debugging.

The discipline stays the same: every new layer must state what contract it adds, what
failure it can observe or recover, what state it owns, and which uncertainty remains.

* Where the book goes next

The next chapters add links, monitors, exit signals, and =process_flag(trap_exit, true)= as explicit failure relationships, then separate those low-level mechanics from OTP behaviours. Project 2 converts the messaging service into an OTP application with =gen_server=; Project 3 introduces a real supervision tree, restart strategy and intensity, queue/admission decisions, and telemetry. Later projects add releases, distributed Erlang, persistence boundaries, testing, tracing, observability, and production debugging.

The progression is deliberate: syntax first, then explicit process mechanics, then OTP. The goal is to understand why the platform's abstractions work well enough to know when you are using them correctly -- and to recognize when a green process is merely hiding a bad protocol.

Before moving on, the reader should be able to answer four questions about Project 1 without hand-waving:

1. Which ordering property does the runtime actually guarantee, and which order is assigned only by our server after reception?
2. What exactly has happened when a caller times out? In particular, what has /not/ happened to work already accepted by the server?
3. What information does a monitor give the caller after server death, and why is that observation not yet a restart policy?
4. Which state is owned by the server process, and what would be lost if that process died right now?

Those questions become the bridge into fault semantics. A link is not just “a stronger monitor,” trapping exits is not supervision, and a supervisor is not persistence. The following project stages will keep those boundaries separate and then show how OTP composes them into a system whose failure behavior can be stated and tested.

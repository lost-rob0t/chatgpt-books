* Sources inspected
** GLEIF Supporting Documents
Official GLEIF documentation states that it publishes sample XML, JSON, and CSV files plus a sample GLEIF API response for verifying and testing current LEI data formats. The current format table identifies:
- LEI-CDF 3.1 for Level 1 records;
- RR-CDF 2.1 for Level 2 relationship records;
- Reporting Exceptions 2.1.

The official JSON sample package is named:
=2021-11-23_lei-cdf-3.1-and-rr-cdf-2.1-and-repex-cdf-2.1-json-samples_v1.1-final.zip=

** GLEIF RR-CDF 2.1 documentation
GLEIF documents Level 2 as the answer to “who owns whom”. RR-CDF relationship records identify the involved legal entities, relationship type/characteristics and dates, plus validation/reporting information. The current RR-CDF version is 2.1.

** GLEIF API documentation
GLEIF's official API documentation exposes direct-parent, ultimate-parent, direct-child and ultimate-child relationship endpoints. A direct-parent relationship is defined around the closest entity preparing consolidated financial statements for the child; ultimate-parent denotes the furthest such entity.

** Current StarIntel 0.9 boundary
The Book 1 adapter remains bound to the pinned canonical StarIntel 0.9 schema established in earlier passes. This pass does not copy GLEIF or StarIntel schema semantics into a second runtime/storage layer.

* Findings
** Official sample bundle is the preferred baseline fixture source
DOCUMENTED.

Project 1 should prefer GLEIF's own current-format JSON sample bundle as the canonical deterministic Level 1 + Level 2 teaching fixture source, rather than making ordinary tests depend on a live API response or a moving latest Golden Copy.

Rationale:
- it is published by the authoritative upstream data owner;
- GLEIF explicitly describes the samples as intended for verification/testing;
- one bundle covers Level 1, Level 2 relationships and reporting exceptions;
- it uses the current documented CDF versions;
- a frozen copy can be hashed and exercised offline after acquisition;
- it avoids choosing a production company solely because its current live record happens to contain a convenient ownership chain.

This does not make live API/Golden Copy testing useless. Live-source refresh belongs in a deliberate refresh/integration path, not the ordinary deterministic unit/research fixture path.

** Target upstream formats
DOCUMENTED.

- Level 1: LEI-CDF 3.1.
- Level 2 relationships: RR-CDF 2.1.
- Level 2 exceptions: Reporting Exceptions 2.1.

Book 1 must not conflate these GLEIF format versions with StarIntel =schema_version: "0.9.0"=. They are independent version domains.

** Required relationship semantics for the adapter
DOCUMENTED upstream; StarIntel mapping remains UNTESTED.

A normalized relation record must preserve at least:
- child/start-node identity;
- parent/end-node identity;
- direct versus ultimate relationship semantics;
- relationship type;
- relevant relationship periods/dates;
- registration status;
- validation/reporting provenance when present.

The adapter should emit canonical StarIntel entity/relation records and preserve source-specific detail in namespaced provenance/extensions rather than reimplementing GLEIF storage or StarIntel runtime semantics.

* Fixture decision
The final Project 1 public fixture is now specified as a *frozen subset of GLEIF's official JSON current-format sample bundle*.

Acquisition contract:
1. download the official JSON sample ZIP from GLEIF;
2. retain the original ZIP bytes or the exact selected JSON member bytes;
3. record source URL, retrieval date, archive/member names and SHA-256 hashes;
4. identify the smallest Level 1 records required by the selected RR-CDF relationship sample;
5. retain at least one genuine relationship record and, if compact enough, one reporting-exception example;
6. normalize only through the narrow Book 1 StarIntel adapter;
7. hash normalized artifacts;
8. validate every emitted StarIntel document against the pinned canonical StarIntel 0.9 schema;
9. record a provenance manifest sufficient to reconstruct source -> member -> normalized entity/relation -> split membership;
10. run offline in CI after the fixture is frozen.

* Implementation implications
Project 1 should now have two source modes:
- deterministic fixture mode: frozen official sample members, offline and hash-verified;
- refresh/integration mode: explicit live API or Golden Copy acquisition that creates a new snapshot/version rather than mutating the deterministic fixture silently.

Neither mode owns CouchDB, RabbitMQ, StarIntel server ingest, or a second StarIntel schema.

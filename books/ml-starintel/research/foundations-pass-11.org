** Primary algorithm sources
- Andrei Z. Broder, =On the Resemblance and Containment of Documents=, SEQUENCES 1997, pp. 21--29, DOI 10.1109/SEQUEN.1997.666900. The paper defines resemblance using set intersection/union and gives the min-wise sampling basis used to estimate resemblance without comparing every element of every document.

This is the primary locality-sensitive hashing framework source used here to justify an approximate candidate index rather than exact all-pairs search.

The paper presents sorted-neighborhood and multi-pass matching as a way to reduce candidate comparisons while recovering matches under alternate keys.

* Comparison
** Exact all-pairs Jaccard
- Semantics: exact for the frozen predicate.
- Scaling: pair count grows quadratically with record count.
- Role: verifier/oracle for small fixtures and for candidate pairs, not the scalable candidate enumerator.

** Sorted neighborhood / deterministic blocking
- Strength: deterministic, explainable, cheap candidate production when useful keys exist.
- Weakness: a blocking key can miss a true pair when the corruption lies in that key; multi-pass keys mitigate but do not remove this risk.
- Project 1 role: deterministic recall aid using source/domain fields or normalized lexical keys when such keys are available. Blocking output is candidate-only.

** MinHash + LSH
- Strength: directly targets set resemblance/Jaccard and reduces candidate search without exact all-pairs comparison.
- Weakness: probabilistic candidate recall near the threshold; results cannot be treated as the duplicate predicate itself.
- Project 1 role: general token-set candidate generator. Every returned pair is rechecked with exact normalized token Jaccard before an edge enters duplicate-component closure.

** Embedding-assisted candidates
Deferred. Embeddings introduce model/version/vector-distance semantics that are unnecessary for the current exact token-Jaccard leakage contract and belong later in the curriculum. They may become an additional candidate source, but cannot silently redefine Project 1 duplicate identity.

* Frozen candidate-generation contract
1. =normalize_text= and =token_set= from the tested Experiment C remain canonical for this Project 1 slice.
2. Exact normalized-text hashes are unioned first and never depend on an approximate index.
3. Near-duplicate truth remains =token_jaccard(left, right) >= 0.80=. Candidate algorithms never change this predicate.
4. Candidate output is an unordered lexical pair of stable record IDs. Pairs are canonicalized as =(min_id, max_id)= and deduplicated before verification.
5. Candidate sources are provenance-tagged. Initial supported source kinds are =exact-hash=, =block=, and =minhash-lsh=.
6. The initial scalable policy is the union of deterministic blocking candidates and MinHash/LSH candidates. A later benchmark may remove a redundant source only after recall behavior is measured on frozen controls/public corpora.
7. The MinHash implementation candidate is =datasketch==2.0.0=. The implementation must explicitly set =scheme="affine32"= and a fixed integer =seed= rather than inheriting mutable defaults. =num_perm= and LSH threshold/banding parameters must be emitted into the dataset/split manifest.
8. The LSH query threshold for the first implementation is the already-frozen exact near-duplicate threshold, 0.80. This is a candidate-index operating point, not a guarantee that every exact >=0.80 pair will be returned.
9. Exact Jaccard verification happens after candidate union and before transitive duplicate-component closure. False-positive candidates are harmless after exact verification; false-negative candidates are the primary research risk and must be measured explicitly.
10. Candidate generation is a pure dataset-preparation concern. No Book 1 index may become a StarIntel persistence/search service. Persistent runtime/storage/index ownership stays behind the StarIntel adapter.

* Predeclared evaluation protocol for the next execution pass
No results are claimed in this pass. Before measuring a larger corpus, the implementation pass must record:
- candidate-pair count versus exact all-pairs pair count;
- exact qualifying pair count from the small oracle corpus;
- candidate recall = qualifying pairs proposed / exact qualifying pairs;
- false-positive candidate count before exact verification;
- deterministic equality of canonical pair output across input order permutations;
- exact equality of final verified duplicate components versus the all-pairs oracle on the frozen Tier C fixture;
- wall-clock/runtime only when actually executed and with environment/corpus size recorded;
- all MinHash/LSH parameters, implementation version, normalization/tokenization version, seed, and source provenance in the artifact.

No minimum recall/runtime threshold is asserted as already achieved. The first benchmark may fail; a failed result is research output, not permission to tune the protocol after observing it.

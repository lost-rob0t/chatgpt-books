* Why content-defined selection
Using “the first 1,200 rows” would accidentally make the benchmark depend on loader ordering. The committed selector instead:
1. rejects texts with fewer than 20 normalized tokens;
2. computes SHA-256 over the decoded text;
3. removes byte-identical decoded texts by hash;
4. sorts eligible texts by full SHA-256;
5. takes the first 1,200 hashes.

The resulting manifest is recorded only as record IDs, source hashes, kinds, and a manifest SHA-256. Raw message bodies are not emitted to the benchmark artifact and are not committed to this repository.

* Controlled near-duplicate stress cases
A public corpus does not provide an authoritative label saying that every pair above Project 1's custom 0.80 token-Jaccard predicate is an intended duplicate. To avoid inventing such labels, this pass separates two roles:
- 20 Newsgroups supplies real public text and any naturally occurring qualifying pairs discovered by the exact oracle;
- the first 200 content-hash-selected originals receive one deterministic new alphanumeric token, producing 200 controlled near-duplicate stress cases.

Those derivatives are benchmark controls. They are explicitly *not* claims that the corresponding upstream messages are naturally duplicated or that the 20 Newsgroups class labels encode duplication.

* Exact oracle
The benchmark precomputes the normalized token set once for every selected/derived record and enumerates every unordered pair. For each pair it calculates the same exact Jaccard predicate used by Experiment C. This quadratic path is intentionally the oracle, not the production-scale candidate mechanism.

The oracle is executed once. Each =num_perm= configuration is then evaluated against the same frozen qualifying-pair set and exact component graph.

* Measurements frozen before execution
For each =num_perm= value, the artifact records:
- total candidate pairs;
- pair-reduction fraction relative to all unordered pairs;
- exact qualifying pairs proposed by the union;
- union qualifying-pair recall;
- qualifying-pair recall attributable to =minhash-lsh=;
- qualifying-pair recall attributable to =block=;
- qualifying-pair recall attributable to =exact-hash=;
- false-positive candidate count before exact verification;
- verified qualifying-pair count;
- exact component equality versus the all-pairs oracle;
- candidate-generation wall-clock seconds from =time.perf_counter()=;
- Python allocation peak observed by =tracemalloc=;
- full candidate parameters including datasketch version, normalization version, threshold, seed, scheme, band count, and rows per band.

The artifact also records Python/platform/scikit-learn/datasketch versions and the selected-manifest hash.

* Measurement boundaries
Runtime and memory are environment-sensitive observations, not universal performance claims. =tracemalloc= observes Python-managed allocations and is *not* total process RSS. The book may use these measurements to teach comparative experimental method only when it names the execution environment and exact corpus/protocol. It must not present a single CI runner timing as a deployment capacity claim.

No minimum recall, runtime, pair-reduction, or memory threshold is introduced after implementation. A poor result is a valid experimental result and must be recorded as such rather than tuned away.

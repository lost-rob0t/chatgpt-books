* What the counterexample establishes

BK01's =aggregate_synthetic_events= counts event IDs in three 60-second
windows. As its docstring correctly warns, its caller, not the function,
asserts window completeness. The native filter maps high/low counts into a
posterior and then forecasts the next high/low bucket. Its ten numerical
prior/transition/emission probabilities are *fixed*, not trained.

A complete invented inventory of five input events produces counts =[0,2,3]=
and next-window =P(high)=0.5059188644380984=. If the last three events
silently disappear and a producer rewrites both its event digest and its
=complete=true= seals, the same native algorithm accepts =[0,2,0]= and
returns =P(high)=0.3541110514301061=. This is not an upstream bug: the
producer supplied a false completeness premise.

BK10's new gate binds the invented input to a *separately frozen* tuple of
source ID plus observed timestamp (SHA-256
=ee9d63ba24cc5e9c4dee8ec857de2dfb30d62094a672faeafe1321fb43d9c292=).
It verifies provider Git source bytes, exact schema, event inventory, ordered
window boundaries and per-window source IDs *before* calling the native
filter. Rewriting all caller-controlled fields after event loss no longer
passes the frozen receipt check.

* Evaluated result, limits, and surprising metric

In the executed local pinned-provider run, 30 of 30 Python tests passed.
The unguarded counterfactual's next-high probability differed by
=0.1518078130079923=. Against the *one held-out low* outcome, clean Brier was
=0.255953897394335=, while the corrupted input's Brier was *lower*
(=0.12539463674493526=). A fortunate single-outcome score cannot establish
that the capture was correct: the corrupted forecast was based on fabricated
coverage. No calibration/generalization claim follows from one example.

These are 400-iteration *local Python 3.13.5 / x86-64* medians, not throughput or
precision claims. Native and gated timing scopes differ. The VM exposed an
Intel Xeon Platinum 8370C; total-process RSS was not measured.

* What production would need that this receipt does not prove

An independently frozen synthetic SHA-256 *cannot* establish live data-source
completeness. The test's receipt is hard-coded and could have been forged at
fixture creation. A production adapter would need an authorized source's
scope-specific monotonic offset/cursor or signed capture manifest, watermark,
late-event policy, window-close acknowledgement, event identity and provenance,
retention/replay contract and canonical schema validation. Otherwise report
=unknown/missing= and abstain from this filter; never fabricate zero counts.
This gate does not confer target, actor, database or runtime authority.

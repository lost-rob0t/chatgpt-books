* Failure: increasing timestamps are not contiguous timestamps
Issue [[https://github.com/lost-rob0t/chatgpt-books/issues/152][#152]] contains an executable zero-training capstone. Its baseline uses
the last two counts as a per-tick delta, then predicts at =as_of+1=.
Before this checkpoint =validate_observations= only enforced =t > previous_t=.
Consequently input with t=0,1,3 was accepted, but the difference between t=1
and t=3 was incorrectly treated as a one-tick change. The source is frozen
synthetic aggregate counts, not a live event stream. Gaps must be rejected,
not imputed as zeros or silently resampled.

The correction enforces =t == previous_t + 1= for every adjacent pair while
accepting any valid non-negative integer origin. The public =encode_state=
entry point revalidates its rows so direct callers cannot bypass the gate.
A malformed or partial BK01 window cannot be declared complete by this rule.

                             |
                    state: as_of=2, delta=1
                             |
                   candidates t=3: 4,5,6
                             |
           independent allowlisted HTML extraction
                             |
               reveal held-out count=6
#+end_example

* Model and time-domain boundaries
BK10 uses *abstract contiguous unit ticks*. No wall-clock origin, UTC offset,
window completeness signal or event-level provenance is supplied. BK01's
candidate binary filter expects complete aligned *60-second windows* with
event-source identifiers. BK06's candidate diffusion example expects four
continuous numeric observations and produces six continuous future readings.
No lossless mapping is currently established. Converting a BK10 tick to
seconds, padding a missing interval or fabricating an event source is forbidden
by this integration contract.

The frozen count witness still has a center=5 forecast and held-out count=6:
=absolute_error=1= for *one synthetic case*. Its 250000/500000/250000
scenario weights are hand assigned, not calibrated. This does not measure
generalization, model uncertainty or operational detection quality.

* CPU sizes and evaluation are different questions
| Provider | Fitted state | Training effort | CPU inference driver | Same-fixture metric |
|-
| BK10 arithmetic | zero parameters | none | validation linear in number of rows; one-step O(1) | n=1 absolute error 1 |
| BK01 binary filter | zero fitted parameters, fixed probabilities | none | forward pass per complete window | NOT RUN |
| BK02 latent dynamics | size not verified | epochs x examples x transitions | rollout steps x transition | NOT RUN |
| BK03/BK04 tiny LLM | model size unverified | tokens x attention/MLP backward passes | prefill plus token-by-token decode; cache RAM rises with context | NOT RUN |
| BK05/BK06 trajectory diffusion | BK06 has toy residual mixture | examples x noise steps x denoiser training | reverse steps x sampled trajectories | NOT RUN on shared data |
| BK07/BK08 tool calling | BK07 candidate policy; BK08 is an evaluator | DOM examples x model passes | DOM encoder + typed actions + independent executor | separate frozen HTML tasks |
| BK09 metadata classifier | no verified implementation | labeled records x feature/classifier passes | features plus scoring | NOT RUN |

Parameter count alone is not latency. Future experiment manifests must fix
CPU, RAM, threads, precision, software versions, train/test separation, seed,
artifact SHAs, sample counts, peak RSS, wall/CPU time, and task metrics
before comparing alternatives. No invented model accuracy or CPU benchmark is
promoted by this interface checkpoint.

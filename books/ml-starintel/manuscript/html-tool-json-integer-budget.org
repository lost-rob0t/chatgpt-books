* Scope: data ingestion, not model inference
This lab belongs to the offline HTML trace *data and evaluation* path
(issue #150). It does not change the model, decoder, fitted node-ranker
weights, accepted HTML selector grammar, or gold-trace scoring metrics.
All input is local JSONL. Network calls are neither necessary nor permitted.

A reproducible benchmark needs deterministic failure types. Before this
increment, a JSON integer with thousands of decimal digits reached the
standard Python integer converter. On environments with a configured decimal
integer digit limit, the reader raised a bare =ValueError= instead of its
published typed =TraceFailure("invalid_record")=. On an interpreter where that
limit was disabled, the same token could be accepted instead. The result was
not a stable data-ingestion contract across interpreters.

* Bounded token before numeric conversion
The reader now has an explicit =MAX_JSON_INTEGER_DIGITS = 256= contract.
=read_jsonl= registers a =parse_int= callback with =json.loads=. The callback
counts decimal digits on the *raw numeric token* (excluding a leading minus)
and raises =invalid_record= before calling =int= if the limit is exceeded.

This is intentionally a *JSON token* rule, not a limit on the length of a
quoted string. A string containing 6,000 digits is still a string and must
be validated by the later record schema, rather than misclassified as an
integer. Finite floats retain their separate =parse_float= path and
non-finite constants remain rejected.

| Input fragment | Reader outcome | Reason |
|----------------+----------------+--------|
| ={"n": 7}= | Accept | Seven is a one-digit integer token. |
| ={"n": -0}= | Accept | The numeric token has one decimal digit. |
| ={"n": 999...}= (256 digits) | Accept | At the explicit boundary. |
| ={"n": 999...}= (257 digits) | =invalid_record= | Above token budget. |
| ={"n": 999...}= (6,000 digits) | =invalid_record= | Never delegates huge token to =int=. |
| ={"n": "999..."}= (6,000-character string) | Accept at JSONL decoding | Quoted data is not an integer token. |
| ={"n": 1e999999}= | =invalid_record= | Non-finite float rejected by the existing float converter. |

"Accept" here means that JSONL token decoding succeeds. It does *not*
assert that the object is a canonical BK08 record; the evaluator applies
separate identity, field, fixture, and trace checks later.

* Why this is an evaluation invariant
1. The reader should not depend on an interpreter's configurable decimal
   conversion limit.
2. A typed input error must remain typed when emitted by the CLI, rather
   than becoming an unhandled stack trace.
3. Quoted literals, finite floats, and legitimate integer tokens should not
   be reinterpreted by the new integer converter.
4. The fixed token limit is an ingestion budget, not a StarIntel schema
   change or an assertion that Python cannot represent larger integers.

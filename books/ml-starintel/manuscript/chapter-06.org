** Chapter 6 -- Regression: Predicting a Quantity Without Fooling Yourself
:PROPERTIES:
:ID:       70021bd7-53c7-4314-853e-1e669df31198
:END:

Project 1 gave us something more valuable than a clever model: a trustworthy boundary around the data. We know which rows belong together, which information is allowed at prediction time, which records are held out, and which source evidence produced the experimental view.

Now we can finally fit a model that uses features.

Regression is the right first step because the mechanism can be derived almost completely with algebra. We do not need to invoke a neural network, a black-box optimizer, or a large framework. We can start with the constant baseline from Chapter 1, add one slope, inspect exactly what least squares is minimizing, and then scale the same idea to several features with scikit-learn.

The teaching task in this chapter is deliberately synthetic: predict a numeric =review_minutes= quantity from three deterministic features of a StarIntel-style document view. The rows are Tier C controls. They do *not* describe real analyst productivity and they do not establish a production model. Their purpose is to make fitting, held-out evaluation, residuals, outliers, extrapolation, and coefficient-identifiability failures observable under a known data-generating process.

The rule from the previous chapters still applies:

#+begin_quote
A better model does not excuse a worse experiment.
#+end_quote

*** 1. Regression answers a numeric question
:PROPERTIES:
:ID:       b94a4f3a-c920-4bb6-9614-1ecedbd1e581
:END:

A regression model predicts a quantity rather than a discrete class label.

Examples of legitimate future tasks might include estimating processing latency, resource demand, expected document volume, or another measured continuous outcome. Before using any of those in a real system we would need an explicit target definition, measurement procedure, prediction time, admissible features, and deployment population.

For the lab we use a simpler contract:

#+begin_example
one example       = one synthetic StarIntel-style document view
target             = synthetic review_minutes
features           = token_count, relation_count, source_count
evaluation unit    = synthetic case group
train/test policy  = whole groups stay together
#+end_example

The target is generated by deterministic code with a small deterministic error term. Because we own the control, we know that a linear relationship exists. That makes the exercise useful for verifying mechanics. It would be circular evidence for a claim that real investigation work is linear, so we make no such claim.

*** 2. Start where Chapter 1 left off

The Chapter 1 constant regressor predicts the training mean for every test row. Under squared error that is the best possible single constant.

If the training targets are \(y_1,\ldots,y_n\), the model is

\[
\hat y = \bar y.
\]

That baseline ignores every feature. A regression model earns its complexity only if feature-dependent predictions improve the held-out task under the same evaluation boundary.

Suppose one feature \(x\) appears useful. The smallest extension is a line:

\[
\hat y = b_0 + b_1x.
\]

The intercept \(b_0\) is the prediction at \(x=0\). The slope \(b_1\) tells us how much the prediction changes when \(x\) increases by one unit, holding the model form fixed.

Those are fitted parameters. We do not choose them by eye.

*** 3. Derive the one-feature least-squares line

For observed pairs \((x_i,y_i)\), define residuals

\[
e_i = y_i - (b_0+b_1x_i).
\]

Ordinary least squares chooses \(b_0\) and \(b_1\) to minimize the residual sum of squares

\[
\operatorname{RSS}(b_0,b_1)
  = \sum_i [y_i-(b_0+b_1x_i)]^2.
\]

The centered solution is especially useful for understanding the mechanism. Let \(\bar x\) and \(\bar y\) be the training means. Then

\[
b_1 =
\frac{\sum_i(x_i-\bar x)(y_i-\bar y)}
     {\sum_i(x_i-\bar x)^2}
\]

and

\[
b_0 = \bar y - b_1\bar x.
\]

The denominator is the amount of variation in the input feature around its training mean. If every training value of \(x\) is identical, that denominator is zero. There is no observed information from which to estimate a slope.

The Chapter 6 implementation treats that as a failure, not as an excuse to return a made-up coefficient:

#+begin_src python
line = fit_simple_ols([0, 1, 2, 3], [3, 5, 7, 9])
assert line.intercept == 3.0
assert line.slope == 2.0
#+end_src

For the exact points above, the fitted line is \(\hat y=3+2x\). The unit test also feeds a zero-variance feature and requires the fit to fail closed.

This is our first example of a general debugging habit: inspect whether the data can identify the quantity the model is trying to estimate before blaming an optimizer.

*** 4. Multiple features keep the same idea

A real experimental view usually has more than one useful feature. With \(p\) features the linear model becomes

\[
\hat y = b_0 + b_1x_1 + b_2x_2 + \cdots + b_px_p.
\]

In matrix notation we often write

\[
\hat{\mathbf y} = X\mathbf b + b_0.
\]

The objective is still residual squared error. Current scikit-learn documents =LinearRegression= as ordinary least-squares linear regression and states that it minimizes the residual sum of squares between observed targets and predictions [cite:@sklearn2026linearregression]. The library gives us a robust implementation; it does not change what problem we are solving.

The lab uses:

#+begin_src python
model = LinearRegression()
model.fit(x_train, y_train)
prediction = model.predict(x_test)
#+end_src

That three-line interface can hide a dangerous amount of experimental state if we do not control where =x_train= and =y_train= came from. The important part is not the constructor. The important part is that the test targets never participate in =fit=.

The focused test proves this boundary behaviorally. It changes only a held-out group's target values by a huge amount and verifies that the fitted intercept and coefficients do not move. Test error changes, as it should; training-derived state does not.

*** 5. Keep the split upstream of the estimator

Chapter 5 compiled dependency constraints into stable group IDs before any model fitting. Chapter 6 consumes that idea instead of reinventing it.

The synthetic control contains twelve case groups with three records each. Eight complete groups are declared training groups; four complete groups are held out. The implementation checks that the sets of group IDs do not overlap.

#+caption: Chapter 6 keeps evidence and split semantics upstream of fitting. Baseline and OLS use the same training rows; only held-out rows feed the metrics and residual audit. Failure injection creates a new experiment rather than rewriting source evidence.
#+attr_html: :alt Validated rows flow through a declared group split into a training-only mean baseline and training-only ordinary least-squares fit, then held-out metrics, residual analysis, failure injection, and an explicit experiment-revision loop.

This separation matters even for a trivial linear model. A leaked linear regression can look impressive for exactly the same reasons as a leaked classifier or embedding model.

A reusable rule is:

#+begin_quote
Split first according to the task contract. Fit every learned quantity only on the training side. Evaluate only after the fitted state is frozen.
#+end_quote

*** 6. A baseline and a model must face the same test

The lab compares two predictors on exactly the same held-out rows:

1. the Chapter 1-style baseline, fitted as the mean of the *training* targets;
2. a three-feature ordinary least-squares model, fitted on the same training groups.

This comparison would be invalid if the baseline used a different test population, a different temporal boundary, or a mean computed from all rows. Simplicity does not exempt the baseline from the experiment contract.

The synthetic generator creates =review_minutes= from a declared linear rule plus a small deterministic error term. Therefore the OLS model should have a structural advantage over the constant predictor on this control. The test suite requires lower held-out RMSE for OLS and requires an \(R^2\) above 0.9 on this *frozen synthetic case only*.

That assertion is not a production quality threshold. It is a regression test for a teaching fixture deliberately constructed to contain a recoverable linear signal.

*** 7. Error metrics answer different questions
:PROPERTIES:
:ID:       1b5459b9-a738-4d99-b5f2-afff046aa71a
:END:

A residual is

\[
e_i = y_i-\hat y_i.
\]

Positive residuals mean the model predicted too low; negative residuals mean it predicted too high.

From residuals we can build several metrics.

**** Mean absolute error

\[
\operatorname{MAE} = \frac{1}{n}\sum_i |e_i|.
\]

MAE is in the same units as the target. Current scikit-learn documentation defines it as a non-negative regression loss whose best value is zero [cite:@sklearn2026mae]. For our control, the unit is synthetic review minutes.

**** Root mean squared error

\[
\operatorname{RMSE}
=
\sqrt{\frac{1}{n}\sum_i e_i^2}.
\]

RMSE is also in target units, but squaring makes large residuals contribute disproportionately before the final square root. Scikit-learn exposes =root_mean_squared_error= directly in its current regression metrics API [cite:@sklearn2026rmse].

**** Coefficient of determination

For non-constant targets,

\[
R^2
=
1 -
\frac{\sum_i(y_i-\hat y_i)^2}
     {\sum_i(y_i-\bar y)^2}.
\]

A common beginner mistake is to assume that \(R^2\) must lie between zero and one. It does not. On held-out data a model can be worse than the constant reference and therefore obtain a negative value. Current scikit-learn documentation explicitly notes that the best possible score is 1.0 and that the score can be negative [cite:@sklearn2026r2].

Do not compress these metrics into "the regression score." Each emphasizes something different, and none rescues a badly designed test set.

*** 8. Residuals are a debugging interface

A scalar metric tells us how much error exists under one summary. Residuals tell us where that error lives.

After fitting, inspect at least:

- residual versus predicted value;
- residual versus important input features;
- unusually large positive and negative residuals;
- residuals by source, group, time period, and other operational slices that were declared before looking for a good story;
- whether errors grow when inputs approach or exceed the observed training range.

Patterns matter. A curved residual pattern can indicate that the relationship is not well described by a straight line. A fan-shaped pattern can indicate that error variance changes with the prediction scale. A small cluster of huge residuals may indicate data errors, a missing subgroup, or a real tail the model does not represent.

The executable lab writes two reproducible SVGs: predicted versus actual, and residual versus predicted. They are generated from the same report used by the tests rather than being hand-drawn illustrations.

This is a useful distinction between /diagnosis/ and /optimization/. We inspect residuals to understand what the model is failing to represent. We do not automatically add complexity until the plot looks aesthetically random.

*** 9. Failure injection -- one bad target
:PROPERTIES:
:ID:       9bdab2c5-e112-49f1-8633-0e5663e8de5d
:END:

To make metric sensitivity concrete, the lab adds sixty synthetic minutes to the first held-out target while leaving predictions unchanged.

Nothing is retrained. We are asking a diagnostic question:

#+begin_quote
How does one large residual change the summaries of the same prediction vector?
#+end_quote

The regression test requires the increase in RMSE to exceed the increase in MAE for this frozen failure case. That is a fixture-specific executable consequence of squaring the residual before averaging.

Do not generalize the exact numeric delta. Change the sample size, original residuals, or injected error and the numbers change. The durable lesson is mechanical: squared-error summaries amplify large misses more strongly than absolute-error summaries.

In a real system, a huge residual should trigger investigation before deletion. The row might be corrupt. It might also be the exact rare case the model needs to handle.

*** 10. Failure injection -- extrapolation has no warranty
:PROPERTIES:
:ID:       d02b2eb2-7c37-4718-9f18-4fbca19623d9
:END:

A linear formula will happily produce a number outside the region represented by its training data.

The lab constructs one explicit probe whose =token_count= exceeds the observed training maximum. The model returns a prediction because algebra permits it. The report also records:

#+begin_example
outside_observed_training_range: true
label_available: false
#+end_example

That second line is important. Without a ground-truth outcome we cannot score the probe. A number coming out of =predict= is not evidence that the model works there.

For multiple features, "inside the range" is more complicated than checking each column independently; combinations can be unusual even when every individual feature falls between its training minimum and maximum. Later chapters will add richer distribution-shift diagnostics. For now, the chapter records the simplest support warning rather than pretending that linearity licenses arbitrary extrapolation.

*** 11. Coefficients are not automatic explanations

**** Duplicate predictors can destroy coefficient identifiability
:PROPERTIES:
:ID:       7e8ae345-5bd3-4ab1-8d74-e9ad77abec8f
:END:

There is a second reason to distrust a coefficient-by-coefficient story even before causality enters the picture: the design matrix may not contain enough independent information to identify every coefficient separately.

Take the fitted model and add a fourth column that is an exact copy of =token_count=. Call its two coefficients \(b_t\) and \(b_d\). Their contribution is

\[
b_t x + b_d x = (b_t+b_d)x.
\]

Predictions depend on the *sum*. If one solution changes \(b_t\) by \(+c\) and \(b_d\) by \(-c\), the prediction is unchanged for every row. The data therefore cannot tell those two individual coefficients apart.

The Chapter 6 failure probe does exactly this after the normal fit. It refits the same training targets with =token_count= duplicated, while leaving the original model and held-out rows untouched. Current scikit-learn documentation exposes the rank and singular values of the dense training matrix through =LinearRegression.rank_= and =LinearRegression.singular_= [cite:@sklearn2026linearregression]. The report records both designs rather than guessing from coefficient magnitudes.

The executable acceptance condition is intentionally structural:

- the original three-column training design must have full column rank on this frozen control;
- the four-column duplicated design must have rank smaller than its feature count;
- predictions from the base and duplicated designs must agree within a declared floating-point tolerance on the same held-out rows;
- the two duplicated =token_count= coefficients must sum to the original =token_count= coefficient within tolerance.

We do *not* require a particular split between the two duplicate coefficients. A least-squares solver can choose one representative among multiple coefficient vectors that produce the same predictions. The individual values are not separately identified by these data.

This is stronger than saying "correlated features can be confusing." Exact duplication gives us a case we can prove. Near-collinearity is the messier real-world version: coefficients may become highly sensitive to small changes even when predictive behavior moves much less. That broader stability question needs its own experiment before we attach measured claims to it.

Now consider the more familiar interpretability trap. Because a linear model exposes coefficients, it is tempting to read them as causal effects:

#+begin_example
relation_count coefficient = 2.4
therefore each additional relation causes 2.4 more minutes
#+end_example

That conclusion does not follow from ordinary predictive regression.

A coefficient describes the fitted predictive relationship conditional on the features included in this model and the sampled data. Correlated features, omitted variables, measurement choices, selection effects, and the synthetic/observational nature of the data all affect interpretation.

In our control the generating rule is known because we wrote it. In a real StarIntel-derived dataset we usually do not get that privilege. Treat coefficients first as model parameters to inspect and debug, not as causal proof.

This boundary becomes even more important when later models have thousands or millions of parameters.

*** 12. What scikit-learn is doing -- and what it is not doing

Scikit-learn's =LinearRegression= gives us fitted coefficients, an intercept, and a predictable estimator interface. In the current 1.9.1 documentation, OLS is described as minimizing residual sum of squares; the implementation notes identify least-squares solver machinery behind the estimator [cite:@sklearn2026linearregression].

The library does *not* know:

- whether =review_minutes= was measured correctly;
- whether two records describe the same investigation;
- whether a future feature leaked into training;
- whether a target is ethically or operationally appropriate;
- whether the held-out groups resemble the population where the model will be used;
- whether an extrapolation is safe;
- whether a coefficient is identifiable from the supplied design;
- whether a coefficient should be interpreted causally;
- whether a smaller RMSE is worth the operational complexity.

Those belong to the experiment and system design around the estimator.

This is why the project architecture keeps the StarIntel evidence/document boundary outside the model code. The ML project consumes an experimental view. It does not reimplement StarIntel persistence, queues, actors, authorization, or search.

*** 14. Debugging sequence for a bad regression result

When a regression model looks suspicious, use this order before changing model families:

1. Re-read the target definition. Are we predicting the quantity we think we are?
2. Verify train/test membership and group/time constraints.
3. Verify that all fitted transforms saw training rows only.
4. Compare against the training-only constant baseline.
5. Inspect target units and impossible values.
6. Inspect MAE and RMSE together instead of one scalar alone.
7. Plot residuals and identify which rows dominate error.
8. Check whether test examples are outside the observed training support.
9. Check for duplicated or highly dependent records that escaped the split contract.
10. Check whether predictors are duplicate or linearly dependent before interpreting individual coefficients.
11. Only after those checks decide whether the model form is too simple.

This sequence is intentionally boring. Boring diagnostics are cheaper than discovering after deployment that a fancy model learned a broken table.

*** 15. What this milestone proves -- and does not prove

The Chapter 6 code is designed to establish a bounded set of facts once its focused tests and book checks pass:

- the first-principles one-feature OLS implementation recovers an exact known line;
- zero-variance input is rejected rather than silently assigned a slope;
- MAE, RMSE, and \(R^2\) formulas are executable;
- complete synthetic groups remain disjoint across the declared split;
- test-target mutation cannot change training-fitted coefficients;
- OLS beats the training-mean baseline on the deliberately linear frozen control;
- one injected large error affects RMSE more strongly than MAE in the frozen failure case;
- an out-of-range prediction is explicitly labeled as an unscored extrapolation probe;
- an exact duplicate predictor makes the augmented dense design rank-deficient while leaving the held-out prediction vector equivalent within the tested tolerance.

It does *not* prove:

- that real analyst effort follows a linear model;
- that these three features are appropriate production features;
- that the fixture metrics estimate production quality;
- that OLS is the best model for later StarIntel tasks;
- that coefficient signs are causal explanations;
- that near-collinear real-world features will have a particular coefficient-instability magnitude;
- that the model is robust to arbitrary outliers or distribution shift;
- that any production integration, throughput, or deployment behavior has been tested.

Those limits are part of the result, not fine print.

**** ★ Attack the training boundary

**** ★ Compare metrics

**** ★ Negative \(R^2\)

**** ★ Residual plot failure lab

**** ★ Group leakage regression

Create repeated rows for each synthetic case and compare a row-random split with the existing group split. Do not claim a general leakage effect from one fixture; report only the exact contamination and metric difference you measured.

**** ★ Extrapolation audit

Add a helper that reports, for every test row, whether each feature lies outside the observed training min/max. Explain why this per-feature check is useful but insufficient in multiple dimensions.

**** ★ Metric provenance

**** ★ Beyond ordinary least squares
